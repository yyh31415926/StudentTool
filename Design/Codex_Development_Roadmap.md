## 0. 如何使用这份文档

这份文档的作用是**把"做一个网站"拆成 Codex 能安全执行的多个阶段**。它回答四个问题：

1. **这个阶段要做什么**（任务清单）

## 1. 开发原则

### 1.1 不一次开发整个网站

- 每个 Phase 只解决一个明确目标，**一次只交付一块**。
- 禁止在一个任务里同时做"架构 + 功能 + 视觉 + 测试"。
- 每一阶段产出的都是一个**可运行、可访问、可验证**的中间状态，而不是"半成品堆料"。

### 1.2 优先搭架构，再增加功能

- 先做**工具系统内核**（Phase 2），再做**具体工具**（Phase 3 起）。
- 理由：内核是"加工具 = 加一个文件"的基石。内核做对，后面 6 个工具都是重复劳动；内核敷衍，每加一个工具都是痛苦。
- 同理：先做**统一 UI 组件**（Phase 1），再做**具体页面**；先做**存储封装**（Phase 5），再做**使用它的功能**（Phase 6）。

### 1.3 每个阶段完成后可运行测试

- 测试基础设施在 **Phase 0 就建立**，不是最后补。
- 每个 Phase 交付时，测试、lint、构建三绿（见 §0.5）。
- 新功能 = 新测试，同步提交，**不允许"先上线、后补测试"**。

### 1.4 避免过度设计

| 过度设计的表现 | 正确做法 |
| --- | --- |
| 为"将来可能"预留大量未使用的抽象 | 只抽象"现在或下一个 Phase 确定会用到"的东西 |
| 工具定义里加一堆用不到的字段 | 只用 v0.2 §3.5 契约里的字段 |
| 一个工具一个模板 | 复用现有模板，模板总数 ≤5 |
| 为可能的需求建接口层 | 存储接口层是唯一例外——因为账号同步是**已规划**的明确方向 |
| 引入重量级状态管理、UI 库 | 不引入。用 React 内置能力 |

**判断标准**（引用技术研究文档的结论）：**过早抽象和过晚抽象一样有害。** 当"多样性来自数据"（如单位种类）用数据表吸收；当"多样性来自逻辑"（如编码算法）才写代码。

### 1.5 一次只做一件事

- 不夹带重构、不顺手优化无关代码、不删除已有功能。
- 发现某个地方确实需要重构 → **单独提出为独立任务**，不混在当前 Phase 里。
- 每个 Phase 内部的任务按顺序执行，前一任务通过后再做下一个。

## 2. Phase 0 · 项目初始化

### 目标

**建立一个可以运行的 Next.js 项目。**

### 前置条件

- 无（本 Phase 是起点）。但建议先完成 §0.2 的"项目名称"定案，避免后续改动存储键名前缀。

### 任务清单

| # | 任务 | 说明 |
| --- | --- | --- |
| 1 | 创建 Next.js 项目 | 使用官方脚手架创建，启用 **TypeScript**、**App Router**、**Tailwind CSS**、**ESLint**、**`src/` 目录** |
| 2 | 确认 `src/` 布局 | 项目必须采用 `src/` 作为源码根目录（见 AGENT_RULES §8.2） |
| 3 | 建立基础目录骨架 | 创建 `lib/`、`components/`、`hooks/`、`types/`、`content/`、`tests/` 等空目录（不写逻辑，只搭结构） |
| 4 | 配置测试框架 | 引入测试框架（建议 Vitest），配置好脚本与一个冒烟测试 |
| 5 | 配置代码质量 | 确认 ESLint 生效；TypeScript 严格模式开启 |
| 6 | 配置 `.gitignore` | 排除 `node_modules/`、`.next/` 等构建产物（**第一次提交前必须配好**） |
| 7 | 配置路径别名 | 配置 `@/` 指向 `src/` |
| 8 | 跑通四件套 | `dev` / `build` / `lint` / `test` 四条命令全部可运行 |

### 涉及目录

- 项目根目录（配置文件）
- `src/`（空骨架）
- `tests/`（冒烟测试）
- `public/`（脚手架默认资源）

### 不要做

- ❌ 不写任何工具逻辑、页面逻辑、业务组件
- ❌ 不引入 UI 组件库、状态管理库等任何额外依赖
- ❌ 不创建 `Documents/`、`Design/` 下的新文件（文档由人类协作者管理）

### Codex 工作规范

| 项 | 内容 |
| --- | --- |
| **先读** | `AGENT_RULES.md` §3、§8（技术栈与目录结构）；`Documents/WebsiteDesignDocument_v0.2.md` §7 |
| **修改目录** | 仅项目根目录配置文件与 `src/`、`tests/` 空骨架 |
| **不碰** | `Documents/`、`Design/`、`AGENT_RULES.md` |
| **完成后测试** | 依次运行 `npm run dev`（可启动）、`npm run build`（成功）、`npm run lint`（无错误）、`npm run test`（冒烟测试通过） |

### 验收标准（门禁）

- [ ] `npm run dev` 可以运行，首页（`http://localhost:3000`）可以访问

- [ ] TypeScript 严格模式开启，且无类型错误
- [ ] `src/` 布局确认（不是根目录 `app/`）

| 风险 | 应对 |

## 5. Phase 3 · 第一个工具：字数统计

### 目标

**交付第一个完整可用的工具：字数统计（`char-count`）。**

### 为什么选字数统计作为第一个工具

| 理由 | 说明 |
| --- | --- |
| **交互最简单** | 纯输入 → 实时统计，无"转换"按钮、无下拉、无复杂状态、无异步 |
| **算法最易验证** | 边界清晰，容易写满 10+ 组用例 |
| **能立即验证模板机制** | 正好用 Phase 2 的 CounterTemplate，闭环验证"内核"是否好用 |
| **风险集中在"口径定义"** | 真正的难点是"字符数 / 字数 / 词数 / 行数"怎么算，这是**契约精确性**的绝佳训练，为后续工具打样 |
| **不踩后续的坑** | 不涉及 Unicode 编码（Base64 的坑）、精度（进制转换的坑）、安全（Markdown 的坑），先专心跑通全流程 |

**它验证的链路**：定义文件 → 注册表 → 动态路由 → 模板 → 算法纯函数 → 测试 → 页面展示。**这条链路跑通，后面 5 个工具都是重复。**

### 任务清单

| # | 任务 | 说明 |
| --- | --- | --- |
| 1 | 工具定义 | 完整契约，含 tags（`语文/作文/写作/高中`）、pinyin（`zs`）、tip、exampleInput |
| 2 | 算法（纯函数） | 统计字符数 / 字数 / 词数 / 行数；明确中英文混排、标点、换行的口径 |
| 3 | 完善 CounterTemplate | 边输入边实时显示，无"转换"按钮 |
| 4 | 页面展示 | 标题、说明、示例按钮、复制、收藏占位 |
| 5 | 测试 | ≥10 组边界用例 |

### 涉及目录

- `src/lib/tools/definitions/char-count.ts`（+ 聚合入口加一行）
- `src/components/tools/templates/`（CounterTemplate）
- `tests/tools/char-count.test.ts`

### 不要做

- ❌ 不实现收藏的真实存储（收藏按钮此时为占位，Phase 5 接入）
- ❌ 不做其他工具
- ❌ 不做搜索（Phase 6）

### Codex 工作规范

| 项 | 内容 |
| --- | --- |
| **先读** | `Documents/WebsiteDesignDocument_v0.2.md` §3.5（契约）、§3.6（验收）；`AGENT_RULES.md` §4.4 |
| **修改目录** | `src/lib/tools/definitions/`、`src/components/tools/templates/`、`tests/tools/` |
| **不碰** | `src/lib/storage/`、`src/app/page.tsx`（除注册表自动体现外不改首页代码）、`Documents/`、`Design/` |
| **完成后测试** | 运行 `char-count` 测试全绿；手动验证空输入、中英文混排、纯标点；`lint` / `build` 通过 |

### 验收标准（门禁）

## 14. 开发任务粒度建议

### 14.1 单个 Codex 任务的范围上限

🔴 **一次 Codex 任务不得超出以下范围：**

| 维度 | 上限 |
| --- | --- |
| 主题 | **一个 Phase 的一个任务项**（不是整个 Phase） |
| 涉及文件 | 通常 ≤ 8 个文件（含测试）；一个工具的定义 + 算法 + 测试 = 约 3–4 个文件 |
| 范围 | 只做一类事（架构 / UI / 工具 / 测试中的一类） |
| 时长目标 | 单次可完成、可验证，不留"待下次继续"的半成品 |

**判断标准**：如果一个任务需要输出超过一份"修改前说明"才说得清，说明它应该拆开。

### 14.2 四类任务的标准形态

| 任务类型 | 做什么 | 交付 | 例子 |
| --- | --- | --- | --- |
| **架构任务** | 搭骨架、定义类型与接口 | 类型/接口/注册表 + 冒烟验证 | Phase 2 的"注册表 + 查询函数" |
| **UI 任务** | 布局、组件、样式 | 组件 + 三档断点/对比度验证 | Phase 1 的"基础 UI 组件" |
| **工具任务** | 定义 + 算法 + 页面 | 工具 + ≥10 用例 + 手动验证 | Phase 3 的字数统计 |
| **测试任务** | 为已存在功能补/改测试 | 测试 + 全绿 | 某工具的边界用例补齐 |

### 14.3 推荐的任务拆分顺序

一个 Phase 的推荐拆分粒度（以 Phase 3 为例）：

```
任务 1：字数统计的工具定义（契约字段 + 聚合入口一行）       ← 工具任务
任务 2：字数统计算法（纯函数）                            ← 工具任务
任务 3：算法测试（≥10 组边界用例）                        ← 测试任务
任务 4：CounterTemplate 完善 + 页面接入                   ← UI 任务
任务 5：Phase 3 整体验收（三绿 + 手动验证）               ← 架构任务（收口）
```

**每个任务独立提交、独立可验证**，上一个任务三绿后再做下一个。

### 14.4 禁止的拆法

| 反模式 | 问题 |
| --- | --- |
| 一个任务做完整条线（如一次做 3 个工具） | 出错难定位，验收难执行 |
| 一个任务同时改架构 + 功能 + 视觉 | 违反"一次只做一件事" |
| "顺便修一下发现的小问题" | 夹带，破坏任务边界 |
| 任务大到无法一次验证 | 必然留下半成品 |

### 14.5 测试任务的粒度

| 规则 | 说明 |
| --- | --- |
| 测试与实现**同任务提交** | 工具任务自带的测试就在该任务内完成 |
| 独立测试任务仅用于"补课" | 补历史欠账时单独开测试任务 |
| 每个工具 ≥10 组用例 | 硬性下限，见 AGENT_RULES §4.4 |
| 不写"为了通过而通过"的用例 | 覆盖边界，不是凑数 |
