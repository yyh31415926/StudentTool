## 0. 评审摘要（速览）

**总体判断**

"工具负责效率，动漫负责体验"是一个干净、可执行、且确实存在市场空隙的理念。市面上的在线工具站（各类"工具大全""开发者工具箱"）普遍是密集列表、冷硬配色、广告干扰、英文优先；而二次元风格的站点大多止步于"好看的活动页"，没有真正的工具能力。这个交叉位置是真空的，值得做。

但文档目前把"工具集合"当成了产品。**工具集合不是产品，工具集合是内容。** 用户不会因为"这里工具多"而回来，因为搜索框里的"在线进制转换"一秒钟能找到十个。产品必须回答的问题是：**用户为什么要记住这个网址，而不是每次搜索？**

**必须解决的三个问题**

| # | 问题 | 严重度 |
| --- | --- | --- |
| 1 | 定位未收敛：既是"高中生+大学生"的双用户画像，又是"日常数字处理"的泛需求，导致工具选型和首页都要同时讨好两类人 | 高 |
| 2 | 第一批 6 个工具中，Base64 / JSON / Markdown 对高中生几乎零价值，工具集与"高中生"画像错配 | 高 |
| 3 | 分类维度不统一（学科 / 用途 / 载体三种维度混用），且"文件工具"是空分类 | 中高 |

**最大的三个机会**

| # | 机会 | 说明 |
| --- | --- | --- |
| 1 | **空状态与反馈态的角色化** | 这是"动漫负责体验"最有价值、也最被低估的落地场景。工具站的空状态、错误提示、加载、成功反馈通常极其冰冷，这里可以做成本项目最强的记忆点 |
| 2 | **"学生专属工具空间"的归属感** | 不做成"工具箱"，做成"我的工作台"。免登录 + 本地收藏/最近使用已经具备基础，只差一层"这是你的地方"的叙事 |
| 3 | **中文学生的刚需长尾词** | "在线进制转换""单位换算 物理""字数统计 作文"，中文长尾搜索量大、竞争弱、转化精准，是低成本获客的入口 |

## 1. 当前产品定位分析

### 1.1 现有定位陈述

> 面向高中生和大学生的在线学习辅助工具网站。通过简洁易用的工具、可爱的动漫视觉设计以及良好的用户体验，帮助学生快速解决学习过程中遇到的数字处理需求。

**这段陈述有两个问题**：一是"学习辅助工具"过宽，可以指习题、题库、笔记、番茄钟，什么都像；二是"数字处理需求"过窄，把范围锁死在"数据处理"上，与"高中生"的低频数据需求形成矛盾。

### 1.2 定位合理性评估

| 维度 | 判断 | 说明 |
| --- | --- | --- |
| 目标用户明确度 | ⚠️ 部分合理 | 高中生与大学生是两个不同的需求集群，文档未区分主次。建议**以高中生为主、大学生为辅**，理由见 1.4 |
| 使用场景清晰度 | ❌ 不清晰 | "学习过程中"太泛。真实场景应该是：做完物理作业要换算单位、写作文要数字数、上信息课要转进制。**场景应当具体到"作业/课堂/自学"三类** |
| 差异化程度 | ✅ 合理 | "学生向 + 动漫体验"确实是空白位，不是自嗨 |
| 竞争壁垒 | ⚠️ 偏弱 | 工具本身无技术壁垒，任何人可复制。真正的壁垒只能来自**内容质量（准确性、中文适配）+ 视觉一致性 + 品牌记忆** |
| 视觉理念一致性 | ✅ 合理 | "工具优先、动漫辅助"这条边界写得很清醒，是整个文档最好的部分 |
| 可执行性 | ✅ 合理 | 无后端、LocalStorage、Next.js 静态化，第一阶段完全可落地 |
| 可持续性 | ⚠️ 有隐患 | 免费开源 + 无商业模式 + 需要长期维护，缺少维护者激励设计 |
| 定位与角色定位的一致 | ✅ 合理 | 明确"角色是视觉资产，不是 AI 助手"，避免了最容易被带偏的方向 |

### 1.3 风险清单

| 编号 | 风险 | 等级 | 具体影响 | 缓解建议 |
| --- | --- | --- | --- | --- |
| R1 | **"工具集合"陷阱** | ★★★ | 用户用完即走，无回访理由；与搜索引擎自带工具无差异，长期无人记住域名 | 引入"工具箱/工作台"叙事：收藏 + 最近使用 + 继续上次，让"你的常用工具"成为回访理由 |
| R2 | **工具与画像错配** | ★★★ | 高中生打开首页看到 Base64 / JSON / Hash，第一反应是"这不是给我用的" | 重排工具优先级（见 3.5），第一批以高中生刚需为骨架 |
| R3 | **动漫风格被误读为"幼稚"** | ★★ | 学生（尤其大学生）可能不信任"可爱网站"的工具准确性 | 采用"专业感 + 可爱感"双层结构：**工具操作区绝对专业克制（等宽字体、精确数值、清晰校验），角色只在操作区之外活动** |
| R4 | **留存机制过弱** | ★★ | LocalStorage 收藏/最近使用是弱钩子，用户清缓存即丢失，无损失感 | 第一版可接受；但首页必须做"继续上次使用"入口，把弱钩子用到极致 |
| R5 | **名称缺记忆点** | ★★ | "学习工具基地"不可搜索、无域名联想、与动漫体验无关，且极易与"学习基地"类教培词混淆 | 建议改名（见 1.5），名称应同时满足：短、可拼写、有画面感、.com 或 .cn 易得 |
| R6 | **"免费开源"的可持续性** | ★★ | 无收入 + 有维护成本 = 高烂尾概率，工具准确性一旦失修会损害信任 | 在文档中显式定义"商业化红线"：只卖外观/皮肤，不锁功能（见 6.3） |
| R7 | **SEO 优势可能落空** | ★★ | Next.js 的 SEO 能力需要靠"工具详情页 + 长尾文案 + 结构化数据"兑现；如果做成纯客户端 SPA，SEO 优势归零 | 每个工具页必须有：独立 URL、H1 含中文关键词、一段"这是什么/怎么用"的说明文本、FAQ 结构化数据 |
| R8 | **角色定位漂移** | ★★ | 只要首页出现一个角色，用户天然会去点它、期待它说话，从而误解为 AI 助手 | 设计手段消解预期：角色无对话气泡、无输入框、不主动说话、不可点击为"对话"（见 4.2 禁区） |
| R9 | **首页模块过多导致效率下降** | ★★ | 文档列出 6 个首页模块（Logo/角色/分类/推荐/我的工具箱/学习小提示），模块越多，用户抵达工具越慢 | 首页模块收缩为 3 个功能区（见 2.4） |
| R10 | **"学习小提示"内容无来源** | ★ | 无人撰写则变成长期空白或低质占位，伤害整体质感 | 第一版降级为"工具内的一句话技巧"，不做独立模块 |

### 1.4 优化建议：把定位收成一句话

**建议的定位重写**

> 一个属于学生的工具工作台。
> 所有琐碎的数字、文本、格式转换，在同一个地方、用同一种熟悉的方式解决。
> 它长得不像工具站，但它比工具站更快。

**核心调整三件事**

1. **收敛用户**：以高中生为主（需求更具体、竞争更弱、情感黏性更高），大学生通过"编程/文本类工具"自然覆盖，不单独做设计妥协。
2. **收敛场景**：把模糊的"学习过程中"替换为三个具体场景 —— **写作业时**（单位换算、进制转换、字数统计）、**上信息课时**（进制、编码、Markdown）、**自习整理时**（文本处理、文档格式化）。首页文案、工具排序、示例数据全部围绕这三个场景组织。
3. **收敛价值主张**：从"工具多"改为"快 + 不用注册 + 没有广告 + 界面舒服"。**前三点是学生真实痛点**，因为现有工具站普遍广告满天飞、强制登录、弹窗注册。

**补充建议：给首页加一句可传播的 slogan**

工具站的 slogan 不需要煽情，需要**说到用户痛点**。方向举例（供内部讨论，不直接采用）：

- 「打开就能用，用完不用管。」
- 「学生的工具，一个页面搞定。」
- 「没有广告，不用注册，直接算。」

### 1.5 名称建议方向

现有名称"学习工具基地"的问题：4 个常见词组合，无识别度、无衍生空间（域名、Logo、IP 角色、周边都难做）。

好的名称应该能同时支撑：域名、Logo 图形化、角色世界观、以及"工具感"。建议从三个方向候选：

| 方向 | 逻辑 | 特征 |
| --- | --- | --- |
| 空间/基地型 | 呼应"未来学习基地"的视觉方向 | 好记，但需避免与教培撞词 |
| 角色/伙伴型 | 用主角色命名，让 IP 直接成为品牌 | 最利于"动漫负责体验"，且天然形成回访情感 |
| 功能/快捷键型 | 名字本身暗示"快、顺手" | 最利于搜索与口碑传播 |

> 建议：**角色名 = 品牌名 = 域名关键词**，三者统一。这是二次元属性项目最省力的品牌路径。

## 2. 首页 UI 设计建议

### 2.1 首页的唯一目标

首页只有一个 KPI：**让用户以最少的交互到达工具页。**

所有设计取舍都服从这一条。任何"好看但需要多一次点击"的模块，都应该被砍掉或降级。

### 2.2 桌面端布局（推荐）

```
┌──────────────────────────────────────────────────────────────┐
│  [Logo 角色头像]  站名        全局搜索        我的工具箱  GitHub │  ← 顶栏 56-64px
├──────────────────────────────────────────────────────────────┤
│                                                              │
│   属于学生的工具工作台                       ╭──────────╮    │
│   打开就能用，不用注册                       │  主视觉  │    │  ← Hero 区
│                                             │   角色   │    │    高度约 40-45vh
│   ┌─────────────────────────────┐           │          │    │
│   │ 🔍  搜工具，如"进制""字数"    │           ╰──────────╯    │
│   └─────────────────────────────┘                           │
│         ↑ 首屏最核心元素，宽度 480-560px，居中偏左            │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│  [ 转换工具 ]  [ 文本处理 ]  [ 开发辅助 ]    ← 分类卡片 3 列 │  ← 功能区 1
├──────────────────────────────────────────────────────────────┤
│  常用工具                       查看全部 →                   │  ← 功能区 2
│  [进制转换] [单位换算] [字数统计] [JSON 格式化] [Markdown]    │
├──────────────────────────────────────────────────────────────┤
│  我的工具箱（含收藏 / 最近使用；无数据时显示角色空状态）       │  ← 功能区 3
│  继续上次：单位换算 →                                        │
├──────────────────────────────────────────────────────────────┤
│  关于 · 开源地址 · 反馈      角色小元素装饰                    │  ← 页脚
└──────────────────────────────────────────────────────────────┘
```

**布局要点**

| 要点 | 规格 | 理由 |
| --- | --- | --- |
| Hero 采用**非对称双栏**（文字左、角色右） | 文字区 60%，角色区 40% | 避免居中对称布局的"活动页感"，更像工具站 |
| 角色不得遮挡或压住搜索框 | 角色容器与搜索框水平不重叠 | 搜索是效率核心，视觉必须让路 |
| 搜索框在首屏垂直位置 60% 以上 | 保证 1366×768 分辨率下无需滚动即见 | 学生笔记本普遍是 768-900 高度 |
| 顶栏常驻「我的工具箱」 | 与搜索框并列，不做折叠菜单 | 回访用户的最短路径 |
| 不做轮播 Banner | — | 轮播是首页最大的效率杀手 |
| 不做弹窗、公告条、Cookie 提示 | — | 直接扣分项 |

### 2.3 移动端布局

| 项目 | 建议 |
| --- | --- |
| Hero | 角色缩小为顶部装饰（高度 ≤ 120px），或以"半身局部"形式作为背景，文案与搜索框置顶 |
| 搜索框 | 吸顶，宽度 100%，高度 ≥ 48px（触控目标） |
| 分类 | 2 列卡片，图标 + 名称 + 工具数量 |
| 常用工具 | 2 列网格 |
| 触控目标 | 所有可点元素 ≥ 44×44px |
| 字体 | 正文 ≥ 16px，避免移动端自动缩放 |

### 2.4 信息层级（三层，建议严格保持）

| 层级 | 内容 | 视觉权重 | 说明 |
| --- | --- | --- | --- |
| **L1 找工具** | 全局搜索 + 分类入口 | 最强（大字号、高对比、首屏） | 用户 80% 的进入意图在这里被满足 |
| **L2 用工具** | 常用工具 + 我的工具箱 + 继续上次 | 中等 | 承接"不知道要什么"和"老用户回访" |
| **L3 辅助** | 关于、开源、反馈 | 最弱（页脚） | 不占用首屏视觉资源 |

> **明确建议：把原文档的"学习小提示"从首页移除**，改为在工具页底部以一行小字呈现（例如进制转换页下方："小技巧：十六进制每位对应 4 位二进制，可以直接两两对照。"）。这样既保留了"有温度"的体验，又不占用首页的宝贵层级。内容来源问题也随之降级为"每个工具写一句"，工作量可控。

### 2.5 用户进入网站后的浏览流程

**路径 A · 目标明确（占预计 60%+，必须做到最短）**

```
进入首页 → 搜索框输入关键词 → 下拉即时显示匹配工具 → 回车/点击 → 工具页
         ↑ 理想：全程 2 次交互，且不发生页面跳转（下拉直接选）
```

关键设计：搜索必须是**即时匹配的下拉**，不是跳转到搜索页。用户在输入"进"时就应该看到"进制转换"，输入"单"就看到"单位换算"。这一个小设计，价值大于首页任何装饰。

**路径 B · 目标模糊（占预计 25%）**

```
进入首页 → 扫视分类卡片（3 个，可一眼看完）→ 进入分类页 → 选择工具
```

关键设计：分类必须**少而清晰**（见第 3 节），3 个分类一眼看完；分类页内每个工具卡片要有一句话说明"这个能干什么"，降低选择成本。

**路径 C · 回访用户（占预计 15%，但留存价值最高）**

```
进入首页 → 直接看到"我的工具箱"里的收藏 / 最近使用 → 一次点击直达
      或 → "继续上次：单位换算" → 一次点击直达
```

关键设计：**回访用户应该 1 次点击离开首页**。建议在首屏 Hero 搜索框下方直接插入一行"继续上次使用"的快捷入口，而不是放在页面下半部分 —— 这是把弱留存机制做到极致的关键。

**推荐工具区的排序规则**

不要人工维护"推荐"，用行为数据排序，规则简单可执行：

```
首页"常用工具"排序权重 =
    收藏数 × 3
  + 近 7 天使用次数 × 2
  + 是否属于"作业高频场景" × 1
```

第一版没有后端统计，可以先按**人工预设的静态顺序**（把单位换算、进制转换、字数统计放在最前），但**代码结构上要预留排序函数的位置**，后续接入统计时只改一个函数。

## 3. 工具分类设计建议

### 3.1 现有分类诊断

| 现有分类 | 包含工具 | 诊断 |
| --- | --- | --- |
| 数学工具 | 二进制转换、单位换算 | ⚠️ 二进制转换本质是"进制转换"，属于计算机基础，放进"数学"会让信息课学生找不到 |
| 编程工具 | Base64、JSON 格式化、Hash | ⚠️ 名称对高中生不友好；且这些工具大学生/开发者用得更多，与主用户画像错位 |
| 学习工具 | Markdown 预览、字数统计 | ❌ **"学习工具"是无效分类名**。数学工具和编程工具难道不是学习工具？用户无法建立稳定心智 |
| 文件工具 | （空） | ❌ 空分类上线会立刻暴露"这个站还没做完"，损害信任 |

### 3.2 核心问题：分类维度不统一

现有 4 个分类混用了三种不同的切分维度：

| 分类 | 使用的维度 |
| --- | --- |
| 数学工具 | **学科**维度 |
| 编程工具 | **学科/领域**维度 |
| 学习工具 | **用途**维度 |
| 文件工具 | **数据载体**维度 |

同一个层级里混用三种维度，是分类设计中最典型的结构性错误。用户的大脑无法建立一致的预期："数学工具和编程工具并列，那学习工具是什么？数学不是学习吗？"

### 3.3 推荐方案

**方案 A · 按任务类型分类（推荐）**

| 分类 | 工具 | 一句话定位 |
| --- | --- | --- |
| **转换工具** | 进制转换、单位换算、Base64、URL 编码 | 把一种格式变成另一种 |
| **文本处理** | 字数统计、Markdown 预览、大小写转换、文本去重 | 和文字打交道 |
| **开发辅助** | JSON 格式化、Hash、时间戳、正则测试 | 给写代码的人 |

推荐理由：

- **维度统一**：全部按"用户想做什么"切分，心智模型一致
- **与搜索天然配合**：用户搜"转换"能命中整类，搜"字数"直接命中工具
- **不排斥任何用户**：高中生用"转换工具"，大学生用"开发辅助"，各取所需，无需为双画像做妥协
- **可扩展性最好**：新增"图片压缩"→ 归入新增的"文件处理"类，不破坏既有结构

**方案 B · 按学科分类（次选）**

| 分类 | 工具 |
| --- | --- |
| 数学计算 | 进制转换、单位换算、方程求解 |
| 编程开发 | Base64、JSON、Hash、时间戳 |
| 文档文本 | 字数统计、Markdown、文本处理 |
| 图片文件 | （工具数 ≥ 3 个后再上线） |

适用前提：**如果网站未来要往"学科工具包"方向走**（如"高中物理工具包""离散数学工具包"），方案 B 更顺。但在第一版工具仅 6-8 个时，方案 B 会导致"数学计算"类只有 2 个工具，分类页过于空旷。

**结论：第一版用方案 A，未来如需学科化，用"标签"而非"分类"来补。**

### 3.4 分类 + 标签 双轨制（重要建议）

不要把每个工具硬塞进唯一分类。推荐：

| 机制 | 维度 | 作用 | 数量限制 |
| --- | --- | --- | --- |
| **分类（category）** | 任务类型，1 个/工具 | 导航、面包屑、首页入口 | 全站 3-6 个 |
| **标签（tag）** | 学科、学段、场景，多个/工具 | 检索、筛选、跨类推荐 | 每工具 2-4 个 |

示例：

```yaml
进制转换:
  category: 转换工具
  tags: [数学, 计算机, 信息课, 高中]

单位换算:
  category: 转换工具
  tags: [物理, 化学, 数学, 高中, 大学]

字数统计:
  category: 文本处理
  tags: [语文, 作文, 写作, 高中]
```

双轨制的好处：

- 用户从"学科"路径（搜"物理"）和"任务"路径（搜"换算"）都能命中同一个工具
- 未来做"高中物理工具包"这类专题页时，**只需按 tag 聚合，无需重构分类**
- 新增工具只需填一个 config，符合文档 §10.1 的模块化原则

### 3.5 分类调整的落地规则

| 规则 | 内容 |
| --- | --- |
| 分类数量 | 全站控制在 3-6 个；**少于 3 个工具不开新分类** |
| 空分类 | 绝不显示空分类。工具数不足时该分类直接不渲染（文件工具第一版隐藏） |
| 工具数 < 10 时 | 首页可退化为"全部工具网格 + 标签筛选"，比空荡荡的分类更实用 |
| 分类命名 | 用**用户会说的话**，不用行业术语。"转换工具"优于"编码转换"，"文本处理"优于"字符串处理" |
| 排序 | 工具按"使用频次 × 学生场景相关度"排序，不按名称字母序 |

**第一批工具的建议优先级重排**（括号内为理由）：

| 优先级 | 工具 | 理由 |
| --- | --- | --- |
| P0 | 单位换算 | 高中物理/化学作业高频，几乎每天用 |
| P0 | 字数统计 | 语文作文、英语作文、论文都有字数要求，绝对刚需 |
| P0 | 进制转换 | 信息课/计算机基础必学，且学生常算错 |
| P1 | Markdown 预览 | 大学生写笔记/作业常用，高中生也逐渐接触 |
| P1 | JSON 格式化 | 大学生/选修信息课，专业感来源 |
| P2 | Base64 | 使用频次最低，但实现成本低，作为"完整性"保留 |

## 4. 动漫视觉设计建议

### 4.1 核心原则

> **角色"在场"，但从不"挡路"。**

判断标准可以简化为一句话：**用户在使用工具时，不应该意识到角色的存在。**

角色承担三个功能，且只有这三个：建立品牌识别（Logo）、降低陌生感（首屏与空状态）、提供情绪反馈（成功/错误/空）。任何超出这三件事的角色用法，都是在消耗效率。

### 4.2 角色出现的 5 个位置与 4 个禁区

**✅ 允许出现的 5 个位置（按价值从高到低排序）**

| 优先级 | 位置 | 呈现方式 | 为什么这里有价值 |
| --- | --- | --- | --- |
| ★★★ | **空状态** | 半身像 + 一句人话（如"这里还空着，去挑几个顺手的工具吧"） | 空状态是工具站体验最冷的死角，也是角色最能创造记忆点的地方 |
| ★★★ | **Logo / 顶栏** | 角色头部圆形头像（24-32px） | 品牌识别的最小成本实现 |
| ★★ | **首页 Hero** | 完整形象，占右侧 35-40% 区域 | 第一印象与风格定调 |
| ★★ | **反馈态** | 转换成功/输入错误的迷你表情变化（仅头部，≤64px） | 把枯燥的操作变成有反馈感的行为 |
| ★ | **工具页留白区** | 小尺寸（≤120px）半身或头部，位于操作区外侧的边距内 | 纯装饰，营造"这是同一个世界"的连贯感 |

**❌ 禁止出现的 4 个位置 / 4 种用法**

| 禁区 | 原因 |
| --- | --- |
| 输入框、按钮、输出结果的相邻区域 | 直接干扰注意力，违背"简洁优先" |
| 对话气泡、语音气泡、"问我吧"类文案 | **会立刻让用户把它当成 AI 助手，直接违背文档 §4.2 的定位** |
| 自动循环播放的全身动画 | 持续运动元素会不断抢夺视线，是效率杀手 |
| 工具页正中央或输入输出之间的插入位 | 打断操作动线，且大幅增加纵向滚动 |
| （用法）可点击触发多帧交互动画 | 开发成本高、"复杂动画"已在第一阶段排除范围 |
| （用法）角色"说话"式文案（第一人称表述） | 强化 AI 助手错觉，建议用**旁白式第三人称或无人称短句** |
| （用法）在错误提示中卖萌 | 用户犯错时最需要清晰的修复指引，不是可爱。**错误提示必须专业、明确、可操作** |
| （用法）在小屏幕上与内容争夺空间 | 移动端角色必须降级为装饰层或直接隐藏 |

> 关于"角色是否该说话"的补充：建议采用 **"旁白式"文字**，而不是"角色口吻"。例如空状态写："还没有收藏工具。"（旁白）而不是"我帮你找找工具吧～"（角色第一人称）。后者一出现，AI 助手的预期就建立起来了，且很难再纠正。

### 4.3 避免影响工具效率的量化约束

以下数值建议写进设计规范，便于后续开发直接执行与验收：

| 约束项 | 数值 | 说明 |
| --- | --- | --- |
| 角色在工具页占屏幕面积 | ≤ 15% | 首页 Hero 可放宽至 25% |
| 操作区（输入/按钮/输出）周围的装饰元素 | **0 个** | 硬性红线 |
| 装饰元素不透明度（背景纹样等） | ≤ 12% | 保证不与前景争夺对比度 |
| 正文文字对比度 | ≥ 4.5:1（WCAG AA） | 输入框内的文字尤其重要 |
| 输入框/按钮区域背景 | 纯色或极浅渐变，**不透明** | 纹样不得透过表单控件 |
| 单个动画时长 | ≤ 300ms | 反馈要快，慢动画在工具站等于卡顿 |
| 动效分级 | 仅用不超过 3 种缓动曲线 | 一致性 > 花样 |
| `prefers-reduced-motion` | 必须支持 | 提供动效关闭降级 |
| 移动端角色 | 高度 ≤ 120px 或隐藏 | 小屏幕空间极其宝贵 |
| 首屏可见内容 | 搜索框 + 分类入口必须在 768px 高度内可见 | 学生笔记本常见分辨率 |

补充一条容易被忽视的：**工具区内不要使用角色配色作为功能性颜色。** 例如不要让"复制成功"用角色头发的粉色、让"错误"用角色的蓝色。功能性颜色（成功/警告/错误）必须固定在语义色板上，与角色配色解耦。

### 4.4 页面装饰体系建议

**色彩系统（建议三档结构）**

| 层级 | 用途 | 建议方向 |
| --- | --- | --- |
| 主色（1 个） | 品牌、主按钮、链接、选中态 | 偏冷色的科技蓝紫 / 青蓝。冷色与"未来学习基地"的方向一致，且长时间使用不刺眼 |
| 辅色（2-3 个） | 角色、分类色标、装饰点缀 | 从角色设定中取色（暖色系点缀：粉 / 橙 / 薄荷）。**辅色只用于装饰和非关键信息** |
| 中性色（灰阶 6-8 档） | 背景、卡片、边框、正文 | 最深的一档用于正文，最浅的一档用于页面底色。**中性色必须占页面面积的 80% 以上** |

> 关键判断：**一个二次元风格的工具站，画面 80% 应该是克制的灰阶，20% 才是色彩与角色。** 反过来做就会变成"活动页"，专业感全失。

**装饰元素建议**

| 元素 | 用法 |
| --- | --- |
| 细网格 / 星点 | 低透明度（≤8%）作为页面背景底纹，呼应"数据空间" |
| 圆角卡片 + 柔和阴影 | 统一圆角（建议 12-16px），阴影不超过两层，避免"新拟态"式厚重 |
| 发光描边 | 仅用于重点按钮或选中态，不做大面积发光 |
| 几何小图标 | 与角色世界观一致（数据碎片、能量线、坐标点），用于分类图标 |
| 分割线 | 用极浅色 1px 线，不用装饰性花边 |

**字体建议（工具站的专业感主要来自这里）**

| 用途 | 建议 |
| --- | --- |
| 中文正文 / 界面 | 系统字体优先（苹方 / 微软雅黑 / 思源黑体），不做花哨字体。**中文界面禁用圆体/手写体**，会显著降低可读性 |
| 数字与代码 | **等宽字体必须（如 JetBrains Mono / Fira Code）**。进制转换、Hash 结果、JSON 输出的对齐要求等宽，这是工具站专业度的分水岭 |
| 字号阶梯 | 建议 12 / 14 / 16 / 20 / 28 / 40 六档，控制在 6 档以内 |

### 4.5 关于暗色模式的澄清（重要）

文档 §7 把"多主题系统"列入第一阶段不做的范围，但同时 §4.1 的视觉方向是"未来科技 / 未来学习基地"，这类方向天然适合暗色底。这里存在**概念歧义，需要澄清**：

| 概念 | 建议 | 理由 |
| --- | --- | --- |
| **暗色模式（单套暗色主题）** | ✅ **纳入第一阶段** | 学习工具高频使用时段是晚上；暗色与"未来科技"视觉方向天然契合；实现成本仅为定义一组 CSS 变量 |
| **多主题系统（用户可切换多套皮肤 + 主题管理界面）** | ❌ 不纳入第一阶段 | 需要设计多套配色、维护成本成倍增加，属于"外观系统"，应放到商业化阶段 |

建议做法：第一阶段定义**两套 token（亮 / 暗），跟随系统偏好自动切换**，不在界面上提供切换器。这样既拿到暗色的体验收益，又不触碰"多主题系统"的范围红线。

### 5.3 不建议做（第一版明确排除）

| 不建议项 | 原因 |
| --- | --- |
| AI 聊天助手 / 任何对话界面 | 与"角色不是 AI 助手"的核心定位直接冲突；且会引入后端、成本、内容安全等一系列复杂度 |
| 账号系统、云同步 | 无后端架构下强上会破坏"打开就能用"的核心体验 |
| 社区、评论、排行榜、用户投稿 | 需要运营与审核，与"工具站"定位无关，且冷启动必然失败 |
| 游戏化成长系统（积分/等级/成就/签到） | 会稀释"效率"核心，且一旦上线就要长期维护，容易变成负担；用户来这里是解决问题，不是玩游戏 |
| 多主题皮肤系统 | 见 4.5，属于商业化阶段的能力 |
| 首页轮播图 / 大尺寸自动动画 | 效率杀手 |
| 广告位 | 与"免费、干净、学生向"的定位根本冲突，第一版绝不能有 |
| 语音、摄像头、实时协作 | 与第一版工具范围无关 |
| 一次性上线 20+ 工具 | 工具质量会崩。**第一版宁可 6 个工具都做到零缺陷，也不要 20 个半成品** |
| 用户行为分析 SDK（第三方） | 学生向产品引入第三方追踪会引发信任问题；如需数据，用自建轻量埋点 |

### 5.4 第一版质量验收标准

建议把"6 个工具都做到零缺陷"作为第一版的正式验收线，因为工具出错一次，用户就再也不会回来。

| 维度 | 验收标准 |
| --- | --- |
| 输入容错 | 空输入、超长输入、非法字符、纯空格、粘贴带换行 —— 全部有明确提示，不白屏、不报错崩溃 |
| 错误提示 | 说明"哪里错了"+"怎么改"，不卖萌、不显示原始异常堆栈 |
| 结果准确性 | 每个工具准备至少 10 组边界用例（如 0、负数、超大数、Unicode 字符、空字符串）逐个验证 |
| 复制结果 | 一键复制，有明确的成功反馈 |
| 示例数据 | 每个工具提供"试试示例"，让学生 3 秒理解怎么用（**这对高中生尤其重要**） |
| 键盘可用 | Tab 顺序合理、Enter 可提交、Esc 可清空 |
| 移动端 | 真机验证输入法弹出时不遮挡输入框 |
| 性能 | 首屏 LCP < 2s（4G 网络），不引入不必要的第三方库 |
| 代码结构 | 新增一个工具 = 新增一个 config + 一个组件，不改动首页代码（对齐文档 §10.1） |

## 6. 后续扩展方向

### 6.1 扩展原则

沿用文档的核心方向不动摇，扩展只允许沿三个轴向进行：

| 轴 | 含义 | 不允许越界的方向 |
| --- | --- | --- |
| **更全** | 覆盖更多学生真实需要的工具，工具质量不下降 | 不做题库、课程、笔记、待办等"学习管理"功能 |
| **更快** | 更短的路径、更少的点击、更好的键盘与批量体验 | 不引入需要登录/注册才能使用的能力 |
| **更暖** | 让角色与体验更自然、更有归属感 | 不让角色变成会说话的助手，不做游戏化养成 |

**三个不改变**：不说自己是 AI 助手、不做社区社交、不做把功能锁在付费墙后的商业化。

### 6.2 扩展路线（按可执行性排序）

**阶梯 1 · v1.1 —— 补齐高中生刚需工具（最高优先）**

| 工具 | 学生痛点 | 实现难度 |
| --- | --- | --- |
| 化学式/摩尔质量计算 | 高中化学作业高频 | 中 |
| 一元/二元方程求解 | 数学作业验算 | 低 |
| 函数图像绘制 | 数学理解函数性质 | 中 |
| 时间/日期计算（天数差、倒计时） | 考试倒计时、作业截止 | 低 |
| 二维码生成 | 社团、班级通知 | 低 |
| 图片压缩 / 格式转换 | 提交作业有大小限制 | 中（纯前端 canvas 可实现） |
| PDF 合并 / 拆分 | 交作业要合并多个 PDF | 中（需引入库） |

建议以**"数据驱动淘汰"**替代"拍脑袋加功能"：上线 3 个月后，把使用次数为 0 的工具下线，把使用次数最高的 3 个工具做深度优化。

**阶梯 2 · v1.2 —— 效率深化（最能强化定位）**

- 命令面板（Cmd/Ctrl + K）：一键呼出，键盘直达任意工具 —— 这是"快"的定位最有力的表达
- 工具间互跳：如算完进制转换可直接跳到 Hash
- 批量处理：多行/多文件一次处理
- 结果导出与分享链接
- 历史记录（本地，可查看最近 20 次输入输出）

**阶梯 3 · v2.0 —— PWA 与工程化**

- PWA：可安装、离线可用（工具全是纯前端逻辑，天然适合离线）
- 工具全面配置化：新增工具只增一个 config，路由与首页自动生成
- 自建轻量埋点：统计工具使用频次，驱动排序与淘汰

**阶梯 4 · v2.x —— 可选账号与个性化（商业化落脚点）**

- 账号仅用于**同步收藏**，且**完全可选**：不登录也能用全部功能
- 个性化作为付费点：角色换装、主题皮肤、角色装扮作为周边感内容
- 这符合"只卖外观，不锁功能"的红线，也天然契合二次元用户的付费习惯

**阶梯 5 · 长期（谨慎）**

- 学科工具包（"高中物理工具包""离散数学工具包"）：用 tag 聚合即可实现，无需重构
- 前提：内容质量需要真实教学视角审核，否则容易出错并损害信任

### 6.3 商业化边界（建议现在就写进文档）

| 允许 | 不允许 |
| --- | --- |
| 卖外观（角色皮肤、主题、装扮） | 把工具功能锁在会员后 |
| 卖容量/性能（如大批量处理、更大文件上限） | 强制登录才能使用基础工具 |
| 接受自愿赞助 / 开源打赏 | 插入广告或第三方追踪 |
| 卖"周边"性质的内容 | 卖用户数据 |

把这条边界**提前写进设计文档**，可以避免未来在压力下做出伤害核心体验的决策。

### 6.4 每个扩展方向的前提

| 方向 | 前提条件 | 主要风险 |
| --- | --- | --- |
| 增加工具 | 现有工具零缺陷已达成 | 数量增长导致质量下滑 |
| 命令面板 | 工具数 ≥ 12 | 用户教育成本，需有提示 |
| PWA | 移动端使用占比 ≥ 40%（有数据支撑再做） | 过早投入，收益不明显 |
| 账号系统 | 出现明确的"跨设备同步"用户诉求 | 破坏"打开即用"的核心体验 |
| 学科工具包 | 相关内容质量可被专业审核 | 内容出错会直接摧毁工具站的信任基础 |
| 角色周边/IP 化 | 主角色获得正向用户反馈 | 过早投入，方向可能推翻重来 |

## 8. 附：上线后如何验证定位是否成立

第一版上线后，建议用以下指标判断"工具负责效率，动漫负责体验"是否真的成立。这些指标不需要复杂分析，自建轻量埋点即可采集。

| 指标 | 衡量什么 | 健康参考 | 不健康时的动作 |
| --- | --- | --- | --- |
| **首页 → 工具页转化率** | 首页是否有效 | ≥ 60% | 检查搜索是否好用、分类是否清晰 |
| **搜索使用率** | 搜索框是否是主路径 | ≥ 30% 的首页用户使用过 | 提高搜索框视觉权重 |
| **平均单次会话工具数** | 是否有"逛"的行为 | ≥ 1.5 | 增加"工具间互跳"与相关推荐 |
| **7 日回访率** | 留存是否成立 | ≥ 15%（无账号的纯工具站已属良好） | 强化"继续上次"与收藏入口 |
| **收藏转化率** | "我的工具箱"是否被使用 | ≥ 10% 的用户产生过收藏 | 降低收藏操作成本，优化空状态引导 |
| **移动端占比** | 是否需要提前做 PWA | ≥ 40% 可考虑提前 | 未达则维持现状 |
| **工具使用分布** | 哪些工具真被需要 | 头部 3 个工具占 ≥ 60% 使用量属正常 | 依据分布淘汰长尾工具，加深头部工具 |
| **错误率 / 无结果率** | 工具质量 | 无结果率 ≤ 5% | 补搜索同义词、修正工具逻辑 |

**最重要的一个判断**：如果"7 日回访率"上不去，但"首页 → 工具页转化率"很高，说明**网站是好用的，但没有让人记住的理由**。这正是 R1 风险的显性化。此时的解法不是加工具，而是强化"这是你的工作台"的归属叙事（收藏 + 最近 + 继续上次 + 角色）。

## 9. 结论

**这个方向值得做。** 面向学生的工具站 + 二次元体验，是目前真实存在且少有人认真做的位置；而文档在"角色不是 AI 助手""工具优先""不引入复杂度"这几条边界上写得非常清醒——这是最难得的，因为绝大多数项目都是在这里跑偏的。

**需要在设计阶段收尾前完成三件事：**

1. **收敛定位**：高中生为主，三个具体场景（作业 / 信息课 / 自习整理），工具优先级据此重排
2. **重做分类**：按任务类型分为 3 类（转换 / 文本 / 开发），并引入标签作为第二维度；隐藏空分类
3. **首页瘦身**：只保留"搜索 + 分类 + 常用工具 + 我的工具箱"四个功能区，把搜索框做成第一优先级元素

**同时守住三条红线：**

- 角色在场，但从不挡路（4.2 与 4.3 的量化约束）
- 不把它做成会说话的助手（定位不漂移）
- 第一版宁可 6 个工具零缺陷，也不要 20 个半成品

只要这三件事做到，第一版就具备"简单、美观、好用"的全部条件；后续扩展也有一条清晰、可控、不偏离核心方向的阶梯可走。
