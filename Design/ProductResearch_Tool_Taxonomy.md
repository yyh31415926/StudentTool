## 0. 结论先行

| # | 问题 | 结论 | 是否需改现有定案 |
| --- | --- | --- | --- |
| 1 | 当前 3 分类是否合理 | **3 个分类本身没错，但它们是为 6 个工具设计的尺码。** 用一级分类的容器去装"换算""文本""代码"三个高度不对称的抽屉，到 20 个工具就会明显吃力 | 不改（v1 保持） |
| 2 | 50–100 工具的一级分类 | **6 个**：文本与写作 / 计算与换算 / 代码与数据 / 图表与图片 / 时间与日程 / 校园与生活 | v1.1 起分批落地 |
| 3 | 是否需要二级分类 | **需要，但形态不是"第二层分类"，而是"分类页内的分区标题"。** 触发阈值：一级分类下工具数 ≥ 12 | 不新增字段 |
| 4 | 分类名偏技术还是偏用户 | **必须偏用户**。但采用"**界面偏用户、代码与 URL 偏技术**"的分离策略：界面显示中文用户词，`slug` 保持英文短词 | 补充规则 |
| 5 | 是否修改现有 `ToolDefinition` | **`category` 的取值与语义一个都不改；`ToolDefinition` 类型需要补齐已定案的字段。** 分类相关的最小改动只有"分类展示名"一处 | **有 1 处必须改（缺陷）** |
| 6 | 首页分类展示建议 | **分类卡片只放"图标 + 名称 + 工具数"，不放一句话说明**；首页分类数上限 6；超过 6 个用分组而非网格 | 补充规则 |

**一句话总结**：分类体系的病不在"3 个"，而在"**没有一个能同时容纳 换算 / 文本 / 代码 / 图像 / 时间 的上位结构，也没有一条判断新工具归哪里的裁决规则**"。当前最紧要的不是加分类，而是**先补一条分类判定规则**，否则每加一个工具都要重新吵一次。

## 1. 现状核实（先行声明）

在给建议前，必须如实区分"文档里写的"与"代码里已经有的"。两者当前**并不一致**。

### 1.1 已实现（代码事实）

```
src/types/tools.ts
  ToolCategory = "convert" | "text" | "dev"
  ToolDefinition = { id, name, category, description,
                     template, exampleInput, run }      ← 仅 7 个字段
```

| 工具 | `category` | 文件 |
| --- | --- | --- |
| 字数统计 `char-count` | `text` | `src/lib/tools/definitions/char-count.ts` |
| 单位换算 `unit-convert` | `convert` | `src/lib/tools/definitions/unit-convert.ts` |
| 进制转换 `base-convert` | `convert` | `src/lib/tools/definitions/base-convert.ts` |

**v1 已定案的另外 3 个工具（Markdown / JSON / Base64）尚未创建**，分类页 `/categories/[category]` 也尚未创建。项目实际处于 Codex 路线图的 **Phase 4 结束后**。

### 1.2 文档要求 vs 代码现状的差距

| 项目 | 文档定案 | 代码现状 | 性质 |
| --- | --- | --- | --- |
| 工具数 | 6 | 3 | 进度落后，非缺陷 |
| `ToolDefinition` 字段 | 16（v0.2 §3.5）+ `pinyin` = 17 | **7** | 进度落后，**Phase 2 未按契约完成** |
| `tags` 字段 | ✅ 必填，服务搜索与学科聚合 | **不存在** | 进度落后，且**影响本文结论 3 的落地方式** |
| `order` 字段 | ✅ 必填，分类页排序依据 | **不存在** | 同上 |
| 分类展示名 | 分类页需显示"转换工具" | **不存在**，`registry.ts` 只有 `getToolsByCategory` | 见下 |

### 1.3 已发现的一处真实缺陷（必须修）

`src/components/tools/ToolCard.tsx` 第 23–25 行直接把 `tool.category` 渲染成界面文字：

```
<span className="…">{tool.category}</span>
```

结果是：**用户在工具卡片上看到的是英文 slug —— `text` / `convert` / `dev`，而不是"文本处理""转换工具""开发辅助"。**

同一问题存在于 `src/components/tools/FavoriteToolsSection.tsx` 第 50–51 行。

这直接违反三条既有定案：

| 违反对象 | 原文 |
| --- | --- |
| v0.2 §3.1「分类命名规则」 | 必须用**用户会说的话**，不用行业术语 |
| v0.2 §4.1「明确不是」 | ❌ 专业开发者工具站（**不英文优先**） |
| v0.2 §4.5「色彩与字体」 | 中文正文 / 界面用系统中文字体——即界面主体不应是英文 |

**这不是分类体系的问题，是分类展示层缺失的问题。** 它是本次研究中唯一"现在就该修"的一条。

## 2. 问题 1：当前分类是否合理

### 2.1 做对的部分（应当保留，不要推翻）

`AGENT_RULES.md` §1.5 把"分类体系（convert / text / dev）"列为**核心技术路线**，改动必须走变更流程。这个保护是合理的，因为当前分类在三件事上是对的：

| ✅ 做对了 | 说明 |
| --- | --- |
| **单一维度** | 3 个分类全部来自"任务类型"这一个维度。v0.1 的四分类败在混用"学科 / 用途 / 载体"三种维度，v0.2 已经纠正，这个成果不能丢 |
| **无空分类** | "少于 3 个工具不开新分类" + "空分类不渲染"两条规则，避免了 v0.1"文件工具"空分类的信任损伤 |
| **有裁决依据** | 每个分类都配了一句用户视角定位语（"把一种格式变成另一种"），不是拍脑袋起的名字 |

**结论：v1 不应改分类结构。** 3 个分类装 6 个工具，每个分类 2 个工具，此刻改动只有成本没有收益。

### 2.2 结构性隐患（这才是真问题）

当前分类放在 50–100 工具的目标下看，有三个会在 20 个工具左右集中爆发的问题。

#### 隐患 A：「转换工具」是超级垃圾桶，最终会吞掉半个网站

"把一种格式变成另一种"是一句**没有边界的话**。按这个定义：

| 未来工具 | 是否满足"把一种格式变成另一种" | 结果 |
| --- | --- | --- |
| 进制转换 | ✅ | 在 `convert` |
| 单位换算 | ✅ | 在 `convert` |
| 时间戳转换 | ✅ | 会进 `convert` |
| 日期计算 | ✅ | 会进 `convert` |
| Base64 | ✅（但被移到了 `dev`） | 靠人工干预才没进 |
| URL 编码 | ✅ | 会进 `convert` |
| 图片格式转换 | ✅ | 会进 `convert` |
| PDF 转 Word | ✅ | 会进 `convert` |
| 二维码生成 | ✅（文本 → 图形） | 会进 `convert` |
| 大小写转换 | ✅ | 会进 `convert` |

**10 个里有 8 个会掉进 `convert`。** 而 Base64 之所以没掉进去，v0.2 §0.4 说得很直白——理由是"三个分类各 2 个工具，**结构均衡**"。

> **一个需要靠"凑数均衡"来人工干预的分类，说明它的定义撑不住规模。** 分类的判定标准应该是"这个工具本质是什么"，不是"怎么分才好看"。

#### 隐患 B：3 个分类的抽象层级不一致

| 分类 | 抽象层级 | 用户认知路径 | 问题 |
| --- | --- | --- | --- |
| `convert` 转换工具 | **动作**维度（做什么） | "我要把一个东西变成另一个" | 与 text 不完全互斥 |
| `text` 文本处理 | **对象**维度（处理什么） | "我要处理文字" | 与 convert 重叠：文本 → 文本的转换算哪个？ |
| `dev` 开发辅助 | **人群**维度（谁用） | "我是写代码的" | 与其他两个不同层：开发者也要做换算和文本处理 |

v0.2 §3.1 批评 v0.1"混用三种不同切分维度"，这个批评是对的。但**当前 3 个分类其实也混了 3 种维度：动作 / 对象 / 人群**——只是混得不那么刺眼，因为只有 3 个、且刚好每个装了 2 个工具。

**为什么现在不痛**：3 个分类时，用户不需要理解维度，靠"3 个里挑 1 个"的穷举就能完成。
**为什么将来会痛**：20 个工具、5 个分类时，用户遇到"给文章排版"这种任务会在 `text` 和 `convert` 之间犹豫；作者遇到"给文档加时间戳"会在 3 个分类之间犹豫。**犹豫一次，分类导航的价值就归零一次。**

#### 隐患 C：`dev` 是唯一带人群标签的分类，且与产品定位有张力

产品定位是"**高中生为主，大学生为辅**……产品会退化成又一个开发者工具站，丧失差异化"（v0.2 §1.2）。

而 `dev` 这个分类名与定位语在打架：

- 高中生看到 `开发辅助`——**"这不是给我用的"**。信息课学生并不认为自己在"开发"。
- 但信息课是 v0.2 §1.3 明确的三大场景之一，且 `dev` 分类下规划的 JSON / Base64 正是信息课的产物。
- 结果是：**最该被信息课学生发现的两个工具，被装进了一个他们会绕开的名字里。**

同理，`dev` 的命名也是"行业术语"，违反 v0.2 §3.1 自身的命名规则（"写代码、处理数据结构时用"是解释，不是名字）。

### 2.3 问题 1 的答案

> **当前分类在 v1 完全合理，不需要改。但它的定义精度只够撑到约 15–20 个工具。**
>
> 具体地：
> - 「转换工具」的定义（"格式变格式"）**必须在扩到 20 个工具之前收窄**，否则它会把所有新工具吸走，让分类导航失去意义。
> - 「开发辅助」这个**名字**对目标用户有排斥性，是三大场景中"信息课"落地的主要阻碍。
> - 三条主线全在 15–20 工具规模上：分类结构的重构应从 **v1.1（12–15 工具）** 启动，而不是等到 50 个工具时再动。

## 3. 问题 2：50–100 个工具推荐的一级分类

### 3.1 推荐方案（6 个一级分类）

| # | 分类名（界面文字） | slug | 一句话定位（用户视角） | 用户心智问题 | 当前/规划工具数 |
| --- | --- | --- | --- | --- | --- |
| 1 | **文本与写作** | `text` | 和文字打交道：统计、排版、改写 | "我在写字" | 6–10 |
| 2 | **计算与换算** | `calc` | 算数、换算、求解 | "我在算东西" | 10–15 |
| 3 | **代码与数据** | `data` | 处理代码、结构化数据、编码格式 | "我在弄代码或数据" | 12–18 |
| 4 | **图表与图片** | `media` | 图片、二维码、图表、PDF | "我在弄图或文件" | 10–15 |
| 5 | **时间与日程** | `time` | 日期、时间、倒计时、期限 | "我在管时间" | 5–8 |
| 6 | **校园与生活** | `campus` | 学习与校园生活里的杂事 | "这是学校里的事" | 6–12 |

**合计容量 50–80 个工具**，且每个分类都有明确的"这是什么"的一句话——不需要用户理解抽象维度。

### 3.2 为什么是这 6 个（三条设计依据）

#### 依据 1：全部落在"**对象 + 动作**"的同一维度上

新版 6 个分类，每个都是"**我对什么东西做什么事**"：

```
文本与写作  →  对象：文字        动作：写 / 统计 / 排版
计算与换算  →  对象：数值        动作：算 / 换 / 解
代码与数据  →  对象：代码与数据   动作：格式化 / 编码 / 校验
图表与图片  →  对象：图像与文件   动作：生成 / 转换 / 压缩
时间与日程  →  对象：时间        动作：算 / 倒计 / 提醒
校园与生活  →  对象：校园事务     动作：各类杂事
```

**这是对"隐患 B"的直接修正**：不再混用动作 / 对象 / 人群三种维度，而是统一为"对象主导"。

#### 依据 2：每一个都对应真实的学生场景，而不是工具的技术属性

对应 v0.2 §1.3 的三大场景 + §9.2 已列的扩展候选：

| 新分类 | 承接的既有场景 / 已定候选 |
| --- | --- |
| 文本与写作 | 场景①"写作业时"（作文）、场景③"自习整理时"（笔记）；已含 `char-count`、`markdown-preview` |
| 计算与换算 | 场景①（单位换算、验算）；已含 `unit-convert`、`base-convert`；§9.2 的方程求解、函数图像、化学式/摩尔质量 |
| 代码与数据 | 场景②"上信息课时"；已含 `json-format`、`base64`、`base-convert` 的部分场景；§3.2 的 Hash、URL 编码、正则测试 |
| 图表与图片 | §9.2 的二维码生成、§3.2 的图片压缩、PDF 合并拆分（v1.2 候选） |
| 时间与日程 | §9.2 的日期计算（天数差、倒计时） |
| 校园与生活 | 社团、班级通知、成绩换算、课表相关等学生杂事 |

**注意：6 个分类没有一个是为"技术好奇"设的，全部是从已定案的场景和候选中长出来的。** 这符合 v0.2 §1.3 的硬规则："新增工具时必须能归入其中之一，否则需要先讨论是否偏离定位"。

#### 依据 3：修正"隐患 A"和"隐患 C"

| 隐患 | 修正方式 |
| --- | --- |
| **A.「转换」是垃圾桶** | **取消"转换"作为分类概念。** 6 个分类中没有一个是"转换"。转换动作被打散到对象分类里：单位换算 → `calc`；大小写转换 → `text`；图片格式转换 → `media`。**"我在转换什么"比"我在做转换"是更有用的信息** |
| **C.「开发辅助」排斥学生** | 改为「**代码与数据**」。它描述的是**内容**（代码、数据），不是**身份**（开发者）。信息课学生在处理 JSON 时，不会觉得"这不是给我用的" |

### 3.3 更关键的是"分流规则"，不是"分类名单"

6 个分类的名字会随规模继续演化，但**判定规则必须现在定下来并写进 v0.2**，否则 100 个工具会有 100 次归类争论。

**建议写入 v0.2 的分类判定流程（3 步裁决）**：

```
新增一个工具，问三个问题：

问题 1：用户处理它的「主要对象」是什么？
        文字 → 文本与写作      数值 → 计算与换算
        代码/结构化数据 → 代码与数据
        图片/文件 → 图表与图片  时间 → 时间与日程
        校园事务 → 校园与生活

问题 2：它是否需要写代码的背景知识才能理解用途？
        是 → 代码与数据      （覆盖问题 1，解决"进制转换算计算还是代码"）
        否 → 保持问题 1 的答案

问题 3：现有分类下它会不会落单（< 3 个同类）？
        会 → 暂不新建分类，先并入最接近的分类，并在工具上标 tags
        不会 → 归入该分类
```

**三个问题依次回答，第一个能定案就停止。** 这套流程的价值在于：任何两个人按同一流程走，会得到同一个答案。

**几个典型样例的裁决结果**：

| 工具 | 问 1（对象） | 问 2（需代码知识？） | 最终归类 |
| --- | --- | --- | --- |
| 单位换算 | 数值 | 否 | `calc` |
| 进制转换 | 数值 | **是** | `data` ← 覆盖问 1 |
| 字数统计 | 文字 | 否 | `text` |
| Base64 | 代码/数据 | 是 | `data` |
| JSON 格式化 | 代码/数据 | 是 | `data` |
| Markdown 预览 | 文字 | 否 | `text` |
| 二维码生成 | 图片 | 否 | `media` |
| 日期计算 | 时间 | 否 | `time` |
| 化学式 / 摩尔质量 | 数值 | 否 | `calc` |
| 大小写转换 | 文字 | 否 | `text` |
| 方程求解 | 数值 | 否 | `calc` |
| 倒计时 / 考试日期 | 时间 | 否 | `time` |

> ⚠️ **注意进制转换的裁决结果从 `convert` 移到了 `data`。** 这是本方案中**唯一一个与现有定案冲突的归类**。理由：进制转换在 v0.2 §1.3 中被明确归入"**上信息课时**"场景，而非数学场景；其核心难点（大数精度、BigInt）也是编程知识而非数学知识。
>
> **但这不构成现在就改的理由**——见 §7 的演进路线，此项建议在 v1.1 与分类重构一并处理，v1 保持 `convert` 不动。

### 3.4 备选方案对比

| 方案 | 分类数 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| **A. 维持 3 分类** | 3 | 零改动，符合现有定案 | 每分类 17–33 个工具，导航失效；`convert` 吞噬一切 | ❌ 不可行 |
| **B. 本方案 6 分类**（推荐） | 6 | 维度统一；容量 50–80；贴合学生场景；无垃圾桶分类 | 需要一次重构（改 slug、改工具归类、改首页） | ✅ **推荐** |
| **C. 学科分类**（数学 / 物理 / 化学 / 语文 / 英语 / 信息） | 6–9 | 直接对应课业，"高中物理工具包"天然成立 | 单学科工具数少（化学约 2–3 个），大量分类页空旷；且违反已定案"用 tags 不用 category 承载学科" | ❌ 不采纳（学科继续用 `tags`） |
| **D. 用途分类**（做作业 / 上课 / 自习整理 / 生活） | 3–4 | 与 v0.2 §1.3 场景完全一致 | 同一工具服务多个场景（字数统计既用于作业也用于自习），必然重复归类，违反"category 只能有 1 个" | ❌ 不采纳（场景继续用 `tags`） |
| **E. 扁平无分类**（只有搜索 + 标签筛选） | 0 | 规模到 100 时最简单；搜索是最短路径 | 移除分类导航＝移除"目标模糊"用户的唯一路径（v0.2 §5.5 路径 B，占 25%）；且搜索前提是用户知道搜什么 | ⚠️ 可作 100+ 时的补充，不可替代分类 |

**方案 C / D 被否决的共同理由**：它们都试图让 `category` 承载"学科"和"场景"，而 v0.2 §3.3 已经定案这两个维度归 `tags`。**保持这个分工，分类体系就不会失控。**

## 4. 问题 3：是否需要二级分类

### 4.1 结论

> **需要分层，但反对做"二级分类"。**
>
> 正确形态是：**在分类页内部用"分区标题"组织工具，而不是新增第二层分类结构。**

### 4.2 为什么反对真正的二级分类

| 二级分类的代价 | 具体影响 |
| --- | --- |
| **路由翻倍** | 从 `/categories/{slug}` 变成 `/categories/{slug}/{sub}`，SEO 页面数从 6 变 30+，其中大量页面工具数 < 5，构成低质量聚合页——**违反 v0.2 §8「❌ 不做聚合采集页」** |
| **新增契约字段** | 需要 `subCategory`，而 `category` 只能有 1 个的规则会传染到二级，产生"这个工具属于哪个二级"的新争论 |
| **点击深度 +1** | 违反 v0.2 §1.4「查找工具 ≤ 2 次交互」。路径 B 从"首页 → 分类页 → 工具页"变成 4 步 |
| **100 个工具不需要 2 层** | 二级分类的合理触发点是"一级分类下有 **40+** 个工具"。100 个工具 ÷ 6 分类 ≈ 17 个/分类，**远未到需要第二层的规模** |
| **标签已经承担了这个职责** | v0.2 §3.3 已定案：学科 / 学段 / 场景用 `tags` 承载，`tags` 可以做筛选与聚合。再加一层分类是重复建设 |

### 4.3 推荐的替代形态：分类页内分区

```
/categories/text                    ← 一级分类页（URL 不变，SEO 不受影响）
  ├─ 分区标题：统计与检查            ← 纯展示层，无独立 URL
  │    ├─ 字数统计
  │    ├─ 敏感词检查
  │    └─ 重复行检测
  ├─ 分区标题：排版与格式
  │    ├─ Markdown 预览
  │    ├─ 文本去重
  │    └─ 大小写转换
  └─ 分区标题：改写与生成
       ├─ 拼音标注
       └─ 繁简转换
```

| 特性 | 说明 |
| --- | --- |
| URL | **不变**。仍是 `/categories/text`，SEO 结构零变化 |
| 数据 | **不新增字段**。分区归属可由 `tags` 或展示层的分组映射派生 |
| 交互深度 | **不变**。仍是"首页 → 分类页 → 工具页"3 步 |
| 扩展成本 | 分区是**展示层概念**，改分区不触碰任何工具定义；加工具时若落不进任何分区，直接追加一个分区即可 |
| 空分区 | 与空分类同理：**工具数 < 3 的分区不渲染** |

### 4.4 触发阈值（建议写入 v0.2）

| 规模 | 分类页形态 | 首页形态 |
| --- | --- | --- |
| **< 12 工具 / 分类** | 单一网格，无分区 | 分类卡片 + 全部工具网格 |
| **≥ 12 工具 / 分类** | **启用分区标题** | 分类卡片 + 常用工具（不再列全部） |
| **≥ 20 工具 / 分类** | 分区 + 分区内排序（按 `order`） + 页内快速筛选 | 同上 + 标签筛选入口启用（v0.2 §3.3 已定案 min 10） |
| **≥ 40 工具 / 分类** | 才重新评估是否需要真正的二级路由 | 同上 |

**当前是 2 工具/分类。距离第一档阈值还有 5 倍空间，因此 v1 什么都不用做**——但阈值必须先写进 v0.2，避免将来靠感觉决策。

## 5. 问题 4：分类名称偏技术还是偏用户

### 5.1 结论

> **必须偏用户。** 但采用**分层策略**：界面文字偏用户，代码标识与 URL 偏技术。

### 5.2 为什么必须偏用户（四条依据，全部来自既有定案）

| 依据 | 原文 |
| --- | --- |
| v0.2 §3.1 命名规则 | 必须用**用户会说的话**，不用行业术语 |
| v0.2 §1.2 用户定位 | 主要用户是**高中生**。高中生没有"字符串处理""编码转换""数据结构"这些词汇 |
| v0.2 §4.1 明确不是 | ❌ 专业开发者工具站（**不密集、不冷硬、不英文优先**） |
| WorkBuddy 评审 §3.5 | "转换工具"优于"编码转换"，"文本处理"优于"字符串处理" |

**反例（应当避免）**：字符串处理、编码转换、数据结构工具、格式化工具、正则工具、进制计算器、Markdown 工具、加密解密。

**正例**：文本与写作、计算与换算、代码与数据、图表与图片、时间与日程、校园与生活。

### 5.3 但"偏用户"有一个必须处理好的副作用

如果分类名全部中文化，界面上会出现**中文名与英文 slug 并存**的情况。这需要一个明确的分工规则，否则代码里会出现"分类名硬编码在组件里"的退化（**这正是 §1.3 已经发生的缺陷**）。

**建议的分层规则（值得写入 v0.2 §3.1）**：

| 层 | 用什么 | 示例 | 理由 |
| --- | --- | --- | --- |
| **界面显示** | 中文用户词 | "计算与换算" | 用户只认这个 |
| **URL / slug** | 英文短词 | `/categories/calc` | URL 一旦上线不可改（同 §3.4 工具 id 规则）；中文 URL 会出现百分号编码，对分享和 SEO 都不利 |
| **代码标识** | 英文键名 | `ToolCategory = "calc"` | 与 slug 保持 1:1，避免两层映射 |
| **搜索匹配** | 中文名 + 拼音 + 同义词 | 输入"换算""单位""huansuan"都能命中 | 与 v0.2 §5.1 拼音搜索一致 |

**核心要求**：`category` 的**中文显示名必须有唯一定义处**（建议定义在分类注册表里），组件只能读取，**禁止在任何组件里写"计算与换算"这类字面量**。

这与 v0.2 §7.2「单一数据源」和 AGENT_RULES §4.1「禁止硬编码」是同一条原则的延伸——当前分类体系缺的正是这个"分类的单一数据源"。

### 5.4 一个具体的命名权衡：「开发辅助」→「代码与数据」

| 维度 | `开发辅助`（现有） | `代码与数据`（建议） |
| --- | --- | --- |
| 描述的是 | **身份**（谁是开发者） | **内容**（代码、数据） |
| 高中信息课学生读到 | "这不是给我用的" | "哦，处理代码和数据的" |
| 是否行业术语 | 是（"辅助"是行业黑话） | 否 |
| 与定位一致性 | 有张力（定位明确不要开发者工具站） | 一致 |

**建议改名，但归类不变**：`dev` 这个 slug 建议保留到分类重构时再一并处理（slug 变更涉及 URL，属于核心路线变更）。

## 6. 问题 5：是否需要修改现有 ToolDefinition

### 6.1 分类维度：`category` 取值与语义 — 一行都不改

**v1 期间 `category` 的取值 / 类型 / 语义保持 100% 不变**，理由：

| 理由 | 说明 |
| --- | --- |
| `AGENT_RULES.md` §1.5 | 分类体系被列为**核心技术路线**，改动需走 6 步变更流程并等待人类协作者同意 |
| `MEMORY.md` | 分类 slug 已列为"**已定案标识符（禁止变更）**" |
| 收益/成本 | v1 只有 6 个工具、3 个分类。现在改分类，收益是 0（用户不会因为分类名更好而多用一个工具），成本是改类型 + 改 3 个定义 + 改首页 + 改测试 + 改文档 |
| 顺序风险 | 在 6 个工具零缺陷这一红线尚未达成时动分类结构，属于"在错误的时机做正确的改动" |

### 6.2 但 `ToolDefinition` 类型本身需要补字段（进度问题，非分类问题）

当前 `src/types/tools.ts` 只有 7 个字段，而 v0.2 §3.5 定案 16 个 + 技术文档建议的 `pinyin` = 17 个。

**其中与分类体系直接相关的有 2 个字段，必须在做分类页之前补齐**：

| 字段 | 为什么和分类相关 | 缺了会怎样 |
| --- | --- | --- |
| **`order`** | v0.2 §5.2 定案：分类页"按分类内的 `order` 权重"排序 | 分类页无法排序，工具顺序变成代码数组顺序（不可控） |
| **`tags`** | §4.3 的"分类页内分区"、未来的学科聚合都依赖它 | 分区无法自动派生；搜索命中维度减少 |

**其余字段**（`summary` / `tip` / `keywords` / `pinyin` / `emptyHint` / `errorHint` / `seoFaq` / `hidden` / `customUI`）按 Codex 路线图 Phase 2 的原计划在对应 Phase 补齐，**不属于本次分类研究的范围**。

### 6.3 分类展示层：这是**唯一必须现在改**的地方

| 项目 | 现状 | 建议 | 优先级 |
| --- | --- | --- | --- |
| 分类中文名定义处 | **不存在** | 新增一个分类注册表（分类 slug ↔ 中文名 ↔ 定位语 ↔ 图标 ↔ `order`） | 🔴 高 |
| `ToolCard` 渲染 `tool.category` | 直接显示英文 slug | 改为经分类注册表解析后显示中文名 | 🔴 高（**现有缺陷**） |
| `FavoriteToolsSection` 渲染 `tool.category` | 同样显示英文 slug | 同上 | 🔴 高（**现有缺陷**） |
| `registry.ts` 查询函数 | 只有 `getToolsByCategory` | 建议增加"取分类列表 / 取分类中文名"的查询函数 | 🟡 中 |

**`getToolsByCategory(category)` 的签名不要改**——它是公共接口（AGENT_RULES §7.5），改签名会波及所有调用方。新能力用**新增函数**的方式叠加。

### 6.4 修改清单（供 Codex 路线图落位）

| # | 改动 | 落位 Phase | 性质 |
| --- | --- | --- | --- |
| 1 | 新增分类注册表（中文名 / 定位语 / `order` / 图标） | **Phase 6**（分类页任务） | 补缺 |
| 2 | `ToolCard` 改读分类中文名 | Phase 6 | **修缺陷** |
| 3 | `FavoriteToolsSection` 改读分类中文名 | Phase 6 | **修缺陷** |
| 4 | `ToolDefinition` 补 `order` 字段 | Phase 2 遗留 / Phase 6 前置 | 补缺 |
| 5 | `ToolDefinition` 补 `tags` 字段 | Phase 2 遗留 | 补缺 |
| 6 | 分类判定规则（§3.3 三问）写入 v0.2 §3.1 | **文档任务** | 新增规则 |
| 7 | 分区阈值（§4.4）写入 v0.2 §5.2 | **文档任务** | 新增规则 |
| 8 | 6 个一级分类方案写入 v0.2 §3.1（标注为 v1.1 目标） | **文档任务** | 规划 |

**第 1–3 项是这一批里唯一"不修就是错的"的改动**，其余是规划与补课。

## 7. 问题 6：首页分类展示建议

### 7.1 v1 立即适用的 4 条建议

#### 建议 1：分类卡片只放"图标 + 名称 + 工具数"，不放一句话说明 🔴

**理由**：v0.2 §4.4 有一条硬红线——

> **首屏可见内容：搜索框 + 分类入口必须在 768px 高度内可见（适配 1366×768 笔记本）**

同时 v0.2 §5.1 要求"我的工具箱**必须**在首屏可见范围内"。**首屏要装 3 个模块：搜索框 + 分类入口 + 我的工具箱。**

按 1366×768 估算桌面端垂直预算：

| 区块 | 估算高度 |
| --- | --- |
| 顶栏（Logo + 搜索 + 我的工具箱入口） | ≈ 64px |
| Hero（slogan + 搜索框 + 角色） | ≈ 200–240px |
| 分类区标题 + 3 卡片一行 | ≈ 145px（卡片 ≈ 100px） |
| 我的工具箱（继续上次 + 收藏行） | ≈ 140–180px |
| **累计** | **≈ 550–630px** ✅ 766px 内可容纳 |

**如果分类卡片加上一句话说明**（每卡 ≈ 140px）：

| 场景 | 分类区高度 | 累计 | 结论 |
| --- | --- | --- | --- |
| 3 分类 × 1 行（含说明） | ≈ 185px | ≈ 590–670px | ⚠️ 边界 |
| **6 分类 × 2 行（含说明）** | **≈ 325px** | **≈ 730–810px** | 🔴 **超出 768px** |
| **6 分类 × 2 行（不含说明）** | **≈ 265px** | **≈ 670–750px** | ✅ 可行 |

> **结论：分类卡片的"一句话说明"是首屏预算里最贵的一块，必须在分类数超过 3 之前砍掉。** 一句话说明的正确位置是**分类页**（v0.2 §5.2 已定案"分类页卡片必须带一句话说明"），不是首页分类卡片。

#### 建议 2：首页分类数量上限 = 6，且超过 3 个时必须用"分组"而非"平铺"

**理由**：v0.2 §3.1 定案"分类数量全站控制在 3–6 个"。但**首页是否应该平铺全部 6 个，是另一个问题**。

| 首页分类数 | 布局建议 | 理由 |
| --- | --- | --- |
| **3 个**（v1） | 单行 3 列等宽卡片 | 一眼看完，符合 §5.5 路径 B |
| **4–6 个** | **分组**：主推 3 个（单行大卡）+ 其余折叠为一行小卡 / "更多" | 保持"一眼看完"的心智：用户扫视的永远是 3 个主入口 |
| **> 6 个** | 出现即说明分类体系失效，应回到 §4 用分区解决，**不要靠首页堆卡片解决** | — |

**移动端的额外约束**：v0.2 §5.6 定案移动端分类为 2 列卡片。6 个分类 = 3 行卡片 = 至少 300px 以上的首屏消耗。移动端首屏本就紧张（角色要 ≤120px 或隐藏、搜索框要吸顶），**建议移动端首页只平铺 3–4 个分类，其余收进"全部分类"**。

#### 建议 3：分类卡片必须显示"工具数量"

**理由**：零工具的分类页 = 点击即"这个站还没做完"，是 v0.1 空分类教训的翻版。工具数是**用户侧的诚实信号**，也是**作者侧的健康指标**（数量长期为 0 的分类应下线）。

同时落实 v0.2 §3.1 已有的两条硬规则：
- 工具数 **< 3** 的分类在首页**不渲染**
- 工具数 **= 0** 的分类**绝不出现**（v0.2 §5.2 已定案）

#### 建议 4：分类卡片显示中文名，不显示英文 slug 🔴

**这是 §1.3 已发现的现有缺陷的首页表现。** 分类卡片与工具卡片上的分类标签，必须显示"计算与换算"而不是 `calc`。参照 v0.2 §4.6「几何小图标」——分类图标也应来自分类注册表，与角色世界观一致（数据碎片 / 能量线 / 坐标点）。

### 7.2 为什么"首页全部工具网格"不是分类的替代品

`src/app/page.tsx` 当前渲染的是"**全部工具**"网格（标题即"全部工具"）。这作为 3 工具时的临时形态**没问题**，但不能作为长期方案：

| 工具数 | "全部工具网格"的问题 |
| --- | --- |
| 3 | 没有问题，一屏看完 |
| 12 | 需要滚动 2–3 屏才能看全，"浏览"开始变慢 |
| 30 | 首页首屏（768px 红线）装不下搜索框 + 分类入口 + 我的工具箱 + 工具网格 → **必然违反红线** |
| 100 | 完全不成立 |

**建议：首页的工具展示按规模切换。**

| 规模 | 首页工具区形态 |
| --- | --- |
| < 10 | 「全部工具」网格（现状） |
| **10–24** | 「常用工具」8–12 个（按 `order` / 未来的使用数据排序）+ "查看全部" |
| ≥ 25 | 「常用工具」+ 「最近更新」+ 分类入口（工具不再全量平铺） |

这与 v0.2 §5.1 定案的"**常用工具**（高频工具卡片网格）"一致——**当前 `page.tsx` 的"全部工具"标题与 v0.2 §5.1 的"常用工具"是有偏差的**，可作为 Phase 6 首页完善时一并对齐。

### 7.3 首页分类展示的规格建议

| 元素 | 规格 | 依据 |
| --- | --- | --- |
| 卡片数量上限（桌面首屏） | 3 主推，其余折叠 | §7.1 建议 2 |
| 卡片数量上限（移动首屏） | 3–4（2 列） | v0.2 §5.6 |
| 卡片内容 | 图标 + 中文名 + 工具数 | §7.1 建议 1、3 |
| **卡片内容中不含** | ❌ 一句话说明 ❌ 英文 slug ❌ 角色形象 | 首屏预算 + §1.3 缺陷 + §4.4 操作区无装饰 |
| 卡片高度 | ≤ 100px | §7.1 建议 1 的预算推导 |
| 分区/排序 | 按分类注册表的 `order` | 与 v0.2 §5.2 一致的排序原则 |
| 空分类 | 不渲染（工具数 < 3） | v0.2 §3.1 已有定案 |

## 8. 演进路线建议

### 8.1 按规模分阶段

| 阶段 | 工具数 | 分类动作 | 首页动作 |
| --- | --- | --- | --- |
| **v1（现在）** | 3 → 6 | **结构零改动**。只做：分类注册表 + 修 ToolCard/FavoriteToolsSection 的中文名缺陷 | 分类卡片瘦身（去说明） |
| **v1.1** | 12–15 | **启动分类重构**：走 AGENT_RULES §1.5 变更流程，先改 v0.2 再改代码。引入 6 分类方案中的前 4 个（文本与写作 / 计算与换算 / 代码与数据 / 时间与日程） | 首页分类 4 个 = 3 主推 + 1 折叠；标签筛选启用（≥10 已满足） |
| **v1.2** | 20–30 | 补齐 6 个一级分类（+ 图表与图片 / 校园与生活）。一级分类 ≥ 12 工具时**启用分类页内分区** | 工具区从"全部工具"改为"常用工具" |
| **v2.0** | 40–60 | 校准分类归属（用真实使用数据淘汰冷分类）；`tags` 承担学科聚合 | 首页只用 3 个主推分类 + 搜索 |
| **长期** | 80–100 | 仅在某个分类 ≥ 40 工具时才评估真正的二级路由；否则永远用分区 | 首页不再展示工具列表，改为"搜索 + 分类 + 我的工具箱" |

### 8.2 一个必须同时建立的机制：分类健康度自检

分类体系腐化的方式不是"分类名起错了"，而是"**没人再检查分类是否还平衡**"。建议每加 5 个工具做一次自检：

| 自检项 | 红线 | 触线后的动作 |
| --- | --- | --- |
| 单个分类的工具占比 | **> 35%** | 该分类过大，检查是否需要拆出新的对象维度分类 |
| 单个分类的工具数 | **< 3** | 分类过小，并入最接近的分类并下架该分类页 |
| 分类总数 | **> 6** | 违反 v0.2 §3.1，必须先合并或改用 `tags` |
| 归类歧义 | 存在工具**在 2 个分类间摇摆** | 该分类的定义不够精确，回到 §3.3 三问重新裁决并更新规则 |
| 零使用分类 | 上线 3 个月后某分类下所有工具使用次数为 0 | 整个分类下线（对应 v1.1 的"数据驱动淘汰"） |

**第 1 项（35% 红线）是本方案里最重要的一条自检。** 当前 `convert` 占 2/3 ≈ **67%**，已经严重超线——这就是"隐患 A"的量化表达：**`convert` 现在就已经是垃圾桶了，只是因为只有 3 个工具所以看不出来。**
