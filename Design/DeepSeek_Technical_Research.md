# 1. 网站开发基础知识

## 1.1 先建立一个整体认知：一个网页是怎么出现在屏幕上的

用户访问一个页面，背后发生的事可以粗略拆成四步：

```
1. 浏览器请求网址
        ↓
2. 服务器返回 HTML（页面骨架）+ CSS（样式）+ JS（交互逻辑）
        ↓
3. 浏览器解析 HTML 画出界面
        ↓
4. JS 开始运行，让界面能响应用户操作（点按钮、输入文字）
```

传统做法（也叫 SPA，单页应用）是：服务器只返回一个几乎空的 HTML，剩下所有内容都由第 4 步的 JS 在浏览器里"画"出来。

这样做的问题在**第 2 步**：搜索引擎爬虫拿到的 HTML 是空的，它看不到你的内容，所以 SEO（搜索引擎优化）很差。

**Next.js 要解决的核心问题就是这个**：让页面内容在服务器上就已经拼好了，再发给浏览器。

## 1.2 Next.js 是什么

### 一句话定义

> Next.js 是一个建立在 React 之上的**网站框架**。

要理解这句话，先区分两个词：

| 概念 | 是什么 | 类比 |
| --- | --- | --- |
| **React**（库） | 提供"把界面拆成组件、数据变了界面自动更新"的能力 | 一套**发动机和零件** |
| **Next.js**（框架） | 在 React 之上补齐"路由、页面渲染、打包、优化、部署" | 一整台**整车** |

所以：**React 是能力，Next.js 是把这些能力组装成一个真正网站的方式。**

### Next.js 给本项目解决的 5 件事

| # | 能力 | 对本项目的意义 |
| --- | --- | --- |
| 1 | **文件即路由** | 在 `app/tools/base64/page.tsx` 建一个文件，网站就自动有了 `/tools/base64` 这个网址，不用手写路由表 |
| 2 | **服务端渲染 / 静态生成** | 每个工具页的标题、说明文字在服务器上就生成好，搜索引擎能读到 → 直接服务于设计文档 §8 的"SEO 友好" |
| 3 | **自动代码分割** | 用户打开首页时，不会把 20 个工具的全部代码都下载下来，只有进入某个工具页才加载它的代码 → 首屏更快 |
| 4 | **内置优化** | 图片自动压缩和懒加载、字体优化、打包压缩，都是配置即可，不用自己搭工具链 |
| 5 | **一条命令部署** | 相同的代码可以直接部署到 Vercel 等平台，也支持导出静态文件 |

### 必须理解的三个渲染概念

这是初学者最容易糊涂、但必须搞懂的地方。同一个 Next.js 项目里，页面可以有三种"出生方式"：

| 方式 | 中文 | 什么时候生成 HTML | 适合什么页面 | 本项目用例 |
| --- | --- | --- | --- | --- |
| **SSG** | 静态生成 | **构建时**（打包那一刻）就生成好，之后每个用户拿到的都是同一份 | 内容不因人而异、很少变的页面 | 首页、工具页、分类页、关于页（**本项目 95% 的页面都是这一类**） |
| **SSR** | 服务端渲染 | **每次有人访问时**在服务器现场生成 | 内容跟登录用户/实时数据相关的页面 | 未来如果有账号系统，登录后的"我的工具箱"页 |
| **CSR** | 客户端渲染 | 先发空壳，到浏览器里用 JS 填内容 | 强交互、对 SEO 无所谓的部分 | 工具页里的**交互部分**：输入框、转换结果、收藏按钮 |

**本项目的关键理解：一个页面可以同时是 SSG 和 CSR。**

比如"进制转换"工具页：

```
静态部分（构建时生成，供搜索引擎读取）
  ├─ H1：进制转换
  ├─ 一句话说明
  ├─ 怎么用的说明文案
  ├─ 底部小技巧
  └─ FAQ 结构化数据

交互部分（浏览器里运行）
  ├─ 输入框里的数字
  ├─ 转换后的结果
  └─ 收藏按钮的状态
```

这样既拿到了 SEO，又保持了工具的即时响应——**这就是设计文档选 Next.js 的真正理由**。

### 名词表

| 名词 | 含义 |
| --- | --- |
| App Router | Next.js 较新的路由系统，代码放在 `app/` 目录下，用文件夹结构表示网址路径 |
| `layout.tsx` | 布局文件，包住它下面所有页面，用来放顶栏、页脚——**只写一次** |
| `page.tsx` | 一个具体的页面 |
| Server Component | 默认的组件类型，在服务器上运行，**不能**用 `useState`、不能读取浏览器 API |
| Client Component | 文件顶部写 `'use client'` 的组件，在浏览器里运行，可以用状态和交互 |
| `generateStaticParams` | 告诉 Next.js"我要预先生成哪些动态页面"的函数——**新增工具自动化就靠它** |
| `generateMetadata` | 为每个页面动态生成 `<title>`、description 等 SEO 信息 |
| 构建 / build | 把源代码编译、优化、打包成可以部署的产物 |
| 部署 | 把构建产物放到服务器上，让别人能访问 |

## 1.3 React 组件是什么

### 一句话定义

> 组件 = **一个返回界面描述的函数**。

```jsx
// 示意片段（不是完整代码）
function ToolCard() {
  return <div>进制转换</div>   // 描述"这一块长什么样"
}
```

React 的核心思想只有两条：

1. **界面 = 组件的组合**。一个页面不是一整个大文件，而是由许多小零件（组件）拼起来的。
2. **界面 = 数据的样子（UI = f(state)）**。你不去手动改 DOM，你只改变数据，React 负责把界面更新成数据对应的样子。

第二条是本项目"工具正确性"的根本保障：**转换逻辑只关心数据，界面只负责显示数据**，两者分开，才好测试、才好排错。

### 组件的三个核心概念

| 概念 | 通俗解释 | 本项目示例 |
| --- | --- | --- |
| **props**（属性） | 从**外面**传进组件的参数，组件自己不能改。像函数的参数 | `<ToolCard name="进制转换" category="转换工具" />` |
| **state**（状态） | 组件**自己内部**会变化的数据。改它，界面自动更新 | 输入框里的字符串、当前展开的下拉框 |
| **组合**（composition） | 把小组件拼成大组件，而不是靠"继承" | `工具页 = 标题 + 输入区 + 输出区 + 收藏按钮` |

### 数据怎么"流"

React 有一条非常重要的规则：

> **数据从上往下流（父 → 子），事件从下往上冒（子 → 父）。**

意思是：

- 父组件把数据作为 props 传给子组件。
- 子组件不能直接改父组件的数据，只能**通知**父组件"用户点了这里"，由父组件去改。

这条规则听起来绕，但它的好处是：**数据的变化来源永远只有一个地方**。工具站最怕的就是"UI 显示的结果和实际算出来的结果不一致"，而这条规则从结构上就避免了这个 bug。

### 组件树：把页面想成一棵树

以"进制转换"页为例：

```
工具页 (page.tsx)                        ← 服务器组件，负责 SEO 文案
├─ 面包屑 (Breadcrumb)                    ← 展示组件
├─ 工具标题区 (ToolHeader)
│   ├─ H1 标题
│   └─ 一句话说明
├─ 工具交互区 (BaseConverterTool)          ← 客户端组件，负责计算
│   ├─ 输入框 (TextInput)
│   ├─ 进制选择 (Select)
│   ├─ 输出区 (ResultBox)
│   └─ 复制按钮 (CopyButton)
├─ 收藏按钮 (FavoriteButton)               ← 客户端组件，读写 LocalStorage
└─ 小技巧 (ToolTip)                        ← 来自工具配置
```

**看这棵树能得到一个重要结论**：只有需要交互的那部分才必须是客户端组件。标题、说明、小技巧这些纯文字，留在服务器端就够——这样 SEO 好、加载快。

这个"颗粒度"判断，是使用 Next.js 时最值钱的一项技能。

## 1.4 Tailwind CSS 作用

### 它想解决的问题

传统写法：给元素起一个 class 名，然后去另一个 CSS 文件里写样式。

```css
/* 传统方式：要起名字，要在两个文件之间跳转 */
.tool-card { padding: 16px; border-radius: 12px; background: white; }
```

问题在于：**命名成本高、样式和结构分离、改一个组件要翻两个文件、删代码不敢删 CSS。**

Tailwind 的做法是：不写 CSS 文件，直接在标签上用一组预定义的小工具类拼出样式。

```jsx
// 示意片段：直接在结构上表达样式
<div className="p-4 rounded-xl bg-white shadow-sm">进制转换</div>
```

**它为什么叫"原子化 CSS"**：每个 class 只做一件事（`p-4` = padding 1rem，`rounded-xl` = 大圆角）。复杂的样式由这些小原子拼出来。

### 对本项目的三个实际好处

| 好处 | 说明 |
| --- | --- |
| **不用起名字** | 工具站会有大量相似但不完全相同的卡片、按钮，起名会变成负担 |
| **改样式不用切文件** | 想调一个工具的间距，就在那个文件里改，不会误伤别处 |
| **强制统一数值** | 只能从预设的间距/字号/颜色里选，天然避免了"3px、5px、7px 混用"的混乱——这正好服务于设计评审 §4.4 要求的"统一圆角、六档字号、三档色彩" |

### 与"设计规范"的关系（重点）

Tailwind 有一个 `tailwind.config` / 主题配置，可以**把设计规范变成代码里的唯一来源**：

```
设计规范（写进配置）              代码里怎么用
├─ 主色：科技蓝紫        →        bg-primary / text-primary
├─ 辅助色：粉/橙/薄荷    →        bg-accent-1 / bg-accent-2
├─ 中性灰阶 6-8 档       →        bg-gray-50 ... bg-gray-900
├─ 圆角 12-16px         →        rounded-xl
├─ 字号 6 档            →        text-sm / text-base / text-xl ...
├─ 等宽字体（数字/代码） →        font-mono      ← 工具站专业感的关键
└─ 暗色 token           →        dark: 前缀
```

**这一步很重要**：如果设计规范只写在文档里，半年后代码里就会出现十种蓝色。写进 Tailwind 配置后，"用错颜色"变成了一件需要刻意为之的事。

> 补充：Tailwind 近期版本（v4）把配置从单独的 JS 文件改成了 CSS 里写 `@theme`。概念完全一样（"集中定义设计变量，全站引用"），只是写法位置变了。学习时理解概念比记语法重要。

### 需要知道的缺点

| 缺点 | 缓解方式 |
| --- | --- |
| 类名很长，JSX 看起来很乱 | 把重复出现的组合抽成组件（如 `<ToolCard>`），而不是抽成 CSS 类 |
| 需要记类名 | 用编辑器插件自动补全；只记常用的 30 个就够 |
| 复杂状态样式（如 `:hover` 内嵌子元素）略啰嗦 | 这种情况才考虑写少量自定义 CSS |

## 1.5 页面、组件、数据之间的关系

这是第 1 节最重要的一小节。理解了这个关系，第 2、3、4 节都是它的自然推论。

### 三个层次

```
┌─────────────────────────────────────────────────────┐
│  数据层  Data                                        │
│  工具的元数据（名称、分类、标签、说明）+ 算法逻辑      │
│  → 纯 JavaScript，不依赖 React                       │
│  → 可以单独测试，比如"0 转成二进制是不是 0"           │
└──────────────────────┬──────────────────────────────┘
                       │ 被读取
                       ↓
┌─────────────────────────────────────────────────────┐
│  组件层  Components                                  │
│  只负责"数据长什么样"：卡片、输入框、按钮、结果区      │
│  → 不知道数据从哪来，只接收 props 并显示              │
└──────────────────────┬──────────────────────────────┘
                       │ 被组装
                       ↓
┌─────────────────────────────────────────────────────┐
│  页面层  Pages / Routes                              │
│  决定"哪个网址显示哪些组件"，并负责 SEO 元信息          │
│  → app/ 目录下的文件                                 │
└─────────────────────────────────────────────────────┘
```

**关键原则：依赖只能从上往下，不能倒过来。**

- 数据层不知道组件的存在 → 所以算法可以独立测试
- 组件层不知道自己在哪个页面 → 所以同一个卡片能用在首页、分类页、收藏页
- 页面层不做计算 → 所以页面的职责很单纯

### 本项目的三种数据，不要混淆

这是设计文档里没写清、但写代码时一定会撞上的问题。项目里的"数据"其实是三种完全不同的东西：

| 类型 | 举例 | 存在哪 | 谁写的 | 变不变 |
| --- | --- | --- | --- | --- |
| **A. 工具元数据** | 工具名、分类、标签、说明、小技巧 | 写在代码里（工具定义文件） | 开发者 | 只在发版时变 |
| **B. 用户本地数据** | 收藏列表、最近使用、偏好设置 | 浏览器 LocalStorage | 用户行为 | 随时变，因人而异 |
| **C. 运行时数据** | 输入框里的内容、转换结果 | 内存（React state） | 用户输入 | 每次操作都变，刷新即消失 |

**为什么必须区分它们**：

- A 和 B 混在一起 → 会在服务端渲染阶段读取浏览器存储，直接报错
- B 和 C 混在一起 → 会把用户输入的大段文本也存进 LocalStorage，撑爆容量且涉及隐私
- A 和 C 混在一起 → 每次输入都要重新查一遍工具定义，白白浪费性能

**一句话记忆**：

> A 是"网站的地图"，B 是"用户的抽屉"，C 是"手上的草稿纸"。

第 4 节讲 LocalStorage 时，只处理 **B**。

### 完整数据流：用户输入一个数字之后的 6 步

```
1. 用户在输入框打字
        ↓
2. 输入框组件的 state 更新（这是 C 类数据，只在内存里）
        ↓
3. React 发现 state 变了，重新调用组件函数
        ↓
4. 组件调用数据层（A 类）里这个工具的纯函数：convert(input, from, to)
        ↓
5. 纯函数返回结果或错误信息（不碰界面，不碰存储）
        ↓
6. 组件把结果显示到输出区；如果用户点了收藏，
   才把工具 id（不是输入内容）写进 LocalStorage（B 类）
```

注意第 4 步和第 6 步的分工：**算法只做算法的事，存储只做存储的事。** 这样出错时你能立刻定位问题在哪一层。

## 1.6 TypeScript 是什么，为什么本项目强制使用

### 一句话定义

> TypeScript = **JavaScript + 类型标注**。它在**写代码时**就检查"这个值的类型对不对"，而不是等到用户打开页面才发现错误。

```ts
// 示意片段
function add(a: number, b: number): number { return a + b }

add(1, 2)      // ✅ 通过
add("1", 2)    // ❌ 写的时候就报错，不用等到运行
```

### 它解决什么问题

| 没有类型 | 有类型 |
| --- | --- |
| 工具配置少写一个字段，打开页面才发现报错 | 定义处立刻提示"缺少必填字段" |
| 改了字段名，另一处忘了跟着改，运行时崩 | 编译期就指出所有受影响的位置 |
| `run()` 到底收字符串还是数字，要翻代码才知道 | 类型签名就是最准确的文档 |
| 半年后回来看代码，不确定这个函数怎么用 | 编辑器直接提示参数与返回值 |

### 为什么本项目把它列为"强制"

三条理由，全部来自这个项目的特殊处境（对应 `AGENT_RULES.md` §3.2）：

1. **工具契约是公共接口。** 6 个（未来十几个）工具定义文件都遵循同一份契约。契约靠类型表达，比靠文档表达可靠得多——少一个字段，编译期就知道。
2. **`run()` 必须是纯函数。** 类型把"输入是什么、输出是什么"写死在签名上，为"每个工具 ≥10 组边界用例"的测试提供了基础（`AGENT_RULES.md` §4.4 红线）。
3. **项目会长期由不同 Agent 接手。** 人会走、模型会换。**类型是唯一不会忘记上下文的协作者。**

### 需要理解的三个概念

| 概念 | 含义 | 本项目用例 |
| --- | --- | --- |
| **类型标注** | 给变量、参数、返回值写上类型 | `run(input: string): string` |
| **接口 / 类型别名** | 描述一个对象"长什么样" | 工具配置契约本身就是一个类型 |
| **编译期检查** | 在代码运行前检查类型；不合格的代码无法通过构建 | 对应"不提交带类型错误的代码" |

### 常见的两个误解

| 误解 | 澄清 |
| --- | --- |
| "TypeScript 是另一种语言，要重新学" | 不是。它就是 JavaScript 加上可选标注。不写标注也是合法 TS，但本项目的契约字段必须标注 |
| "类型让开发变慢" | 前期多写几行，后期少调几小时。**在这个项目里，类型最大的价值不在写新代码，而在改旧代码。** |

### 与工程规则的对应

| `AGENT_RULES.md` 规则 | 内容 |
| --- | --- |
| §3.1 | 语言 **TypeScript** —— **强制**，不是可选 |
| §3.2 | 不新增 JavaScript 源文件；不用 `any` 绕过类型检查；工具算法必须有明确的输入/输出类型 |
| §3.7 | 🔴 不关闭类型检查或 lint 规则来"通过"改动 |

## 2.3 为什么这样组织：逐条解释

### ① 为什么工具定义放在 `lib/tools/definitions/`，而不是放在 `components/`

这是最重要的一个决定。

如果写成 `components/tools/Base64Tool.tsx`，那么：**算法和界面绑死在一个 React 文件里**。后果是：

- 想测试"Base64 编码是否正确"，必须先启动页面、点按钮——没法自动化测试
- 首页要展示工具列表，只能手动维护另一个数组
- 将来做 App，这段算法没法复用
- 加一个工具，至少要在三四个地方各改一处

**改成"一个工具一个定义文件"以后**，这个文件里放的是：

```
工具 id、名称、分类、标签、说明、小技巧、SEO 文案、排序权重
+ 纯函数算法（输入 → 输出 / 抛错）
+ 可选：自定义界面组件名
```

界面用哪种模板，由配置里的字段决定（见 3.4）。**"新增一个工具"因此变成了"新增一个文件"**，这正是设计文档 §10.1 和设计评审 §5.4 最后一条要求的。

### ② 为什么 `app/` 里只有很少的文件

`app/` 只干两件事：**定义网址**、**填 SEO 元信息**。真正的逻辑都在 `lib/`。

这样做的直接收益：

- 全站只有 **一个** 动态路由文件 `app/tools/[toolId]/page.tsx` 来处理所有工具页。加第 7 个、第 70 个工具，这个文件都不用改。
- 首页、分类页、sitemap 都从同一个工具注册表读取，**不会出现"首页显示了某个工具但点进去 404"这类不一致**。

### ③ 为什么 `components/ui/` 和 `components/tools/` 要分开

| 目录 | 判断标准 | 例子 |
| --- | --- | --- |
| `ui/` | **不知道项目是干什么的**，换个项目也能用 | `Button`、`Card`、`Input` |
| `tools/` | **知道什么是工具**，离开这个项目就没意义 | `ToolCard`、`FavoriteButton`、`ToolLayout` |

好处是：将来做视觉调整时，改 `ui/` 就能影响全站按钮；而改 `tools/` 只影响工具相关区域。这个边界清晰了，样式重构才不会失控。

### ④ 为什么要有 `hooks/` 目录

`hooks/` 存放的是"把数据层接到 React 上"的小函数。它的存在意义是**把 LocalStorage 的脏活集中隔离**：

- 组件里永远不出现 `localStorage.getItem(...)` 这种裸调用
- 处理"服务端渲染时没有 window"的坑，只在一处处理（见 4.5）
- 将来从 LocalStorage 换成账号云同步，**只改 hooks，所有组件不动**

### ⑤ 为什么 `content/` 独立出来

设计评审 §2.4 要求"每个工具配一句小技巧"，§5.1 要求 FAQ 结构化数据。这些是**文案，不是逻辑**：

- 文案需要反复打磨，甚至可能给非开发者校对
- 混在代码里改一次就有改错逻辑的风险
- 独立出来以后，可以做"文案 + 工具 id"的一致性检查（防止某工具忘了写）

### ⑥ 为什么是 `tests/` 而不是和代码放一起

两种做法都合理，本项目选独立目录的理由是：**本项目要测试的东西非常集中**——就是 `lib/tools/definitions/` 里的算法。集中放一个目录，一眼能看出哪个工具还没写测试。这正是设计评审 §5.4 要求的"每个工具至少 10 组边界用例"的落地位置。

### ⑦ 为什么没有 `pages/` 目录

Next.js 早期版本用 `pages/`，现在用 `app/`。**两者不要混用**，否则会出现路由冲突。新项目统一用 `app/`。

## 2.4 对比：一个容易犯错的目录结构

```
❌ 反面示范
components/
  HomePage.tsx
  Base64Page.tsx            ← 页面和组件混在一起
  JsonPage.tsx
  UnitConvertPage.tsx
utils/
  base64.ts                 ← 算法和界面分离得太远，加工具要跳两个目录
  json.ts
data/
  tools.ts                  ← 所有工具信息挤在一个 800 行的大文件里
```

问题：

| 问题 | 后果 |
| --- | --- |
| 页面和组件混放 | 新人不清楚哪个是路由，哪个是零件 |
| 算法在 `utils/`、界面在 `components/`、配置在 `data/` | **加一个工具要改三个目录**，违背 §10.1 |
| `data/tools.ts` 单文件 | 每个工具的信息 + 算法挤在一起，冲突频繁，难以并行开发 |
| 没有 `hooks/` | LocalStorage 调用散落在十几个组件里，无法统一处理 SSR 问题 |
| 没有 `content/` | 文案埋在 JSX 里，改文案要动组件代码 |

## 2.5 这套结构与未来 PWA / App 的关系

这也是把算法放进 `lib/` 的长期价值：

```
                ┌──────────────────────────────┐
                │  lib/  （纯逻辑，无 React）    │
                │  工具算法 + 工具元数据         │
                └───────────┬──────────────────┘
                            │ 谁都能用
        ┌───────────────────┼───────────────────┐
        ↓                   ↓                   ↓
  Next.js 网站        PWA（同一套代码）     未来 App
  app/ + components/  加 manifest +         用 React Native 等，
                      Service Worker        直接复用 lib/ 的算法
```

**如果算法写进了 React 组件，这三条路就全断了。** 所以在项目第一天就把 `lib/` 划出来，成本几乎为零，收益却决定了两年后的可扩展性。

> 注意：设计评审 §6.4 明确指出 PWA 的前提是"移动端占比 ≥ 40%"。这里只是说明结构上留好了路，**不是现在就做 PWA**。

# 3. 工具系统设计思路

这是整份文档技术含量最高的一节，也是决定这个项目能否长大的关键。

## 3.1 先问一个问题：什么是"变"的，什么是"不变"的？

所有框架设计的起点都是这个提问。对本项目做一次拆解：

| 环节 | 会不会随工具增加而变 |
| --- | --- |
| 工具的名称、分类、标签、说明 | 每个工具都不同 → **变** |
| 具体的计算逻辑（怎么转二进制、怎么编码 Base64） | 每个工具都不同 → **变** |
| 界面的**大体形状**（输入 → 按钮 → 输出 → 复制） | 6 个工具里 5 个一样 → **几乎不变** |
| 路由规则（`/tools/xxx`） | 永远一样 → **不变** |
| SEO 元信息的**结构** | 永远一样 → **不变** |
| 收藏按钮的行为 | 永远一样 → **不变** |
| 空状态、错误提示的样式 | 永远一样 → **不变** |

**结论**：变的是"内容"和"算法"，不变的是"骨架"和"规则"。

所以正确做法是：

> **把不变的骨架写一次（写死、写稳），把变的部分抽成配置（只需新增文件）。**

设计文档 §3.3 说的"新增工具不应该重新设计页面"，翻译成工程语言就是这句话。

## 3.2 核心思路：一张注册表驱动整个网站

这是本节的核心概念，请重点理解。

### 从"多处维护"变成"单一数据源"

```
❌ 没有注册表时：加一个工具要改 6 个地方
   1. 写算法函数
   2. 写工具页面组件
   3. 在路由里加一条
   4. 在首页的"常用工具"里加一项
   5. 在分类页里加一项
   6. 在 sitemap 里加一个网址
   → 漏掉任何一处，就出现"有页面但首页看不到"或"首页有但点进去 404"

✅ 有注册表时：加一个工具只改 1 个地方
   1. 新增一个工具定义文件
   → 路由、首页、分类页、搜索索引、sitemap、SEO 全部自动出现
```

用一个类比：**注册表就像图书馆的图书总目录**。

- 每本书（工具）自己知道自己是什么
- 但"哪些书在哪个书架""怎么查书""新书公告"都从总目录派生
- 管理员只需要把新书登记进总目录，不需要重新装修图书馆

### 结构示意

```

┌────────────────────┐              ┌──────────────────────────┐
│ base-convert.ts    │──┐           │  汇总所有定义             │
│ unit-convert.ts    │──┤           │  提供查询函数：            │
│ char-count.ts      │──┼──导入──→  │   getAllTools()          │
│ base64.ts          │──┤           │   getToolById(id)        │
│ json-format.ts     │──┤           │   getToolsByCategory(c)  │
│ markdown-preview.ts│──┘           │   getToolIds()           │
└────────────────────┘              └────────────┬─────────────┘
                                                 │ 被读取
        ┌────────────────┬───────────────┬───────┴────────┬──────────────┐
        ↓                ↓               ↓                ↓              ↓
  动态路由生成      首页工具列表      分类页内容      搜索索引        sitemap/SEO
  [toolId]/page     ToolGrid        [category]/page  search-tools   sitemap.ts
```

### 为什么这能成立：Next.js 提供了两个"钩子"

注册表之所以能驱动路由，靠的是 Next.js App Router 的两个函数：

| 函数 | 作用 | 在本项目里怎么写 |
| --- | --- | --- |
| `generateStaticParams` | 返回一个 id 列表，Next.js 为每个 id 预先生成一个静态页面 | 返回注册表里所有工具的 id |
| `generateMetadata` | 根据当前页面的参数，动态生成 `<title>` 和 description | 从注册表取出该工具的 SEO 配置 |

**这就是"加一个工具不用改路由"的实现原理**：路由文件里写的是"对所有工具都这样做"，而不是"对 Base64 这样做、对 JSON 那样做"。

## 3.3 工具配置契约：一个工具要交代哪些事

"契约"的意思是：**不管什么工具，都要按同一套字段来描述自己**，系统才能统一地处理它——生成路由、渲染界面、跑测试。这是"加工具不改页面"能够成立的前提。

**但"统一"不等于"字段越多越好"。** 第一版采用**分层契约**：框架只强制校验最小的一组字段；其余字段由产品要求填写，但框架不强制。

**为什么要分层**：如果第一版就把所有字段都设成必填，那么"新增一个工具"的启动成本会变高，而且大部分字段（SEO、拼音、版本）在早期根本用不到。**契约应该只强制"系统运转必需"的那一部分。**

### 第一层 · 框架核心字段（第一版必填，6 个）

这 6 个字段是**系统能否运转的底线**：缺任何一个，注册表驱动路由、模板渲染、算法测试三者中就有一环走不通。

| 字段 | 说明 | 缺了会怎样 |
| --- | --- | --- |
| `id` | 网址用的英文标识，如 `base-convert` | 无法生成路由；**一旦上线不能改**（否则收藏失效、外链断开） |
| `name` | 中文显示名，如"进制转换" | 页面上没有标题，用户与搜索引擎都无法识别 |
| `category` | 所属分类，**只能有一个** | 无法归入分类页与首页入口 |
| `description` | 说明段落（工具页正文，也用于 SEO） | 工具页没有正文，SEO 失效 |
| `template` | 用哪个界面模板（见 3.4） | 不知道该用什么界面渲染 |
| `run` | **纯函数**：输入 → 输出，或抛出可读的错误 | 工具无法计算，等于不存在 |

> **`run` 必须是纯函数，这是硬性要求。** 同样的输入永远得到同样的输出，不读写任何外部状态。
> 好处：可以脱离界面单独测试 → 直接服务于"每个工具 ≥10 组边界用例"的验收标准（`AGENT_RULES.md` §4.4 红线）。

### 第二层 · 产品要求字段（第一版仍要填，但框架不强制校验）

以下字段由 `Documents/WebsiteDesignDocument_v0.2.md` §3.5 列为必需。**框架不把它们设成必填，是为了降低早期开发的摩擦；但产品验收时它们是必查项。**

| 字段 | 说明 | 谁在用它 |
| --- | --- | --- |
| `tags` | 标签数组，如 `["数学","计算机","信息课"]` | 搜索命中；未来的学科聚合 |
| `summary` | 一句话说明，卡片上显示 | 首页、分类页的卡片 |
| `tip` | 底部一句话小技巧 | 工具页底部 |
| `exampleInput` | "试试示例"按钮的预填内容 | 工具页（验收项） |
| `keywords` | 搜索关键词 | 搜索匹配 |
| `order` | 人工排序权重 | 首页"常用工具"、分类页排序 |
| `emptyHint` | 输入为空时的提示文案 | 模板的空状态 |
| `errorHint` | 出错时的提示模板 | 模板的错误状态 |

> **为什么不把它们设为"框架必填"**：它们是**内容**，不是**机制**。少写一个 `tip`，工具照样能算能用；少写一个 `template`，系统直接坏掉。把"内容字段"降为软要求，可以让第一个工具更快跑通，也避免早期为了凑字段而写空文案。

### 第三层 · 明确延后到后续版本

**第一版不实现、也不要求填写**的字段（属于"避免过度设计"，见第 7 节）：

| 字段 | 用途 | 延后理由 |
| --- | --- | --- |
| `seoFaq` | 生成 FAQ 结构化数据 | 第一版先把 `description` 写扎实；结构化数据属 v1.1 的 SEO 增强项 |
| `pinyin` | 拼音首字母搜索（`jz` → 进制转换） | ⚠️ 见下方一致性提示 |
| `minVersion` | 工具级版本控制 | 工具 `id` 已不可变，工具级版本在第一版没有使用场景 |
| `hidden` | 临时下架但保留代码 | 第一版不做工具淘汰（淘汰属于 v1.1 的"数据驱动淘汰"） |

> ⚠️ **一致性提示（需人工裁决，建议在开发 Phase 3 之前定）**
>
> **（1）`pinyin` 与 v0.2 冲突。** `WebsiteDesignDocument_v0.2.md` §5.1 与 §3.5 都把"搜索支持拼音首字母"列为 **v1 必做**；`AGENT_RULES.md` 附录 A 也把它记为"已定案：做"。本节按"避免过度设计"把它列入延后，**这意味着 v1 不做拼音搜索**。两个选择必须选一个：
> - **选 A（推荐）**：保留 `pinyin` 在 v1。成本极低（一个字符串字段），且不破坏已定案的搜索能力。
> - **选 B**：确认延后，**同时把 v0.2 §5.1、§3.5 的相关要求改为 v1.1**，否则验收时会出现"设计文档要求、实现没有"的冲突。
>
> **（2）第二层字段与 v0.2 §3.5 的关系。** `tags` / `summary` / `tip` / `exampleInput` / `keywords` / `order` / `emptyHint` / `errorHint` 在 v0.2 §3.5 与 `AGENT_RULES.md` §4.3 中均标记为 ✅ 必填。本节的"框架不强制"**只表示类型层面不设必填**，**不代表产品层面可以不写**。若要真正减少字段，需要同步修改那两份文档，**不要在这里单方面降低要求**。

### 为什么"分类只能有一个，标签可以有很多"

这正是设计评审 §3.4 双轨制的技术落地：

- **分类（1 个）** 承担"导航"职责——用户在**顶部搜索框的空关键词下拉**里看到 3 个分类入口，必须能立刻判断该点哪个，如果工具同时在两个分类里，这种判断就失效了。（此处是旧方案，当时分类以首页独立卡片行呈现；**当前实现以产品设计文档 v0.2 的 2026-10-03 修订为准**：分类入口只在顶部搜索下拉中出现，首页不再有独立分类卡片行。）
- **标签（多个）** 承担"检索"职责——搜"物理"能找到单位换算，搜"信息课"能找到进制转换，同一个工具可以被多个关键词命中。

**关键收益**：将来做"高中物理工具包"，只需要按 tag 过滤，**不需要重新分类、不需要改任何工具定义**。

## 3.4 界面模板：让 90% 的工具共用一个外壳

配置解决的是"数据和算法"，那界面怎么办？答案不是"每个工具写一个页面"，而是**归纳出几种固定的交互形状**。

### 本项目第一批工具的界面形状归纳

| 形状 | 交互模式 | 适用工具 | 模板 |
| --- | --- | --- | --- |
| **A · 文本变形** | 输入一段文本 → 点按钮 → 输出一段文本 | Base64、JSON 格式化 | `TextTransformTemplate` |
| **B · 数值换算** | 输入数值 + 选单位 → 实时/按钮 → 输出数值 | 进制转换 | `ValueConvertTemplate` |
| **C · 实时统计** | 边输入边显示统计结果，无"转换"按钮 | 字数统计 | `CounterTemplate` |
| **D · 实时预览** | 左边写 Markdown，右边实时渲染 | Markdown 预览 | `SplitPreviewTemplate` |
| **E · 自定义** | 交互复杂，无法套用模板 | 单位换算 | `UnitConvertUI`（放 `custom/`） |

**注意：只有 4 个模板 + 1 个自定义组件，覆盖全部 6 个工具。** 未来新增工具时，大概率也能落进这 4 种模板之一。

> ⚠️ 这里有一个容易搞错的地方：**单位换算不要硬塞进"数值换算"模板。** 它的交互（类别切换 + 两个下拉 + 交换按钮）比进制转换复杂得多，强行套模板会为了一个工具污染模板（`AGENT_RULES.md` §4.5 规则 4）。这一点与 v0.2 §5.3 的"单位换算 = 自定义"一致。

### 模板负责什么，工具定义负责什么

这个边界必须划清楚，否则模板会越改越乱：

```
模板（写一次，稳定）负责：
  ✓ 输入框/输出框的布局与样式
  ✓ 按钮的位置和禁用逻辑
  ✓ 复制按钮和复制成功反馈
  ✓ 空输入、错误状态的展示方式
  ✓ 键盘操作（Enter 提交、Esc 清空）
  ✓ 移动端如何堆叠
  ✓ 无障碍属性

工具定义（每个工具各写各的）负责：
  ✓ 输入框的 placeholder 文案
  ✓ 需要几个输入（进制转换需要"从几进制到几进制"两个下拉）
  ✓ 具体的计算规则
  ✓ 错误文案的具体措辞
```

**一句话：模板管"长什么样、怎么操作"，定义管"算什么、说什么"。**

### 什么时候允许打破模板

不能强迫所有工具都塞进模板，但也**不能一遇到不同就开新模板**。建议的判定流程：

```
新工具要上线
     ↓
能用现有 4 种模板吗？
     ├─ 能 → 直接用（大多数情况）
     └─ 不能 → 差异只有一个控件吗？
              ├─ 是 → 用模板的"插槽"塞进去（模板预留少量自定义区域）
              └─ 否 → 才新建模板或放到 components/tools/custom/
```

**判断标准**：如果这个差异**未来会有第三个工具也需要**，就把它提升为模板的能力；如果只有这一个工具需要，就放 `custom/`，不要污染模板。

> 举例：单位换算需要"类别切换（长度/质量/温度）+ 两个下拉 + 交换按钮"，比进制转换复杂。第一版可以放 `custom/`，等第二个类似工具出现时再抽象成模板。**过早抽象和过晚抽象一样有害。**

## 3.5 搜索：注册表的第二个消费者

搜索是本项目首页的最高优先级功能（设计评审 §5.1），它同样应该由注册表驱动，而不是单独维护一个关键词列表。

> **入口形态以 v0.2 的 2026-10-03 修订为准**：全站只有一个搜索框，位于顶部导航；关键词为空时下拉显示三个分类入口（转换工具 / 文本处理 / 开发辅助，链接到既有 `/categories/{slug}`），非空时才走下面的匹配逻辑。分类入口同样取自统一数据源，不在组件里另写分类名映射。旧方案中"Hero 搜索框 + 首页独立分类卡片"已作废。

### 搜索应该匹配哪些字段

```
用户输入 "jz"
   ├─ id 匹配        base-convert? 否
   ├─ name 匹配      "进制转换"? 否
   ├─ pinyin 匹配    "jz" ← 命中 ✓
   ├─ tags 匹配      "计算机"? 否
   └─ keywords 匹配  "进制"? 否
        ↓
   结果：进制转换
```

同理，输入"物理"能通过 tag 命中单位换算，输入"作文"能通过 tag 命名字数统计。

### 为什么搜索逻辑要写成纯函数

```
searchTools(query, tools) → 排序后的匹配结果
```

写成纯函数的好处：

- **可以单独测试**：给一组工具和查询词，断言返回什么，不需要打开浏览器
- **可以复用在多处**：顶部导航搜索下拉、`Cmd+K` 命令面板（v1.2 规划）、分类页内筛选，都用同一个函数
- **排序规则可替换**：第一版按"名称匹配 > 标签匹配 > 拼音匹配"排；将来接入使用数据后，把排序部分换掉即可，匹配部分不动

这一点呼应设计评审 §2.5 的"排序规则要预留函数位置"。

## 3.6 验收问题：新增 Base64 / JSON / 单位换算，到底要改什么？

这是本节的最终检验。用一张表回答"加了新工具，哪些文件动了、哪些没动"。

### 新增「Base64 转换」

| 要改的文件 | 改什么 | 工作量 |
| --- | --- | --- |
| `lib/tools/definitions/base64.ts` | **新建**：填元数据 + 写编码/解码纯函数 | 主体工作 |
| `lib/tools/definitions/index.ts` | 加一行导入 | 1 行 |
| `content/tips.ts` | 加一句小技巧 | 1 行（也可写在定义里，见下） |
| `tests/tools/base64.test.ts` | **新建**：边界用例 | 必做 |

| 不用改的文件 | 为什么不用改 |
| --- | --- |
| `app/tools/[toolId]/page.tsx` | 动态路由，自动为它生成 `/tools/base64` |
| 首页 | 工具列表从注册表读取，自动出现 |
| 分类页 | 同上 |
| `sitemap.ts` | 从注册表派生 |
| 搜索 | 从注册表构建索引 |
| `ToolCard`、`ToolLayout` 等组件 | 已有组件直接复用 |
| 导航、页脚、布局 | 与本工具无关 |

**结论：改 2 行 + 新增 2 个文件，页面零改动。**

### 新增「JSON 格式化」

| 要改的文件 | 说明 |
| --- | --- |
| `lib/tools/definitions/json-format.ts` | 新建。元数据 + 格式化函数（解析失败要给出**行号**，这是错误提示质量的关键） |
| `definitions/index.ts` | 加一行 |
| `tests/tools/json-format.test.ts` | 新建。重点测非法 JSON、超长 JSON、嵌套深度 |

界面用 `TextTransformTemplate`，**组件目录一个文件都不用碰**。

### 新增「单位换算」

这里有个额外的设计点值得说明。单位换算和前两个不一样，它是**数据驱动**的：

```
进制转换：算法驱动 —— 转换规则是"数学"，没有列表
  10 → 2：除以 2 取余

单位换算：数据驱动 —— 转换规则是"一张换算表"
  1 米  = 1        (基准单位)
  1 厘米 = 0.01     ← 新增一个单位 = 新增一行数据
  1 千米 = 1000
```

**这意味着**：以后要加"光年""海里""亩"，**不需要写任何新代码，只需要在换算表里加一行**。

所以单位换算的工具定义里应该包含一张"单位表"：

| 字段 | 说明 |
| --- | --- |
| `categories` | 单位类别。**v1 只做两类：长度、质量（重量）** |
| `units` | 每个单位的名称、符号、与基准单位的换算系数 |

**v1 的范围限制（重要）**

| 类别 | v1 | 原因 |
| --- | --- | --- |
| **长度** | ✅ 做 | 换算规则统一（纯系数乘法），无特例 |
| **质量（重量）** | ✅ 做 | 同上 |
| 温度 | ❌ 暂不做 | **带偏移的线性变换**（摄氏度 → 华氏度不是简单乘法），是唯一需要 `specialCases` 的类别，会显著增加复杂度 |
| 时间 | ❌ 暂不做 | 进位不是十进制（60 / 24 / 月 / 年），边界规则多 |
| 面积 | ❌ 暂不做 | 属于长度换算的平方延伸，收益低 |
| 体积 | ❌ 暂不做 | 同上 |

**为什么**：v1 的目标是**验证"数据表驱动的工具"这条架构路径**，而不是把单位换算做到最全。**先把最规则的 2 类做对，比 6 类都做一半更有价值。** 而正因为 v1 没有温度，单位换算的定义里**不需要 `specialCases` 分支**——这本身就是"避免过度设计"的一个具体体现（见第 7 节）。

> ⚠️ **一致性提示**：`WebsiteDesignDocument_v0.2.md` §3.2 的单位换算说明中包含"温度、面积"，§3.6 更明确要求"温度换算为特例，必须有独立测试"。本节按"避免过度设计"把它排出 v1 范围。**若要真正限制范围，需同步修改 v0.2 §3.2 与 §3.6**，否则验收时会出现"设计文档要求温度、技术文档没有"的冲突。

**这个例子教了一个通用原则**：

> 当"多样性"来自**数据**（有多少种单位），就用**数据表**吸收变化。
> 当"多样性"来自**逻辑**（每种编码算法不同），才用**代码**吸收变化。
>
> 判断错了，就会写出 200 个 `if` 分支。判断对了，工具系统就能一直保持轻。

界面方面：单位换算第一版放 `components/tools/custom/UnitConvertUI.tsx`，因为它的交互比通用模板复杂。

## 3.7 防止工具系统腐化：四条边界

框架最大的风险不是不够用，而是**被"就这一次"的需求慢慢侵蚀**，最后变回一堆 if。所以现在就把边界写下来：

| 边界 | 规则 | 违反的后果 |
| --- | --- | --- |
| **1. 注册表只增不改** | 工具定义文件之间**不能互相引用**；公共逻辑抽到 `lib/utils/` | 出现循环依赖，或改 A 工具弄坏 B 工具 |
| **2. `run` 必须纯净** | 纯函数，不读 localStorage、不发请求、不碰 DOM | 无法测试；同一个输入得到不同结果 |
| **3. 模板数量受控** | 模板总数控制在 **5 个以内**；新增模板要写明"未来哪个工具还会用它" | 变成"每个工具一个模板"，等于没有模板 |
| **4. 定义文件只声明，不实现界面** | 定义里最多写"用哪个模板/组件"，不写 JSX | 定义文件退化成组件文件，`lib/` 失去复用价值 |
| **(补充) 一位工具一个文件** | 不建 `all-tools.ts` 大文件 | 多人同时加工具必然冲突；找代码慢 |

### 加工具的"标准流程"（写进 `AGENT_RULES.md` 的那一条）

```
1. 在 lib/tools/definitions/ 新建 xxx.ts，填完整契约（A+B+C 组字段）
2. 在 definitions/index.ts 里加一行导入
3. 判断能否复用现有模板；不能则说明原因
4. 在 tests/tools/xxx.test.ts 写边界用例：
   空输入 / 非法字符 / 超长输入 / 极值（0、负数、超大数）
   / Unicode / 换行符 —— 至少 10 组
5. 运测试通过后，打开 /tools/xxx 检查：
   SEO 文案是否齐全、错误提示是否清晰、移动端是否可用、键盘是否可操作
6. 确认首页、分类页、sitemap 已自动出现该工具（如果没出现，说明注册表接错了）
```

**第 6 步是这套框架的"自检点"**：如果加完工具首页没自动出现，说明有人绕过注册表写了硬编码列表——这正是要立即发现并纠正的问题。

# 4. 用户数据设计

对应设计文档 §5.4「我的工具箱」：无账号、浏览器本地存储、保存收藏和最近使用。

## 4.1 LocalStorage 是什么

### 一句话定义

> 浏览器提供的一个**按网站隔离的、永久的、只能存字符串的小仓库**。

```js
localStorage.setItem('key', 'value')   // 存
localStorage.getItem('key')            // 取（不存在返回 null）
localStorage.removeItem('key')         // 删
```

### 关键特性（每一条都直接影响设计）

| 特性 | 含义 | 对本项目的影响 |
| --- | --- | --- |
| **只能存字符串** | 存对象必须先转成 JSON 文本 | 每次读写都要序列化/反序列化，要封装 |
| **同步 API** | 读写会阻塞主线程 | 数据量必须小；不能存大文本 |
| **容量约 5MB** | 每个域名共享 | 只存工具 id，**绝不存用户输入的内容** |
| **按域名隔离** | `localhost` 和线上域名是两份数据 | 开发时收藏的东西上线后看不到，属正常现象 |
| **永久保存** | 除非用户主动清除 | 这也是缺点：数据会"僵死"，需要版本管理 |
| **不跨设备** | 换手机/换电脑就没了 | 未来账号系统的动机（设计文档 §11） |
| **用户清缓存即丢失** | 设计评审 R4 已识别 | 所以必须把"弱钩子"用到极致（首屏"继续上次"） |
| **同源页面之间共享** | 同域名的多个标签页能互相看到 | 可以监听 `storage` 事件做跨标签页同步 |
| **在服务端不存在** | Node 环境里没有 `window` | ⚠️ **本项目最大的技术坑，见 4.5** |
| **隐私模式可能不可用** | 部分浏览器隐私模式下写入会抛错 | 所有操作必须包 try/catch |
| **明文存储** | 用户自己能在开发者工具里看到 | **不能存任何隐私信息** |

## 4.2 应该存什么，绝不存什么

| 数据 | 存不存 | 理由 |
| --- | --- | --- |
| 收藏的工具 id | ✅ 存 | 核心功能，数据量可忽略 |
| 最近使用的工具 id + 时间 | ✅ 存 | 核心功能 |
| 使用次数（用于排序） | ✅ 存 | 一个整数，成本极低，却是"推荐工具"排序的依据 |
| 偏好设置（如动效开关） | ✅ 存 | 未来用 |
| **用户输入的内容** | ❌ **绝不** | 进制转换的输入、JSON 的原文、Markdown 的草稿——这些可能有隐私（作文、个人信息），且体积大、易超限 |
| **转换结果** | ❌ **绝不** | 可由输入重新算出，存了纯属冗余 |
| 登录态、Token | ❌ | 第一阶段无账号 |
| 图片文件 | ❌ | 体积远超 5MB |

**这条边界要写进代码注释里**，因为"顺手把上次的输入也存下来吧，体验更好"是非常有诱惑力的错误决定。将来 v1.2 规划"历史记录（最近 20 次输入输出）"时，必须**单独设计**：独立 Key、单独开关、默认关闭、明确说明存在本地。

## 4.3 数据结构设计

### 命名空间与键名

一个浏览器里可能有很多网站，但**开发者工具里所有 Key 会混在一起显示**。所以要有统一前缀：

```
studenttool:favorites     收藏列表
studenttool:recent        最近使用
studenttool:prefs         偏好设置
studenttool:schema        （可选）版本号单独存
```

**规则**：`项目名 : 用途`，全小写，用冒号分隔。所有键名**写成常量**放在 `lib/storage/keys.ts`，代码里不许出现手写的字符串字面量——否则一个拼写错误会导致"数据写进去了却读不出来"这种极难排查的 bug。

> ⚠️ **一致性提示**：上面的 `studenttool` 只是**占位前缀**，不是定案值。
> 项目最终名称尚未确定（v0.2 附录 A 第 1 项），而 `AGENT_RULES.md` 附录 A 有一条明确红线：**"存储键名前缀依赖项目最终名称，在名称确定前不得随意指定。若必须先实现，使用一个常量集中定义，便于后续统一替换。"**
> 因此这里说的"写成常量"不是可选的风格问题，而是**红线要求**。下文出现的 `studenttool:user-data` 同理，全部经由同一个常量生成。

### 数据长什么样

**收藏（favorites）**：只需要一个 id 数组。

```
["unit-convert", "base-convert", "char-count"]
```

为什么不用对象数组？因为收藏的额外信息（名称、分类）**可以从工具注册表查到**。存 id 是"单一数据源"原则的延续：如果连名称也存一份，将来改名就会出现"首页叫进制转换、收藏页叫二进制转换"的不一致。

**最近使用（recent）**：需要 id + 时间，还需要次数（用于排序）。

```
[
  { id: "unit-convert", at: 1735689600000, count: 12 },
  { id: "char-count",   at: 1735603200000, count: 3  }
]
```

| 字段 | 作用 |
| --- | --- |
| `id` | 指向工具 |
| `at` | 时间戳。显示"3 天前"，也用于排序 |
| `count` | 累计使用次数。为设计评审 §2.5 的排序公式预留（收藏数×3 + 近 7 天使用×2 + 场景权重×1） |

**偏好（prefs）**：

```
{ "reduceMotion": false, "recentLimit": 12 }
```

### 版本号：现在不写，以后一定会后悔

**问题**：第一版存的是 `["unit-convert"]`（纯数组）。第二版想改成对象数组（带时间）。老用户浏览器里存的是旧格式，读的时候会直接崩。

**解决**：每个存储项都带一个版本号。两种写法：

| 写法 | 结构 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A · 单文档** | 一个 Key 里存所有数据的对象，带 `schemaVersion` | 版本管理简单、可整体导出/导入、一次写入保证一致 | 改一项要重写整个对象（本项目数据极小，无所谓） |
| **B · 分键 + 各自版本** | 每个 Key 独立带版本 | 写入粒度小 | 版本迁移逻辑分散，一致性难保证 |

**对本项目的推荐**：**A 单文档**。理由是数据量极小（几十个 id 而已），而"迁移逻辑集中在一处"的价值远大于"写入粒度"的收益。

```
Key: studenttool:user-data

{
  "schemaVersion": 1,
  "favorites": ["unit-convert", "char-count"],
  "recent": [
    { "id": "unit-convert", "at": 1735689600000, "count": 12 }
  ],
  "prefs": { "reduceMotion": false },
  "updatedAt": 1735689600000
}
```

设计评审 §5.1 明确要求"数据结构需带 `schemaVersion` 字段便于后续迁移"——就是这里。

### 迁移函数

读取时的流程：

```
读取字符串
   ↓
JSON.parse（失败 → 当作空数据，不报错、不白屏）
   ↓
看 schemaVersion
   ├─ 等于当前版本 → 直接用
   ├─ 小于当前版本 → 逐级迁移 v1→v2→v3，然后写回新格式
   └─ 大于当前版本（用户用过更新的版本）→ 保守处理：只读已知字段，不覆盖
```

**最后一种情况容易被忽略**：用户在公司电脑访存过新版网站，回家用旧版，旧版不能把新版数据清掉。

### 读取时必须做的一道校验

```
读出来的 id 在注册表里还存在吗？
   ├─ 存在 → 保留
   └─ 不存在（工具已下架）→ 丢弃
```

**为什么必须做**：假设 v1.1 淘汰了 Base64（设计评审 §6.2 提到"数据驱动淘汰"），用户的收藏里还留着 `base64`。如果不校验，收藏页会渲染一个点进去 404 的卡片。**这个校验就是"淘汰工具不会造成坏体验"的保障。**

## 4.4 收藏的读写时机

**写（点收藏）**：

```
1. 用户点收藏按钮
2. 更新内存中的状态（界面立刻变化，不等待存储）
3. 把新状态写入 LocalStorage
4. 如果写入失败（配额满 / 隐私模式）→ 回滚界面状态 + 提示"无法保存"
```

第 4 步很关键：**不能出现"界面显示已收藏，刷新后却没了"的情况**。这类"静默失败"最伤信任。

**读（页面加载）**：

```
❌ 错误做法：页面一渲染就读 localStorage
   → 服务端渲染时 window 不存在 → 直接报错

✅ 正确做法：分两步
   1. 服务端渲染时，收藏状态当作"未知"，显示中性状态（按钮不显示"已收藏"）
   2. 浏览器拿到页面、React 接管后（useEffect 阶段），再读 localStorage，
      把真实状态补上
```

## 4.5 最大的技术坑：服务端渲染与 LocalStorage 的冲突

这是本项目**最容易踩、且报错信息最难看懂**的一个坑，单独用一节讲。

### 坑是怎么形成的

```
Next.js 生成工具页 HTML（发生在服务器/构建时）
   ↓
服务器上没有 window，也没有 localStorage
   ↓
所以服务器只能渲染"默认状态"：未收藏
   ↓
浏览器拿到 HTML，先按"未收藏"画出界面（用户看到的第一帧）
   ↓
React 在浏览器里开始运行，读取 localStorage，发现"其实已收藏"
   ↓
React 想把它改成"已收藏"
   ↓
⚠️ 但 React 认为："服务器给我的 HTML 说我未收藏，现在我自己算出已收藏"
   → 两边对不上 → 报错：Hydration mismatch（水合不匹配）
```

**"Hydration（水合）"** 这个词的意思是：浏览器拿到的静态 HTML 是"干的"，React 运行时把事件和状态"注水"进去，让它变成活的。如果注入的内容和静态 HTML 不一致，React 就会警告甚至重建整个界面。

### 三种正确做法

| 做法 | 思路 | 适用 |
| --- | --- | --- |
| **A · 挂载后再读**（推荐） | 首次渲染一律用"空/未知"状态，等组件挂载后的副作用阶段再读存储并更新 | 本项目首选。简单、直观 |
| **B · 用 `useSyncExternalStore`** | React 官方为"外部数据源"提供的钩子，可以分别告诉 React"服务端快照是什么"和"客户端快照是什么" | 想让多个组件共享同一份存储状态时更好 |
| **C · 延迟到只用客户端渲染** | 让整个存储相关组件不参与服务端渲染 | 简单但会牺牲这部分内容的 SEO，本项目不推荐 |

### 用户能感觉到的差别

采用做法 A 时，用户体验是这样的：

```
0ms     页面出现，收藏图标是"空心"（中性状态）
   ↓
~50ms   变成"实心"（读取完成，确实是收藏过的）
```

这个瞬间变化是可以接受的，而且**比显示错误状态好得多**。降低它被察觉的方法：

- 中性状态不要显示成"未收藏"的文字提示，只显示图标
- 图标的变化可以有极短的过渡
- **绝对不要在加载期间显示"你还没有收藏任何工具"**——如果用户其实收藏了，这句话会一闪而过然后被替换，看起来像 bug

同理，"我的工具箱"页面在读取期间应该显示**骨架屏**，而不是"空状态"。

> **这条规则可以总结为一句话**：
> **"不知道"和"知道是空的"是两种不同的状态，界面必须能区分。**
> 这是本项目里所有跟 LocalStorage 交互的地方都要遵守的设计原则。

## 4.6 数据的生命周期管理

### 最近使用：去重 + 排序 + 上限

```
用户使用了"单位换算"
   ↓
列表里已经有 unit-convert？
   ├─ 有 → 把它移到最前面，count + 1，更新 at
   └─ 没有 → 插到最前面
   ↓
列表长度 > 上限？
   └─ 删除末尾（最久未用的）
```

**为什么必须有上限**：用户长期使用会积累几百条记录。虽然几十个 id 不算大，但：

- 首页"继续上次"只显示几条，多余数据没有价值
- 时间戳和计数字段会持续占用空间
- 每次读取都要序列化整个数组，无上限会拖慢

建议上限 **12–20 条**（设计评审提到"最近 20 次"，可以对齐）。

### 收藏：需不需要上限

理论上不需要（用户不可能收藏上万次）。但可以设一个软上限（如 200）用于防御异常数据。

### 数据清理的时机

| 时机 | 动作 |
| --- | --- |
| 每次读取时 | 丢弃注册表里已不存在的工具 id（见 4.3） |
| 每次写入时 | 应用上限截断 |
| 版本变化时 | 触发迁移 |
| 未来提供 | "清空我的数据"按钮（隐私友好，也降低"数据存在本地不放心"的心理门槛） |

## 4.7 封装：组件永远不直接碰 LocalStorage

这是本节最重要的工程建议。

### 反模式

```
❌ 在 15 个组件里各写一遍：
localStorage.getItem('studenttool:user-data')
JSON.parse(...)
try/catch ...
```

后果：

- 服务端渲染的坑要在 15 个地方各处理一遍，漏一个就报错
- 键名和数据结构变了，要改 15 个文件
- 无法统一处理写入失败
- 无法统一做跨标签页同步

### 推荐分层

```
┌─────────────────────────────────────────────┐
│ 组件（FavoriteButton / RecentTools / ...）   │
│ 只调用 useFavorites() 这样的钩子，            │
│ 完全不知道有 localStorage 这回事              │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│ hooks/  （React 适配层）                     │
│ useFavorites / useRecentTools                │
│ → 处理"挂载后再读"、订阅变化、跨标签页同步      │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│ lib/storage/user-data.ts （唯一出入口）       │
│ 提供语义化方法：                              │
│   getFavorites() / toggleFavorite(id)        │
│   getRecentTools() / recordUsage(id)         │
│   clearAll()                                 │
│ 内部处理：序列化、版本迁移、校验、容量上限、     │
│ 异常兜底、写入失败返回布尔值                    │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│ 浏览器 localStorage（或未来的云同步）          │
└─────────────────────────────────────────────┘
```

**这套结构带来的最大好处，正好对应设计文档 §11 的未来规划**：

> 将来做"登录后可同步"时，**只需要替换最底层**，把 `user-data.ts` 的实现从"读写 localStorage"换成"调用后端接口 + 本地缓存"。上面所有的 hooks 和组件**一行都不用改**。

这就是"设计好接口"比"写对代码"更重要的地方。

## 4.8 必须处理的边界情况清单

排查遗漏用的检查表，写代码时逐条对照：

| # | 情况 | 应该的表现 |
| --- | --- | --- |
| 1 | 服务端渲染时 | 绝不读取 localStorage（不检查 `window` 的代码一律视为 bug） |
| 2 | 首次访问，没有任何数据 | 返回默认值（空数组），不报错；界面显示角色空状态 |
| 3 | 存储里是损坏的 JSON | 捕获异常，当作空数据处理，并清掉坏数据 |
| 4 | 存储里是合法 JSON 但结构不对 | 逐字段校验，缺字段用默认值补齐 |
| 5 | 数据版本号比当前代码新 | 只读已知字段，不覆盖用户数据 |
| 6 | 收藏里有已下架的工具 id | 读取时静默丢弃 |
| 7 | 隐私模式 / 存储被禁用 | 所有功能仍然可用，只是收藏失效，并给出**明确但克制**的提示 |
| 8 | 配额写满 | 写入返回失败，界面回滚，提示用户 |
| 9 | 用户手动改了存储内容 | 同情况 3、4 |
| 10 | 同时打开多个标签页 | 监听 `storage` 事件，其他标签页的收藏变化能同步过来 |
| 11 | 用户清空浏览器数据 | 回到首次访问状态，不崩溃 |
| 12 | 在"我的工具箱"读取未完成时 | 显示骨架屏，**不是**空状态 |
| 13 | 搜索/浏览时 | 不产生任何写入（**只有真正使用工具或收藏才写入**） |

第 13 条容易被忽略：如果"打开工具页"就记为"最近使用"，那么用户误点进来也会留下记录，让"继续上次"变得不可信。**"打开"和"使用"要区分开**——建议条件是"产生了有效输出"或"点击了操作按钮"。

## 4.9 与设计评审 R4 的呼应

设计评审把"LocalStorage 收藏/最近使用是弱钩子、用户清缓存即丢失、无损失感"列为 ★★ 风险。技术上能做的缓解：

| 手段 | 说明 |
| --- | --- |
| 把弱钩子用到极致 | 首屏 Hero 区直接显示"继续上次：单位换算"，让回访用户 1 次点击离开首页（设计评审 §2.5 路径 C） |
| 收藏入口不要藏 | 收藏按钮紧邻工具操作区，不要放在页面角落 |
| 空状态要有引导 | 用角色 + 旁白式文案（"还没有收藏工具。"），而不是空白 |
| 明确告知数据在本地 | 在"我的工具箱"页用一行小字说明"数据保存在本机浏览器"，既诚实，也为未来"登录后同步"埋下期待 |
| **不做**损失制造 | 不要用"登录才能保存""数据可能丢失"之类的话术施压——与"打开就能用、不用注册"的核心定位冲突 |

# 5. 网站开发流程

这一节按初学者能理解的顺序，把"从零到上线"拆成 10 个阶段。每个阶段说明：**目标 / 产出 / 验收标准 / 学习重点**。

> 注意：**阶段的先后顺序不完全等于学习新技术的顺序**。学习顺序见第 8 节。
>
> **本章与第 6 节的分工**：本章逐个阶段解释"**为什么**要按这个顺序、这一阶段**学什么**"；第 6 节把同一件事压缩成 7 个**可交付的 Phase**，用于实际排期与拆分任务。两者不冲突，映射表见 §6.0。

## 阶段 0 · 规范与共识（1–2 天）

**目标**：在写第一行代码之前，把"不能违反的事"写下来。

**为什么需要**：所有技术决策后面都会遇到"要不要破例"的诱惑。提前写下边界，破例就需要理由。

**产出**：

- ✅ `AGENT_RULES.md` —— **已建立（v1.0）**。它解决了 `WorkBuddy_Design_Review.md` §7 第 8 条指出、v0.2 附录 A 第 2 项记录的"约束链断裂"问题
- 明确剩余待决事项：项目名称、视觉 token 色值、Markdown 渲染库选型（见本文档 §10.3）

**验收**：`AGENT_RULES.md` 已包含：技术栈、目录规范、加工具的标准流程、三条红线（角色不挡路 / 不做会说话的助手 / 6 个工具零缺陷）。

**学习重点**：不是所有问题都能靠写代码解决；**文档是工程的第一个交付物**。

## 阶段 1 · 设计定型（2–4 天）

**目标**：把设计文档里的建议收敛成可执行的设计规范。

**产出**：

- 色彩 token 表（主色 1 + 辅色 2-3 + 中性灰阶 6-8）
- 字号阶梯（6 档）
- 圆角、阴影、间距规范
- 响应式断点（<768 / 768-1279 / ≥1280）
- 分类最终定案（**v0.2 §3.1 已定案**：转换工具 / 文本处理 / 开发辅助）
- 6 个工具的配置表（id、名称、分类、标签、说明、小技巧、示例输入）

**验收**：任意一个工具卡片，能按规范说出它的所有样式数值来源。

**学习重点**：**设计规范的价值在于"数值有唯一来源"**。这与第 1.4 节 Tailwind 的主题配置直接对应。

> 这一阶段还不碰代码，但它决定了后面所有代码长什么样。设计评审 §3 的分类问题如果拖到编码阶段才改，代价会大十倍。

## 阶段 2 · 环境搭建（半天）

**目标**：让一台电脑能跑起一个空白的 Next.js 项目。

**要做的事**：

1. 安装 Node.js（Next.js 的运行环境）
2. 创建 Next.js 项目骨架
3. 装上 Tailwind 和代码检查工具
4. 打开 `http://localhost:3000` 看到默认页面

**产出**：一个能启动、能自动刷新（改代码后浏览器自动更新）的空项目。

**验收**：改一行文字，浏览器自动变化。

**学习重点**：

- `package.json` 是什么（项目依赖清单）
- `npm install` / `npm run dev` / `npm run build` 分别做什么
- `node_modules` 为什么不该提交到 Git
- **`.gitignore` 必须在第一次提交前就配好**

> 这一阶段最常见的挫败是环境问题。把它单独作为一个阶段，是因为它和业务逻辑完全无关，不该混在一起。

## 阶段 3 · 骨架与设计系统（3–5 天）

**目标**：搭出"空壳网站"——所有页面都在，但工具还没实现。

**产出**：

- `app/layout.tsx`：顶栏（Logo + **全站唯一搜索框**占位 + 我的工具箱）+ 页脚
- 设计 token 落地（Tailwind 主题或 CSS 变量），亮/暗两套
- `components/ui/` 的基础零件：Button、Card、Input、Textarea、Select、CopyButton
- 404 页、空状态组件
- 响应式布局能在手机宽度下正常堆叠

**验收**：

- 用手机打开，顶栏不挤压、按钮不小于 44×44px
- 切换系统深色模式，页面颜色正确跟随
- 正文对比度达到 WCAG AA（可用浏览器开发者工具检查）

**学习重点**：

- React 组件、props、组合（第 1.3 节）
- Tailwind 的类名体系与设计 token 的对应关系（第 1.4 节）
- **服务端组件 vs 客户端组件的分界**（这一阶段不涉及交互，故意全部用服务端组件，先建立"默认不做客户端组件"的习惯）

> 为什么要先做设计系统再做工具？因为工具页要**大量复用** Button、Input、CopyButton。如果先做工具，会写出 6 套不同的按钮，后面返工的成本很高。

## 阶段 4 · 工具系统内核（5–7 天）★ 最关键

**目标**：建立注册表和工具页动态路由，让"加工具"这件事变成加文件。

**产出**：

- `lib/tools/types.ts`：工具契约（3.3 节的字段）
- `lib/tools/registry.ts`：注册表 + 查询函数
- `lib/tools/definitions/`：**先放 1 个最简单的工具**（建议整数字节数统计或最简单的进制转换）
- `app/tools/[toolId]/page.tsx`：动态路由 + `generateStaticParams` + `generateMetadata`
- `components/tools/`：ToolCard、ToolLayout、ToolHeader、ToolTip
- `components/tools/templates/`：**先只做 1 个模板**，够当前这个工具用即可
- `tests/`：第一个算法的边界用例

**验收（这是整个项目的技术里程碑）**：

- 访问 `/tools/<刚做的工具>` 能正常使用
- 在 `definitions/` 里加**第二个**工具定义 + 在 index 里加一行 → **不改任何页面文件**，首页和路由自动出现它
- 查看页面源代码（不是开发者工具的元素面板，而是"查看网页源代码"），能看到工具的标题和说明文字 → **SEO 生效的证明**

**学习重点**：

- **单一数据源**：为什么注册表比手动维护列表好
- **纯函数**：为什么算法要和 React 分开，怎么用测试验证
- **数据驱动路由**：文件路由 + 参数生成 + 元数据生成三者如何配合
- Next.js 的静态生成（SSG）究竟生成了什么

> **这一阶段是整个项目成败的分水岭。** 如果这里做对了，剩下 5 个工具都是重复劳动；如果这里敷衍过去，后面每加一个工具都是痛苦。设计文档 §10.1 的模块化原则，具体就落在这一阶段。

## 阶段 5 · 六个工具的实现（7–12 天）

**目标**：把 6 个工具按优先级做完，每个做到零缺陷。

**顺序**（按 v0.2 §3.2 的优先级，同时考虑"先易后难"建立节奏）：

| 顺序 | 工具 | 模板 | 难点 |
| --- | --- | --- | --- |
| 1 | 字数统计 | CounterTemplate | 简单，用于验证模板机制（注意：中英文混排、标点、换行怎么算） |
| 2 | 进制转换 | ValueConvertTemplate | 大数精度、非法字符、负数、小数 |
| 3 | Base64 | TextTransformTemplate | **Unicode 字符**（中文、Emoji）编码容易出错 |
| 4 | JSON 格式化 | TextTransformTemplate | 错误提示要给出**行号**和原因 |
| 5 | 单位换算 | 自定义 UI | 单位表设计（**v1 只做长度与质量，见第 6、7 节**） |
| 6 | Markdown 预览 | SplitPreviewTemplate | 需要引入 Markdown 解析库；**XSS 安全**（用户输入可能含脚本） |

> **实际排期以第 6 节为准**：字数统计单独作为 Phase 3（用于验证整条链路），单位换算与进制转换合并为 Phase 4。本表列出的是**难度递增**的顺序，用于理解"为什么先易后难"。

**每个工具的固定动作**：

```
1. 写定义文件（契约 + 纯函数）
2. 写测试：至少 10 组边界用例
3. 接界面：优先复用模板
4. 自测：空输入 / 非法输入 / 超长输入 / 移动端 / 键盘操作
5. 检查 SEO 文案是否齐全
```

**验收**（对应 v0.2 §3.6 的零缺陷标准、`AGENT_RULES.md` §4.4 的边界用例清单）：

| 维度 | 标准 |
| --- | --- |
| 输入容错 | 空、超长、非法字符、纯空格、带换行 —— 全部有明确提示，不白屏 |
| 错误提示 | 说清"哪里错了 + 怎么改"，不卖萌、不显示原始异常 |
| 结果准确性 | 每个工具 10 组以上边界用例通过 |
| 示例数据 | 每个工具有"试试示例" |
| 键盘 | Tab 顺序合理、Enter 可操作、Esc 可清空 |
| 移动端 | 真机验证输入法弹出不遮挡输入框 |

**学习重点**：

- 边界思维：**工具站的信誉建立在"错一次就再也不来"上**（设计评审 §5.4）
- 什么时候该引入第三方库（Markdown 解析），什么时候该自己写（进制转换）——判断标准是"这个东西的复杂度是否值得信任一个成熟库"
- 安全性：Markdown 渲染是唯一可能被注入脚本的地方

## 阶段 6 · 用户数据：收藏与最近使用（3–4 天）

**目标**：实现设计文档 §5.4 的"我的工具箱"。

**产出**：

- `lib/storage/keys.ts`、`schema.ts`、`migrate.ts`、`user-data.ts`
- `hooks/useFavorites.ts`、`hooks/useRecentTools.ts`
- `components/tools/FavoriteButton.tsx`
- `app/my-toolbox/page.tsx`（收藏区 + 最近使用区）
- 首页的"继续上次"入口

**验收**（逐条对应 4.8 的清单）：

- 刷新页面后收藏状态保持
- **服务端渲染不报错**（这是本阶段的头号验收项）
- "我的工具箱"打开时不闪"空状态"
- 手动把 LocalStorage 内容改坏 → 页面不崩，自动恢复
- 收藏一个不存在的工具 id → 被静默丢弃
- 开两个标签页，一个收藏，另一个能同步
- 隐私模式下功能仍然可用
- **检查：LocalStorage 里没有任何用户输入的内容**

**学习重点**：

- React 的副作用（组件挂载后执行一次）
- 服务端渲染与浏览器 API 的边界（第 4.5 节）
- "未知" 与 "空" 的区别如何反映到界面上
- 为什么封装比省事重要（第 4.7 节）

> 这一阶段最容易出的 bug 不是逻辑错，而是**时序错**（读得太早、写得太晚）。建议把 4.5 节的图和 4.8 节的清单打印出来贴在旁边。

## 阶段 7 · 首页与搜索（4–6 天）

**目标**：让用户以最少的交互到达工具页（v0.2 §5.1）。

**产出**：

- 顶栏搜索：**全站唯一搜索框**，**即时匹配下拉**，支持名称、标签、关键词、拼音首字母
- 空关键词下拉：**转换工具 / 文本处理 / 开发辅助**三个分类入口，进入既有 `/categories/{slug}`
- Hero 区（**仅 slogan + 角色**，无搜索框、无搜索提示、无分类入口）
- 常用工具区（第一版按预设顺序，代码里预留排序函数）
- 我的工具箱预览 + "继续上次"
- 角色资源接入（标准 / 空状态 / 成功 / 错误四个状态）

> **此处是旧方案，当前实现以产品设计文档 v0.2 的 2026-10-03 修订为准。** 本节原有"Hero 区（slogan + 搜索框 + 角色）"与"分类入口（3 个卡片）"两项已作废：分类入口不再占首页独立一行，而是顶部搜索空关键词下拉中的一部分；Hero 不再有第二个搜索框。

**验收**：

- 输入"进"就能看到"进制转换"，不需要回车、不跳页
- 聚焦空的顶部搜索框时，下拉只显示三个分类入口且顺序正确，进入的是既有分类页
- 清空关键词恢复分类入口；纯空格视为空；失焦或 Esc 收起，Esc 不清空关键词
- 1366×768 分辨率下，顶栏搜索框无需滚动就能看到；展开后三个分类入口无需滚动页面即可见
- 角色不遮挡搜索框，工具操作区周围 0 个装饰元素（设计评审 §4.3 红线）
- 回访用户 1 次点击离开首页

**学习重点**：

- 客户端组件在这里正式登场（搜索需要键盘交互和状态）
- **列表渲染与 key**：搜索结果列表为什么要用工具 id 作为 key
- 排序：为什么第一版不自己做推荐算法，而是留好函数的"插槽"
- 动画的克制：单个动画 ≤300ms，支持 `prefers-reduced-motion`

## 阶段 8 · 质量与响应式收尾（3–5 天）

**目标**：把"能跑"变成"可靠"。

**产出**：

- 三档断点（<768 / 768-1279 / ≥1280）全部检查通过
- 键盘可达性：Tab 顺序、焦点可见
- 无障碍：语义化标签、图标有 `aria-label`
- 性能：首屏 LCP < 2s（4G 网络模拟）
- 浏览器兼容性检查

**验收**：用浏览器开发者工具依次跑一遍 Lighthouse（性能/无障碍/最佳实践/SEO 四项），逐项处理问题。

**学习重点**：

- **无障碍不是一个额外任务，它是"键盘用户能不能用"的可用性底线**
- 性能问题的常见来源：图片没优化、引入了不必要的第三方库、客户端组件用得太靠上

## 阶段 9 · SEO、部署与上线（2–3 天）

**目标**：让搜索引擎能收录，让用户能访问。

**产出**：

- 每个工具页：独立 URL、含中文关键词的 H1、description、FAQ 结构化数据（设计评审 R7）
- `sitemap.ts`（从注册表自动生成）、`robots.ts`
- Open Graph 分享图
- 部署到托管平台
- 自定义域名 + HTTPS

**验收**：

- "查看网页源代码"能看到工具页的标题和说明文字（不是空壳）
- 用搜索引擎的"网址检查"工具提交一个工具页，能被正常抓取
- 手机浏览器访问线上地址，功能正常

**学习重点**：

- **Next.js 的 SEO 优势不会自动生效**，必须靠"独立 URL + 中文关键词 + 说明文案 + 结构化数据"兑现（设计评审 R7）
- 构建（build）与开发模式（dev）的区别：构建产物才是真正上线的东西，构建时的报错在开发模式里可能看不到

## 阶段 10 · 上线后迭代（长期）

**目标**：用真实数据决定下一步做什么，而不是拍脑袋。

**要做的事**（对应设计评审 §8）：

- 自建轻量埋点：统计工具使用频次（**不引入第三方追踪 SDK**）
- 观察 8 个指标，重点看 **7 日回访率** 和 **首页→工具页转化率**
- 用数据驱动工具淘汰与优化，而不是靠感觉加功能

**v1.1 候选**（设计评审 §6.2）：化学式/摩尔质量、方程求解、日期计算、二维码生成、图片压缩。

**学习重点**：

- **产品判断**：如果转化率高但回访率低，说明"好用但没记住的理由"——解法是强化归属感，不是加工具
- 埋点也应该遵守"最小必要"原则，学生向产品尤其要克制

## 5.11 学习顺序建议（与开发顺序不同）

上面是**做项目的顺序**，下面是**学技术的顺序**。如果你是初学者，不要把两者混在一起：

| 步骤 | 学什么 | 学到什么程度就够开始动手 | 对应本项目 |
| --- | --- | --- | --- |
| 1 | HTML 基础 | 知道 div、input、button、h1 是什么 | 阶段 3 |
| 2 | CSS 基础 | 知道盒模型、flex 布局、响应式大概怎么回事 | 阶段 3 |
| 3 | JavaScript 基础 | 函数、数组的 map/filter、对象、try/catch、JSON | 阶段 4 |
| 4 | React 基础 | 组件、props、state、列表渲染、事件处理 | 阶段 3–5 |
| 5 | Tailwind | 类名规律，不用背全 | 阶段 3 |
| 6 | Next.js | 文件路由、服务端/客户端组件、静态生成 | 阶段 4 |
| 7 | 测试 | 会写"输入 A 期望输出 B"就够了 | 阶段 5 |

**建议的学习方式**：不要"先学完再做"。更有效的是——

```
学一点 React → 在阶段 3 做几个静态卡片
   ↓
发现需要状态 → 回去学 state → 应用到阶段 5 的字数统计
   ↓
发现需要读存储 → 学 useEffect → 应用到阶段 6
```

**带着具体问题去学，比按教程顺序学完再动手，效率高得多。**

# 6. 开发实施建议

> 本章是第 5 节的**排期视图**。第 5 节逐个阶段解释"为什么要按这个顺序、这一阶段学什么"；本章把同一件事压缩成 **7 个可交付的 Phase**，用于实际排期、拆分任务、以及交给开发 Agent 分次执行。

## 6.0 与第 5 节的对应关系

| 本章 Phase | 内容 | 对应第 5 节阶段 | 可否独立交付 |
| --- | --- | --- | --- |
| **Phase 0** | 项目初始化 | 阶段 2 | ✅ |
| **Phase 1** | 基础网站框架 | 阶段 1 + 阶段 3 | ✅ |
| **Phase 2** | 工具系统核心 | 阶段 4 | ✅ |
| **Phase 3** | 第一个工具（字数统计） | 阶段 5（第 1 个） | ✅ |
| **Phase 4** | 第一批工具（单位换算、进制转换） | 阶段 5（第 2、3 个） | ✅ |
| **Phase 5** | 用户体验功能（收藏、最近使用、LocalStorage） | 阶段 6 | ✅ |
| **Phase 6** | 优化（SEO、sitemap、移动端、性能） | 阶段 7–9 | ✅ |

**差异说明**：第 5 节的"阶段 7（首页与搜索）"在本章被拆入 Phase 1（骨架）与 Phase 6（优化）。这不是顺序变化，而是**同一件事的两种切分方式**——按阶段切方便理解，按 Phase 切方便交付。**执行时以本章的 Phase 作为任务边界，以第 5 节的说明作为学习参考。**

**硬性依赖**：**Phase 2 必须在 Phase 3 之前完成。禁止在工具系统内核未完成前，用"一个工具一个页面"的方式先做工具**（`AGENT_RULES.md` §9.3）。

## 6.1 Phase 0 · 项目初始化

**目标**：让一台电脑能跑起一个空白的、配置正确的 Next.js 项目。

**内容**

| # | 要做的事 | 关键点 |

## 6.5 Phase 4 · 第一批工具：单位换算、进制转换

**为什么这两个放在一起**

| 工具 | 为什么现在做 | 新增的架构压力 |
| --- | --- | --- |
| **单位换算** | P0 刚需；**数据驱动**的代表 | 首次需要"单位表"这种数据表形态；首次需要自定义界面 |
| **进制转换** | P0 刚需；"数值换算"模板的第二个用户 | 首次需要大数精度处理与非法字符提示 |

**单位换算的 v1 范围限制（重要）**

**第一版只实现：长度、质量（重量）两类。**

| 类别 | v1 | 原因 |
| --- | --- | --- |
| **长度** | ✅ 做 | 换算规则统一（纯系数乘法），无特例 |
| **质量（重量）** | ✅ 做 | 同上 |
| 温度 | ❌ 暂不做 | **带偏移的线性变换**，是唯一需要 `specialCases` 的类别，会显著增加复杂度 |
| 时间 | ❌ 暂不做 | 进位不是十进制，边界规则多 |
| 面积 | ❌ 暂不做 | 属于长度换算的平方延伸，收益低 |
| 体积 | ❌ 暂不做 | 同上 |

**原因**：v1 的目标是**验证"数据表驱动的工具"这条架构路径**，而不是把单位换算做到最全。**先把最规则的 2 类做对，比 6 类都做一半更有价值。** 因为 v1 不含温度，单位换算的定义里也**不需要 `specialCases` 分支**——这就是"避免过度设计"的一个具体落地（见第 7 节）。

> ⚠️ **一致性提示**：v0.2 §3.2 的单位换算说明含"温度、面积"，§3.6 更要求"温度换算为特例，必须有独立测试"。**若要真正限制范围，需同步修改 v0.2 的这两处**，否则验收时会出现冲突。

**交付物**：`unit-convert`（长度 + 质量）、`base-convert` 两个完整工具。

**出口条件**

- [ ] 单位换算：**加一个新单位 = 加一行数据，不改代码**
- [ ] 单位换算：定义里不出现 `specialCases` 之类的特例分支
- [ ] 进制转换：大数不因浮点溢出出错；负数、非法字符有明确提示
- [ ] 两个工具各 ≥10 组边界用例通过
- [ ] **单位换算使用自定义界面，未污染通用模板**（模板总数仍 ≤ 5）

# 7. 第一版避免过度设计

## 7.1 为什么必须单独写这一章

本文档前面多次提到"未来支持 PWA / App / 用户系统"。这些话是**方向的说明**，不是**第一版的待办事项**。

现实中最常见的失败模式，不是"技术做不出来"，而是：

> 为了一个**将来可能用到**的能力，在**现在**引入了一大堆**当前用不上**的复杂度。
> 结果要么第一版迟迟做不完，要么做完了但没人用。

本章的作用，就是把"未来"和"现在"划一条硬线。

## 7.2 未来能力 ≠ 现在实现

| 未来能力 | 第一版是否实现 | 第一版只需预留什么 |
| --- | --- | --- |
| 更多工具（12–15 个） | ❌ 不实现（v1 严格 6 个） | 注册表 + 模板机制（Phase 2） |
| PWA / 离线 | ❌ 不实现 | 算法与界面解耦（`src/lib` 不依赖 React） |
| 手机 App | ❌ 不实现 | 同上，算法可被直接复用 |
| 用户账号 / 云同步 | ❌ 不实现 | 存储读写接口独立于实现（§4.7） |
| 商业化（皮肤、赞助） | ❌ 不实现 | 色彩已 token 化（§1.4） |
| 数据驱动的工具淘汰 | ❌ 不实现 | 最近使用记录里保留 `count` 字段（§4.3） |

**关键区别**：

- **预留 = 把接口和边界划好，不写实现。** 成本几乎为零。
- **实现 = 真的写代码。** 每一个都要花时间、引入风险、增加长期维护面。

**第一版只做"预留"。**

## 7.3 第一版明确不实现

| 不实现 | 为什么现在做是错的 |
| --- | --- |
| **登录系统** | 违背"打开就能用、不用注册"的核心价值主张（v0.2 §1.5），🔴 `AGENT_RULES.md` §2.2 红线。**包括"只做一个登录按钮占位"也不允许**（§9.2 明确） |
| **云数据库** | 引入后端即引入部署、成本、隐私、合规问题；v1 数据全在浏览器（第 4 节）。🔴 `AGENT_RULES.md` §3.1 禁止引入后端服务或数据库 |
| **后端服务 / 接口 / 云函数 / BaaS** | 同上。本项目所有计算都是纯前端可以完成的 |
| **复杂权限系统** | 没有账号就没有权限。为不存在的账号设计权限体系，是纯粹的空转 |
| **复杂插件系统** | 见 §7.4 —— 这是本章最容易搞错的一条 |

## 7.4 特别说明：注册表 ≠ 插件系统

因为名字里都带"扩展"的意味，这两件事经常被混为一谈。它们完全不同：

| 维度 | 插件系统 | 本项目的工具注册表 |
| --- | --- | --- |
| **加载时机** | **运行时**动态加载 | **编译期**静态导入 |
| **来源** | 可能来自外部、第三方 | 只来自项目自己的定义文件 |
| **生命周期** | 需要安装、启用、禁用、卸载 | 只有"存在"和"被导入" |
| **依赖管理** | 需要依赖注入、版本协商 | 不需要；工具之间**禁止互相引用** |
| **隔离 / 权限** | 需要沙箱与权限模型 | 不需要，都是同一份代码 |
| **复杂度** | 高 | **低** |
| **本项目需要吗** | ❌ **不需要** | ✅ **这就是我们要的** |

**判断标准**：

> 如果新增一个工具，需要"打包成独立产物、运行时动态加载进来、还可能卸载"——那是**插件系统**。
> 如果新增一个工具只是"加一个 `.ts` 文件、在聚合入口加一行导入、重新构建"——那是**注册表**。

**本项目要的是注册表。** 它已经足以满足 v0.2 §2.4 的"加工具不改页面"，而复杂度低一个数量级。

> 🔴 **第一版禁止引入任何动态加载 / 插件运行时 / 可插拔配置格式的机制。**
> 一旦引入，就意味着"每个工具都要遵守一套运行时协议"，而这套协议在第一版没有任何真实需求去校准它，几乎必然会设计错。

## 7.5 判断自己是否正在过度设计

出现以下任一信号，说明已经在过度设计，**应当停下来并报告**：

| 信号 | 说明 |
| --- | --- |
| 在为一个**还没有第二个使用者**的需求做抽象 | 例如只有一个工具时就开始设计"模板插槽系统" |
| 写的代码**当前没有任何调用方** | "先写好，以后肯定用得上"——通常永远用不上 |
| 引入了一个库，但只用了它 5% 的能力 | 违背 `AGENT_RULES.md` §3.4 |
| 开始设计"配置的格式"，而不是"配置的内容" | 例如为工具定义设计一套可插拔的元数据 schema |
| 第一版还没跑通，就在写迁移脚本和版本兼容层 | 迁移脚本应当在**第二次改数据结构时**才写（但 `schemaVersion` 字段要一开始就有） |
| 为了"未来的 App"现在就把算法抽成独立包、发布到私有源 | 只要 `src/lib` 不依赖 React 就已经够了 |
| 在讨论"工具之间怎么互相调用" | 第一版工具之间**禁止互相引用**（§3.7 边界 1） |
| 把常用字段全部设为必填以求"完备" | 会让新增工具的成本变高；见 §3.3 的分层契约 |

**反过来的信号**（说明此刻**该补的还没补**）：

| 信号 |
| --- |
| 加一个工具要改 3 个以上的既有文件 |
| 首页的工具列表是手写的数组 |
| 组件的显示结果与实际算法结果不一致 |
| 没有任何测试，只能靠点页面来验证工具对不对 |

## 7.6 第一版的核心目标只有一条

> **把 6 个工具做到零缺陷。**

其他一切都服从这一条：

| 方面 | 取舍 |
| --- | --- |
| **架构** | 够用就好——**能自动加工具、能自动生成路由，就够了**，不需要"可插拔" |
| **功能** | 能少则少——**少一个功能，多一分工具质量** |
| **数据** | 够用就好——**收藏 + 最近使用**就足以支撑回访 |
| **视觉** | 保持克制——**角色在场，但从不挡路** |

## 7.7 本节的落地检查

交付任何 Phase 之前，先回答四个问题：

1. 我写的这段代码，**现在**有调用方吗？
2. 它是在**解决一个已经出现的问题**，还是在**预防一个想象中的问题**？
3. 如果删掉它，第一版还能交付吗？如果能 → 考虑删掉。
4. 它是否让"6 个工具零缺陷"这个目标更远了？

**第 3 个问题的答案如果是"能"，这段代码大概率不该现在写。**

# 8. 推荐学习与开发顺序

本章回答一个具体问题：**如果我是初学者，应该按什么顺序学、按什么顺序做，以及为什么是这个顺序。**

## 8.1 七步顺序

| # | 步骤 | 为什么在这个位置 |
| --- | --- | --- |
| 1 | **理解 React 组件** | 整个网站的界面都由组件拼成。不先理解"组件 = 返回界面的函数"和"props 从上往下传"，后面每一步都会看得云里雾里 |
| 2 | **理解 Next.js 页面结构** | 有了组件概念之后，紧接着要理解"文件即路由"和"服务端组件 / 客户端组件"。**这一步决定了你后面会不会写出 SEO 失效的页面** |
| 3 | **创建基础网站** | 第一次动手。目标是拿到一个"能跑起来的空壳"，把第 1、2 步的知识用在真实文件上。此时**不碰任何工具逻辑** |
| 4 | **创建工具注册表** | 全项目最重要的一个概念。**必须在做第一个工具之前完成**——反过来做（先写工具页面、再回头抽注册表）几乎一定会失败 |
| 5 | **制作第一个工具** | 选最简单的**字数统计**，目的是**验证整条链路是通的**：注册表 → 工具页面 → 组件模板 → 用户交互。这一步的价值不在工具本身，而在"证明地基没问题" |
| 6 | **抽象工具模板** | ⚠️ 注意顺序：**不是先设计模板，而是做完第一个工具之后再抽象**。有了一个真实例子，你才知道哪些部分真的重复。**过早抽象和过晚抽象一样有害** |
| 7 | **增加收藏系统** | 放在最后，因为它引入的是**完全不同的一类问题**：浏览器 API、服务端渲染冲突、数据版本管理。这些问题会掩盖前六步的错误，因此不适合更早做 |

## 8.2 为什么是"这个"顺序（三条理由）

**理由一：先建立心智模型，再动手写代码。**

第 1、2 步不是浪费时间。没有组件和页面结构的概念，第 3 步就只能是"照着教程抄"，抄完什么也没学到。

**理由二：把"最容易返工的决定"尽可能提前。**

| 决定 | 如果做晚了 |
| --- | --- |
| 注册表 | 已经写了 3 个工具页面，抽注册表 = 重写 |
| 服务端 / 客户端组件边界 | 整页都是客户端组件，SEO 已经失效，回头改要动所有页面 |
| 分层（`src/lib` 不依赖 React） | 算法混在组件里，测试和复用都无从谈起 |

**理由三：把"最难调试的问题"放到最后。**

第 7 步的 LocalStorage 会引入**时序问题**（读得太早、写得太晚）和水合不匹配。如果这时前面还留着架构错误，你会同时面对两类 bug，**根本分不清是哪一层的问题**。

## 8.3 每一步"学会的标志"

光"做完了"不等于"学会了"。用下面的自检：

| # | 步骤 | 学会的标志（能自己回答这些问题） |
| --- | --- | --- |
| 1 | React 组件 | 能说清 props 和 state 的区别；能解释为什么数据要"从上往下流" |
| 2 | Next.js 页面结构 | 能说清哪些内容必须在服务端生成、为什么；能判断一个组件该不该加 `'use client'` |
| 3 | 基础网站 | 能不看教程新建一个页面；知道改了哪个文件、为什么会生效 |
| 4 | 工具注册表 | 能说清"加一个工具要改哪几个文件"；能解释为什么首页不需要手写工具列表 |
| 5 | 第一个工具 | 能说清一次输入经过了哪几层；能自己写出一组边界用例 |
| 6 | 工具模板 | 能判断一个新工具的差异"该进模板还是该放自定义组件" |
| 7 | 收藏系统 | 能解释为什么不能在渲染期间读 LocalStorage；能说清"未知"和"空"的区别 |

## 8.4 常见错误顺序

| 错误顺序 | 会发生什么 |
| --- | --- |
| 先学完所有技术再动手 | 学到一半就忘了，且没有目标感。**应该带着具体问题去学** |
| 先做工具页面，后抽注册表 | 每个工具一个页面，加第 4 个工具时彻底失控 |
| 先设计模板，再做工具 | 设计出的模板大概率不匹配真实需求，还要重做 |
| 先做收藏系统，再做工具 | 没有工具可收藏；而且存储的时序 bug 会与工具 bug 缠在一起 |
| 先做视觉和角色，后做工具 | 网站会很漂亮，但没有可用的工具——**违背"工具优先"** |
| 用"学习顺序"代替"开发顺序" | 见 §8.5 |

## 8.5 学习顺序 ≠ 开发顺序

§5.11 的学习顺序建议讲的是**学技术**的顺序；本章讲的是**做项目**的顺序。两者不同，不要混：

| | 学习顺序（§5.11） | 开发顺序（本章） |
| --- | --- | --- |
| **起点** | HTML / CSS / JS 基础 | React 组件（假设基础已具备） |
| **特点** | 由浅入深，按技术依赖展开 | 按"返工成本"排序 |
| **目的** | 建立能力 | 降低风险 |
| **建议** | 学到"够用"就开始动手，边做边补 | 严格按 §8.1 的七步，不跳步 |

**推荐的结合方式**：

```
学一点 React → 做第 3 步（基础网站）
      ↓ 遇到问题
回去补状态管理与副作用 → 做第 4、5 步
      ↓ 遇到问题
回去补浏览器 API → 做第 6、7 步
```

**带着具体问题去学，比按教程顺序学完再动手，效率高得多。**

# 9. 名词速查表

| 名词 | 一句话解释 | 在本项目里什么时候遇到 |
| --- | --- | --- |
| **React** | 把界面拆成组件、数据变了界面自动更新的库 | 全程 |
| **Next.js** | 在 React 之上提供路由、渲染、优化的框架 | 全程 |
| **组件** | 一个返回界面描述的函数 | 阶段 3 起 |
| **props** | 从父组件传进来的、组件自己不能改的数据 | `ToolCard` 接收工具信息 |
| **state** | 组件自己内部会变的数据 | 输入框内容、搜索结果 |
| **App Router** | Next.js 用 `app/` 目录表示网址的路由系统 | 阶段 3 |
| **Server Component** | 服务端组件，默认类型，不能用状态和浏览器 API | 工具页的标题、说明 |
| **Client Component** | 加了 `'use client'` 的组件，能用状态和事件 | 工具交互区、收藏按钮 |
| **SSG** | 构建时就生成好 HTML，本项目 95% 的页面 | 阶段 4 |
| **SSR** | 每次访问时现场生成 HTML | 未来账号系统 |
| **CSR** | 先发空壳，在浏览器里用 JS 填充 | 工具的交互部分 |
| **Hydration** | 浏览器把 React 的运行逻辑"注入"静态 HTML 的过程 | 阶段 6 的核心坑（4.5 节） |
| **Hydration mismatch** | 服务端和客户端渲染结果不一致，React 会警告 | 读 LocalStorage 时机不对就会遇到 |
| **`generateStaticParams`** | 告诉 Next.js 要预生成哪些动态页面 | 阶段 4，路由自动化的关键 |
| **`generateMetadata`** | 为每个页面动态生成 title、description | 阶段 4 / 阶段 9 |
| **Tailwind CSS** | 用一组小 class 直接拼样式，不写 CSS 文件 | 阶段 3 |
| **TypeScript** | JavaScript + 类型标注，在写代码时就检查类型 | Phase 0 起，全程强制（1.6 节） |
| **Design Token** | 设计规范里的数值变量（颜色、字号、圆角） | 阶段 1 定义，阶段 3 落地 |
| **纯函数** | 同样输入永远同样输出，不影响外部 | 工具算法的硬性要求 |
| **注册表（Registry）** | 汇总所有工具的单一数据源 | 阶段 4 / Phase 2，本项目核心 |
| **插件系统** | 运行时动态加载、可卸载的扩展机制 | **本项目不需要**（见 7.4 节） |
| **LocalStorage** | 浏览器提供的按网站隔离的本地小仓库 | 阶段 6 / Phase 5 |
| **schemaVersion** | 数据结构版本号，用于未来数据迁移 | 阶段 6 / Phase 5 |
| **XSS** | 把脚本注入页面并执行的安全漏洞 | Markdown 预览工具 |
| **SSG / CSR 混合** | 同一页面：静态部分给 SEO，交互部分给用户 | 本项目工具页的标准形态 |
| **PWA** | 让网页可以"安装"到桌面、支持离线 | 第二阶段（v0.2 §7.4） |

# 10. 本文档的结论与待决事项

## 10.1 七条核心结论

| # | 结论 | 依据 |
| --- | --- | --- |
| 1 | **Next.js 的价值在于"静态部分给搜索引擎、交互部分给用户"**，本项目工具页正是这种混合形态，选型成立 | §1.2、§1.5 |
| 2 | **工具必须与界面解耦**：一个工具 = 一个定义文件（元数据 + 纯函数），界面用有限几种模板 | §3.2、§3.4 |
| 3 | **注册表是整个项目的枢纽**：路由、首页、分类页、搜索、sitemap 全部由它派生。加工具只需新增文件 + 改 1 行 | §3.2、§3.6 |
| 4 | **LocalStorage 的最大技术风险是服务端渲染冲突**，必须用"挂载后再读"处理，且界面要能区分"未知"与"空" | §4.5 |
| 5 | **Phase 2（工具系统核心）决定项目成败**，其余阶段都是它的重复应用 | §5、§6.3 |
| 6 | **契约应当分层**：框架只强制"系统运转必需的 6 个字段"，内容类字段由产品要求填写但不进类型必填 | §3.3 |
| 7 | **第一版只做"预留"，不做"实现"**。注册表 ≠ 插件系统；未来能力 ≠ 现在待办 | §7 |
