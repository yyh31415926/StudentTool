## 1. 产品定位

### 1.1 一句话定位

> **一个属于学生的数字工具工作台。**

工具负责效率，动漫负责体验。

它和普通在线工具站的区别只有三点：**更快到达、没有干扰、界面舒服**——而不是"工具更多"。

### 1.2 用户定位

| 层级 | 用户 | 说明 |
| --- | --- | --- |
| **主要用户** | **高中生** | 需求更具体、更集中（作业、信息课、自习），情感黏性更高。**所有产品决策以高中生为准** |
| **次要用户** | 大学生 | 不为其单独做设计妥协。通过"开发辅助"分类下的工具（JSON、Base64 等）自然覆盖 |

**为什么以高中生为准**：高中生的需求边界清晰（单位换算、字数统计、进制转换都是课业直接产物），而大学生的需求会向"开发工具集"无限扩散，一旦以大学生为准，产品会退化成又一个"开发者工具站"，丧失差异化。

### 1.3 使用场景

不使用"学习过程中"这类模糊表述。真实场景只有三个：

| 场景 | 典型动作 | 对应工具 |
| --- | --- | --- |
| **写作业时** | 物理化学作业里的单位换算、语文英语作文的字数限制、数学题验算 | 单位换算、字数统计 |
| **上信息课时** | 进制转换、编码转换、Markdown 笔记 | 进制转换、Base64、Markdown 预览 |
| **自习整理时** | 整理笔记、格式化文本、处理数据 | Markdown 预览、JSON 格式化、字数统计 |

**这三个场景是首页文案、工具排序、示例数据的组织依据。** 新增工具时必须能归入其中之一，否则需要先讨论是否偏离定位。

### 1.4 核心理念

| 理念 | 含义 | 具体边界 |
| --- | --- | --- |
| **工具负责效率** | 用户的核心目的是"把事做完"，不是"逛网站" | 查找工具 ≤ 2 次交互；工具操作区绝对无装饰 |
| **动漫负责体验** | 动漫元素提升亲和力与识别度，降低陌生感 | 角色只做品牌形象、页面装饰、情绪反馈三件事 |

**一句话总结两者关系**：动漫元素可以出现在**页面的任何地方，除了工具操作区**。

### 1.5 价值主张

面向用户的一句话（用于首页 slogan）：

> 「打开就能用，用完不用管。」

支撑这个主张的三个事实，必须在产品中可被验证：

| 主张 | 产品要求 |
| --- | --- |
| **打开就能用** | 无需注册、无需登录、无任何前置弹窗 |
| **用完不用管** | 无广告、无推送、不索取任何权限、不需要用户做任何配置 |
| **顺手** | 搜索即时到达；回访用户 1 次点击即可继续上次的工具 |

### 1.6 定位红线（任何阶段不可越界）

以下四条是定位的"承重墙"，任何后续版本都不得突破：

1. **不做 AI 助手**，不做对话式界面。角色永远不说话。
2. **不做社区、社交**。不做评论、排行榜、用户投稿。
3. **不做必须登录才能使用的功能**。账号只允许用于"可选的"数据同步。
4. **不做以"上瘾"为目的的机制**。不做签到、积分、等级、养成。

## 2. 产品原则

### 2.1 简洁优先

网站核心是工具。任何视觉设计、任何新功能，都不得影响以下三件事：**查找工具、使用工具、获取结果**。

判断方法：如果一个改动让用户到达结果慢了一步，它就是错的，无论多好看。

### 2.2 工具优先

动漫角色和视觉元素用于增强体验，**不是网站主体**。

- 用户第一次打开网站，看到的是工具和搜索，不是角色
- 角色的功能总时长占比应当极低
- 如果去掉所有动漫元素网站依然好用，说明工具优先做对了

### 2.3 准确优先（v0.2 新增）

**工具出错一次，用户就再也不会回来。**

这条原则凌驾于开发速度之上：宁可第一版只有 6 个工具，也不要 20 个半成品。每个工具必须有边界用例测试，宁可功能朴素，不可结果出错。

### 2.4 易扩展

新增工具时，**不应该重新设计页面**，也不应该修改首页代码。应该通过统一的工具系统，以"新增一个工具定义文件"的方式添加。

具体要求见技术研究文档 §3；本文件约束其**验收标准**（见 §3.6）：加完工具后，首页、分类页、搜索、站点地图必须**自动出现**该工具。

### 2.5 免费开放

- 第一阶段：免费使用、开源
- 未来：允许根据发展情况引入商业模式，但**受 §9.3 商业化红线约束**

## 3. 工具规划

### 3.1 工具分类

**分类采用"任务类型"维度，全站统一，共 3 类。**

| 分类 | 定位（用户视角） | slug | v1 工具 |
| --- | --- | --- | --- |
| **转换工具** | 把一种格式变成另一种 | `convert` | 进制转换、单位换算 |
| **文本处理** | 和文字打交道 | `text` | 字数统计、Markdown 预览 |
| **开发辅助** | 写代码、处理数据结构时用 | `dev` | JSON 格式化、Base64 转换 |

**为什么废弃 v0.1 的四分类**

v0.1 的四个分类混用了三种不同的切分维度（数学 / 编程 = 学科维度，"学习" = 用途维度，"文件" = 载体维度）。同一层级混用多种维度，用户无法建立稳定预期——"数学工具和编程工具并列，那学习工具算什么？"

**分类命名规则**

- 必须用**用户会说的话**，不用行业术语
- 分类数量全站控制在 **3–6 个**
- **少于 3 个工具不开新分类**；工具数不足的分类**直接不渲染**（不允许出现空分类）

### 3.2 工具清单与优先级

**第一版工具总数为 6 个**，与 v0.1 保持一致，仅重排优先级与实现顺序。

| 优先级 | 工具 | 工具 id | 分类 | 界面形状 | 一句话说明 |
| --- | --- | --- | --- | --- | --- |
| **P0** | 单位换算 | `unit-convert` | 转换工具 | 自定义 | 长度、质量、温度、面积等常用单位的互相换算 |
| **P0** | 字数统计 | `char-count` | 文本处理 | 实时统计 | 统计字符数、字数、行数，看清作文是否达标 |
| **P0** | 进制转换 | `base-convert` | 转换工具 | 数值换算 | 二进制、八进制、十进制、十六进制互转 |
| **P1** | Markdown 预览 | `markdown-preview` | 文本处理 | 左右分栏预览 | 写 Markdown 时实时看到渲染效果 |
| **P1** | JSON 格式化 | `json-format` | 开发辅助 | 文本变形 | 把压缩的 JSON 排版成可读格式，并校验错误 |
| **P2** | Base64 转换 | `base64` | 开发辅助 | 文本变形 | Base64 编码与解码，支持中文与 Emoji |

**P0 的判断依据**：三者都是高中课业的直接产物（作业里每天会遇到），且用户能在 3 秒内理解用途。

**暂缓工具（P3，第一版不实现）**

| 工具 | 处置 | 理由 |
| --- | --- | --- |
| **Hash 计算** | **降为暂缓** | 对学生的实际使用频次低，且对高中生完全无场景。保留在"开发辅助"分类的规划内，待 v1.1 根据数据决定是否实现 |
| 文本去重、大小写转换、URL 编码、时间戳转换、正则测试 | 保留为"文本处理 / 开发辅助"的未来成员 | 属于同一分类的自然延伸，不构成新分类 |
| 化学式/摩尔质量、方程求解、函数图像、日期计算、二维码生成 | 列为 v1.1 候选 | 见 §9.2 |
| 图片压缩、PDF 合并拆分 | 列为 v1.2 候选 | **v1 明确不引入任何文件上传类工具** |

### 3.3 分类与标签的双轨制

工具配置中同时存在"分类"和"标签"两个字段，职责严格区分：

| 机制 | 数量 | 维度 | 职责 | 使用场景 |
| --- | --- | --- | --- | --- |
| **分类 `category`** | **只能有 1 个** | 任务类型 | **导航** | 首页入口、分类页、面包屑 |
| **标签 `tags`** | 可有 2–4 个 | 学科 / 学段 / 场景 | **检索** | 搜索命中、未来的学科聚合 |

**为什么分类只能有一个**：用户在首页看到 3 个分类卡片时必须能立刻判断该点哪个。如果工具同时属于两个分类，这种判断就失效了。

**为什么标签要有多个**：搜"物理"能找到单位换算，搜"信息课"能找到进制转换。同一个工具可以被多个关键词命中。

**标签的落地范围（v0.2 明确）**：

- ✅ v1：`tags` 作为**搜索匹配维度**使用（零额外 UI 成本）
- ❌ v1：**不提供标签筛选界面**。工具数 ≥ 10 后重新评估

**关键收益**：未来做"高中物理工具包"这类专题页时，**只需按标签过滤，不需要重新分类、不需要修改任何工具定义**。

### 3.4 工具 id 命名规则

**`id` 一旦上线不可更改**（否则用户收藏失效、外部链接断开）。因此必须在设计阶段定死规则：

| 规则 | 说明 |
| --- | --- |
| 字符集 | 全小写英文 + 连字符，仅 `a-z0-9-` |
| 语义 | 用"功能 + 动作"结构，如 `unit-convert`、`char-count` |
| 长度 | 建议 2–3 个单词，不超过 24 字符 |
| 禁止 | 不使用拼音、不使用数字后缀（`tool1`）、不使用缩写（`bc`） |
| 变更 | **上线后禁止变更**。如需变更，必须同时在收藏数据中做迁移映射 |

已确定 id 见 §3.2 表格。

### 3.5 工具配置契约（字段清单）

任何工具都必须提供以下字段，系统才认识它。这是"加工具不改页面"能够成立的前提。字段的完整技术说明见 `Design/DeepSeek_Technical_Research.md` §3.3。

| 分组 | 字段 | 必填 | 说明 |
| --- | --- | --- | --- |
| **身份** | `id` | ✅ | 网址标识，规则见 §3.4 |
| | `name` | ✅ | 中文显示名，如"进制转换" |
| | `category` | ✅ | 所属分类，**只能一个**，取值见 §3.1 |
| | `tags` | ✅ | 标签数组，如 `["数学","计算机","信息课","高中"]` |
| **展示** | `summary` | ✅ | 一句话说明（卡片上显示） |
| | `description` | ✅ | 稍长说明段落（工具页正文 + SEO） |
| | `tip` | ✅ | 底部一句话小技巧 |
| | `exampleInput` | ✅ | "试试示例"按钮的预填内容 |
| | `keywords` | ✅ | 搜索关键词 |
| | `pinyin` | ✅ | 拼音首字母，如 `jz` 命中"进制转换" |
| | `order` | ✅ | 人工排序权重（v1 无统计数据时使用） |
| **行为** | `template` | ✅ | 使用的界面形状 |
| | `run` | ✅ | **纯函数**：输入 → 输出，或抛出可读错误 |
| | `emptyHint` | ✅ | 输入为空时的提示文案 |
| | `errorHint` | ✅ | 出错时的提示模板 |
| **可选** | `customUI` | ⬜ | 指定自定义界面组件 |
| | `seoFaq` | ⬜ | 该工具的常见问题（生成结构化数据） |
| | `hidden` | ⬜ | 临时下架但保留代码 |

**`run` 必须是纯函数——这是硬性要求。** 纯函数意味着同样的输入永远得到同样的输出，不读写任何外部状态。这样算法可以脱离界面单独测试，直接支撑 §3.6 的边界用例验收。

### 3.6 工具质量验收标准

**第一版的正式验收线是：6 个工具全部零缺陷。** 这是"准确优先"原则的落地。

| 维度 | 验收标准 |
| --- | --- |
| 输入容错 | 空输入、超长输入、非法字符、纯空格、粘贴带换行——全部有明确提示，不白屏、不报错崩溃 |
| 错误提示 | 说明"哪里错了 + 怎么改"。不卖萌、不显示原始异常、不含堆栈信息 |
| 结果准确性 | 每个工具至少 **10 组边界用例**通过（0、负数、超大数、Unicode、空字符串、换行符等） |
| 示例数据 | 每个工具提供"试试示例"，让学生 3 秒理解怎么用 |
| 复制结果 | 一键复制，有明确的成功反馈 |
| 键盘可用 | Tab 顺序合理、Enter 可提交、Esc 可清空、焦点可见 |
| 移动端 | 真机验证输入法弹出时不遮挡输入框 |
| 性能 | 首屏 LCP < 2s（4G 网络），不引入不必要的第三方库 |
| 结构 | 新增工具 = 新增定义文件 + 改一行导入，**不改动任何页面文件** |
| SEO | 独立 URL、含中文关键词的 H1、description、FAQ 结构化数据齐备 |

**各工具的专项要求**

| 工具 | 专项要求 |
| --- | --- |
| 字数统计 | 明确"字符数 / 字数 / 行数"三个口径差异，中英文混排、标点、换行分别怎么计算，需在界面上说明 |
| 进制转换 | 支持大数精度（不得因浮点溢出产生错误结果）、负数、非法字符提示 |
| Base64 | **必须正确处理 Unicode（中文、Emoji）**，这是最常见的出错点 |
| JSON 格式化 | 解析失败时必须给出**行号与原因**，不接受只说"格式错误" |
| Markdown 预览 | **必须做 XSS 防护**（这是全站唯一可能被注入脚本的地方），渲染库必须过滤危险标签 |
| 单位换算 | 温度换算为特例（带偏移的线性变换，非简单乘法），必须有独立测试 |

## 4. 视觉设计

### 4.1 整体风格

| 关键词 | 说明 |
| --- | --- |
| 动漫、可爱、治愈 | 体验层：降低陌生感，提升亲和力 |
| 未来科技、学习基地 | 空间感：让网站像一个"地方"，而不是一个页面 |

**视觉方向**：未来学习基地——学生使用的未来数字空间。

**明确不是**：

- ❌ 儿童教育网站（不幼稚、不低龄化）
- ❌ 专业开发者工具站（不密集、不冷硬、不英文优先）

**关键配比**：一个二次元风格的工具站，**画面约 80% 应是克制的灰阶，20% 才是色彩与角色**。反过来做就会从"工具站"退化成"活动页"，专业感全失。

### 4.2 角色定位

**角色是什么**

| 是 | 说明 |
| --- | --- |
| 品牌形象 | Logo、favicon、社交分享图、站点识别 |
| 页面装饰 | 首屏、空状态、页面留白区的视觉元素 |
| 情绪反馈 | 成功、失败、空数据的即时反馈 |

**角色不是什么（禁止清单）**

| 不是 | 具体禁止 |
| --- | --- |
| ❌ 不是 AI 助手 | 不提供任何 AI 对话能力，不做"问我"入口 |
| ❌ 不是聊天角色 | **禁止对话气泡、语音气泡、聊天输入框** |
| ❌ 不做主动指导 | **禁止主动弹出提示、引导蒙层、旁白式打断**。角色不主动说任何话 |
| ❌ 不是导航者 | 不允许点击角色触发跳转、菜单、多帧交互动画 |

**风格**：动物 + 机器人混合。特点是可爱、有科技感、适合学生。

**v1 资产范围**：**1 个主角色**，输出 4 个状态——标准（`mascot-main`）、欢迎/空状态（`mascot-welcome`）、成功（`mascot-success`）、错误（`mascot-error`）。格式优先 SVG，其次高分辨率透明 PNG。

**后续**：根据工具分类增加辅助角色（v1.2+，需先确认主角色获得正向反馈）。

**⚠️ 防止定位漂移的最关键一条：角色文案必须用"旁白式"，而不是"角色第一人称"。**

| ❌ 错误（角色口吻） | ✅ 正确（旁白口吻） |
| --- | --- |
| "我帮你找找工具吧～" | "还没有收藏工具。" |
| "把这个输进去，我来算！" | "在左侧输入需要转换的数值。" |
| "哎呀，你输错啦～" | "输入包含非法字符，请只输入数字。" |

**原因**：只要角色开始用第一人称"说话"，用户就会立刻把它当成 AI 助手——这个预期一旦建立，几乎无法纠正，直接违背 §1.6 的定位红线。

### 4.3 角色出现规则

**✅ 允许出现的 5 个位置（按价值排序）**

| 优先级 | 位置 | 呈现方式 | 价值 |
| --- | --- | --- | --- |
| ★★★ | **空状态** | 半身像 + 一句旁白 | 空状态是工具站体验最冷的死角，也是角色最能创造记忆点的地方 |
| ★★★ | **Logo / 顶栏** | 角色头部圆形头像（24–32px） | 品牌识别的最小成本实现 |
| ★★ | **首页首屏** | 完整形象，占右侧 35–40% 区域 | 第一印象与风格定调 |
| ★★ | **反馈态** | 成功/错误的迷你表情变化（仅头部，≤64px） | 把枯燥的操作变成有反馈感的行为 |
| ★ | **工具页留白区** | 小尺寸（≤120px），位于操作区**外侧**的边距内 | 纯装饰，维持世界观的连贯 |

**❌ 禁止出现的 4 个位置 / 4 种用法**

| 禁区 | 原因 |
| --- | --- |
| 输入框、按钮、输出结果的相邻区域 | 直接干扰注意力，违背"简洁优先" |
| 工具页正中央，或输入区与输出区之间 | 打断操作动线，并大幅增加纵向滚动 |
| 移动端与内容争夺空间 | 移动端角色必须降级为装饰层或直接隐藏 |
| 自动循环播放的全身动画 | 持续运动的元素会不断抢夺视线，是效率杀手 |
| （用法）在错误提示中卖萌 | 用户犯错时最需要清晰的修复指引。**错误提示必须专业、明确、可操作** |
| （用法）可点击触发多帧交互动画 | 开发成本高，"复杂动画"已明确排除在第一版范围外 |

### 4.4 视觉量化约束

以下数值是**硬性红线**，后续开发与验收直接对照执行：

| 约束项 | 数值 |
| --- | --- |
| 角色在**工具页**占屏幕面积 | ≤ 15% |
| 角色在**首页首屏**占屏幕面积 | ≤ 25% |
| 工具操作区（输入 / 按钮 / 输出）周围的装饰元素 | **0 个** |
| 装饰元素不透明度（背景纹样等） | ≤ 12% |
| 正文文字对比度 | ≥ 4.5:1（WCAG AA） |
| 输入框 / 按钮区域背景 | 纯色或极浅渐变，**不透明**（纹样不得透过表单控件） |
| 单个动画时长 | ≤ 300ms |
| 动效缓动曲线种类 | ≤ 3 种 |
| `prefers-reduced-motion` | **必须支持**，提供动效降级 |
| 移动端角色高度 | ≤ 120px，或隐藏 |
| 首屏可见内容 | 搜索框 + 分类入口必须在 768px 高度内可见（适配 1366×768 笔记本） |
| 触控目标（移动端） | ≥ 44×44px |
| 移动端正文字号 | ≥ 16px |

**补充红线**：**工具区内不得使用角色配色作为功能性颜色。** 成功 / 警告 / 错误色必须固定在语义色板上，与角色配色解耦。例如不能让"复制成功"用角色头发的粉色。

### 4.5 色彩与字体

**色彩系统（三档结构）**

| 层级 | 数量 | 用途 | 方向 |
| --- | --- | --- | --- |
| **主色** | 1 个 | 品牌、主按钮、链接、选中态 | 偏冷色的科技蓝紫 / 青蓝。与"未来学习基地"一致，长时间使用不刺眼 |
| **辅色** | 2–3 个 | 角色、分类色标、装饰点缀 | 从角色设定取色（暖色系：粉 / 橙 / 薄荷）。**只用于装饰和非关键信息** |
| **中性色** | 6–8 档灰阶 | 背景、卡片、边框、正文 | 面积占比必须 ≥ 80% |

**字体**

| 用途 | 要求 |
| --- | --- |
| 中文正文 / 界面 | 系统字体优先（苹方 / 微软雅黑 / 思源黑体）。**中文界面禁用圆体与手写体**——会显著降低可读性 |
| 数字与代码 | **必须使用等宽字体**（JetBrains Mono / Fira Code）。进制转换、Base64 结果、JSON 输出的对齐依赖等宽，这是工具站专业度的分水岭 |
| 字号阶梯 | 建议 6 档：12 / 14 / 16 / 20 / 28 / 40。**全站不超过 6 档** |

**规范落地要求**：以上数值必须定义为设计 token（颜色 / 字号 / 圆角 / 间距 / 阴影），成为全站唯一来源。**如果设计规范只写在文档里，半年后代码里会出现十种蓝色。**

### 4.6 页面装饰

| 元素 | 用法 |
| --- | --- |
| 细网格 / 星点 | 低不透明度（≤8%）作为页面背景底纹，呼应"数据空间" |
| 圆角卡片 + 柔和阴影 | 统一圆角（建议 12–16px）。阴影不超过两层，避免厚重的"新拟态"感 |
| 发光描边 | 仅用于重点按钮或选中态，不做大面积发光 |
| 几何小图标 | 与角色世界观一致（数据碎片、能量线、坐标点），用于分类图标 |
| 分割线 | 极浅色 1px 线。**不使用装饰性花边** |

### 4.7 暗色模式界定（重要）

v0.1 存在概念歧义：§7 排除"多主题系统"，但 §4.1 的"未来科技"方向天然适合暗色底。v0.2 明确界定：

| 概念 | v1 是否做 | 说明 |
| --- | --- | --- |
| **暗色模式** | ✅ **做** | 定义亮 / 暗两套 token，**跟随系统偏好自动切换** |
| **主题切换器** | ❌ 不做 | 不在界面上提供"切换主题"的控件 |
| **多主题皮肤系统** | ❌ 不做 | 多套配色 + 主题管理界面，属于商业化阶段能力 |

**判断依据**：学习工具的高频使用时段是晚上；暗色与"未来科技"视觉方向天然契合；实现成本仅为多定义一组 token，因为色彩已 token 化。**这不构成"多主题系统"**——多主题系统指的是用户可切换多套皮肤并管理它们。

## 5. 网站结构

### 5.1 首页

**首页的唯一目标：让用户以最少的交互到达工具页。**

所有设计取舍服从这一条。任何"好看但需要多一次点击"的模块，都应被砍掉或降级。

**首页只有 4 个功能区**（v0.1 的 6 个模块收缩而来）：

| 区块 | 内容 | 层级 |
| --- | --- | --- |
| **顶栏** | Logo（角色头像 + 站名）+ **全局搜索** + 我的工具箱 + 开源地址 | 常驻 |
| **首屏（Hero）** | 一句价值主张 + **全局搜索框**（第一优先级元素）+ 主视觉角色 | L1 |
| **分类入口** | 3 个分类卡片（转换工具 / 文本处理 / 开发辅助） | L1 |
| **常用工具** | 高频工具卡片网格 | L2 |
| **我的工具箱** | 首行"继续上次"；下方收藏 + 最近使用；无数据时显示角色空状态 | L2 |
| **页脚** | 关于 · 开源地址 · 反馈 | L3 |

**布局要求（桌面端）**

| 要点 | 规格 | 理由 |
| --- | --- | --- |
| Hero 采用**非对称双栏**（文字左、角色右） | 文字区约 60%，角色区约 40% | 避免居中对称布局的"活动页感"，更像工具站 |
| 搜索框在首屏垂直位置 60% 以上 | 1366×768 下无需滚动即见 | 学生笔记本普遍为 768–900 高度 |
| 角色不得遮挡或压住搜索框 | 两者水平不重叠 | 搜索是效率核心，视觉必须让路 |
| "我的工具箱"必须在**首屏可见范围**内 | 不做深藏 | 保证回访用户 1 次点击离开首页 |
| 顶栏搜索与 Hero 搜索**共用同一组件** | 不做两套 | 编辑一致性 |

**明确不做**

- ❌ 轮播 Banner
- ❌ 弹窗、公告条、Cookie 提示
- ❌ 首页独立的"标签筛选"交互
- ❌ 独立配置的"推荐工具"（用排序规则替代，见下）

**"常用工具"的排序规则**

第一版没有后端统计数据，采用**人工预设静态顺序**（单位换算 → 字数统计 → 进制转换 → Markdown 预览 → JSON 格式化 → Base64）。但**代码结构上必须预留排序函数的位置**，后续接入使用数据时只改一个函数：

```
排序权重 = 收藏数 × 3 + 近 7 天使用次数 × 2 + 学生场景相关度 × 1
```

### 5.2 分类页

| 项目 | 要求 |
| --- | --- |
| 网址 | `/categories/{slug}`，slug 见 §3.1 |
| 内容 | 面包屑 + 分类名 + 一句话说明 + 该分类下的工具卡片 |
| 卡片信息 | 工具名 + 一句话说明（`summary`）+ 收藏状态 |
| 排序 | 按分类内的 `order` 权重 |
| 空分类 | **不渲染**（分类下少于 3 个工具时，该分类不上线） |
| 未找到分类 | 显示 404 页 + 角色空状态，提供"返回首页"与搜索入口 |

**为什么卡片必须带一句话说明**：分类页是"目标模糊"用户的主要落点（详见 §5.5），一句话说明直接降低选择成本。

### 5.3 工具页

**设计原则**：工具区域保持简洁，页面周围增加动漫视觉元素。

**结构（自上而下）**

```
面包屑
工具标题（H1，含中文关键词）
一句话说明
输入区域
操作按钮
输出区域
复制结果
收藏按钮
（底部）小技巧：一句话  ← 来自工具配置的 tip 字段
```

**布局规则**

| 区域 | 规则 |
| --- | --- |
| 操作区（输入 → 按钮 → 输出） | **绝对无装饰元素**。背景不透明，无纹样透过 |
| 操作区宽度 | 建议 640–800px 居中，避免超宽行影响阅读 |
| 角色位置 | 仅允许出现在操作区**外侧**的留白边距内，尺寸 ≤ 120px，面积 ≤ 15% |
| 右侧/左侧留白 | 宽屏下可用于角色与装饰；窄屏下直接收起 |
| 输入 / 输出 | 使用等宽字体；结果区支持一键复制 |

**统一模板要求**

界面形状归纳为有限的几种，由配置中的 `template` 字段决定：

| 形状 | 交互模式 | 适用工具 |
| --- | --- | --- |
| 文本变形 | 输入文本 → 点按钮 → 输出文本 | Base64、JSON 格式化 |
| 数值换算 | 输入数值 + 选单位 → 输出数值 | 进制转换 |
| 实时统计 | 边输入边显示统计，无"转换"按钮 | 字数统计 |
| 左右分栏预览 | 左侧编辑，右侧实时渲染 | Markdown 预览 |
| 自定义 | 交互复杂，无法套用模板 | 单位换算 |

**模板数量必须受控（≤ 5 个）。** 新增模板时必须写明"未来哪个工具还会用它"；如果只有这一个工具需要，就放自定义组件，**不要污染模板**。

**模板与工具定义的职责边界**

| 模板负责（写一次，稳定） | 工具定义负责（各写各的） |
| --- | --- |
| 输入 / 输出框的布局与样式 | 输入框的 placeholder 文案 |
| 按钮位置与禁用逻辑 | 需要几个输入控件 |
| 复制按钮与复制成功反馈 | 具体的计算规则 |
| 空输入、错误状态的展示方式 | 错误文案的具体措辞 |
| 键盘操作（Enter 提交 / Esc 清空） | — |
| 移动端如何堆叠、无障碍属性 | — |

一句话：**模板管"长什么样、怎么操作"，定义管"算什么、说什么"。**

### 5.4 我的工具箱

| 项目 | 要求 |
| --- | --- |
| 网址 | `/my-toolbox` |
| 账号 | **无需账号**，数据存于浏览器本地存储 |
| 功能 | 收藏工具、最近使用工具、"继续上次" |
| 数据范围 | 只存工具 id、时间戳、使用次数。**绝不存储用户输入的内容与转换结果** |
| 数据版本 | 必须带 `schemaVersion` 字段，便于未来迁移 |
| 数据说明 | 页面上用一行小字说明"数据保存在本机浏览器"，诚实且为未来"登录后同步"埋下期待 |
| 加载状态 | 读取期间显示**骨架屏**，不是空状态 |
| 空状态 | 使用角色 + 旁白式文案 |

**近期使用判定条件（v0.2 定案）**：**"打开工具页"不算"使用"，必须"产生了有效输出"或"点击了操作按钮"才记录。**

理由：如果误点进来也留下记录，"继续上次"会变得不可信。

**明确不做**：v1 不提供"清空我的数据"按钮（无账号下误触不可恢复），仅做文字说明。按钮延后至 v1.1。

**未来**：登录后可同步（见 §9.2 阶梯 4）。

### 5.5 用户浏览流程

**路径 A · 目标明确（预计 60%+，必须做到最短）**

```
进入首页 → 搜索框输入关键词 → 下拉即时显示匹配工具 → 回车/点击 → 工具页
         ↑ 理想：2 次交互，且不发生页面跳转（下拉直接选）
```

**关键设计**：搜索必须是**即时匹配的下拉**，不是跳转到搜索页。用户输入"进"时就应该看到"进制转换"，输入"单"就看到"单位换算"，输入 `jz` 也能命中"进制转换"。

> **这一个小设计的价值，大于首页任何视觉装饰。**

**路径 B · 目标模糊（预计 25%）**

```
进入首页 → 扫视 3 个分类卡片（一眼看完）→ 进入分类页 → 根据一句话说明选择工具
```

**关键设计**：分类必须少而清晰（3 个，一眼看完）。

**路径 C · 回访用户（预计 15%，留存价值最高）**

```
进入首页 → 直接看到"我的工具箱"首行的"继续上次：单位换算" → 1 次点击直达
```

**关键设计**：**回访用户必须 1 次点击离开首页。**

## 7. 技术方向

### 7.1 技术栈

| 层 | 选型 | 状态 |
| --- | --- | --- |
| 前端框架 | **Next.js**（App Router） | 暂定 |
| UI 库 | **React** | 暂定 |
| 样式 | **Tailwind CSS** | 暂定 |
| 动效 | Framer Motion（仅用于轻量过渡） | 可选 |
| 数据存储 | **浏览器 LocalStorage** | 暂定 |
| 语言 | TypeScript（推荐） | 建议 |

**选择 Next.js 的核心原因**：让"工具页的静态部分（标题、说明、FAQ）供搜索引擎读取"与"交互部分（输入、结果）在浏览器即时响应"在同一页面共存。这是本项目 SEO 与工具体验能同时成立的技术基础。

> 技术原理、目录结构、工具系统设计、LocalStorage 细节见 `Design/DeepSeek_Technical_Research.md`。本文件只约束**要求**，不重复推演过程。

### 7.2 架构要求

| 要求 | 说明 |
| --- | --- |
| **单一数据源** | 全站工具信息来自唯一的工具注册表。首页、分类页、搜索、站点地图全部由它派生，**禁止手写硬编码工具列表** |
| **算法与界面解耦** | 工具算法必须是纯函数，放在不依赖 React 的目录下，可独立测试，并为未来 PWA / App 复用 |
| **分层清晰** | 数据层 / 组件层 / 页面层职责单一，依赖只能自上而下 |
| **服务端与客户端分离** | 纯文字内容留在服务端（保 SEO），只有需要交互的部分才是客户端组件 |
| **路由自动化** | 工具页使用单一动态路由，新增工具不改路由文件 |

### 7.3 数据存储原则

| 项目 | 要求 |
| --- | --- |
| 存储位置 | 浏览器 LocalStorage，**v1 无后端、无账号** |
| 允许存储 | 收藏的工具 id、最近使用的工具 id + 时间 + 次数、偏好设置 |
| **禁止存储** | ❌ 用户输入的内容、❌ 转换结果、❌ 登录态与 Token、❌ 图片文件 |
| 键名前缀 | 统一命名空间前缀，键名必须定义为常量，代码中禁止手写字符串字面量 |
| 版本管理 | 必须带 `schemaVersion`；迁移逻辑集中在一处；遇到更高版本时只读不覆盖 |
| 读取校验 | 读取时必须丢弃"注册表中已不存在"的工具 id（保障未来淘汰工具不产生坏体验） |
| 写入失败处理 | 必须回滚界面状态并提示。**不允许出现"界面显示已收藏，刷新后却没了"的静默失败** |
| 服务端渲染 | 首屏一律使用"未知"状态，挂载后再读取本地数据。**界面必须能区分"未知"与"空"** |
| 封装 | 组件永远不直接调用 LocalStorage，必须通过统一的 hooks 与数据接口层 |

**未来迁移路径**：`LocalStorage → 可选账号云同步`。为此，数据读写的**接口层必须独立于实现**，将来只需替换最底层实现，上层组件与 hooks 一行不改。

### 7.4 平台规划

| 阶段 | 内容 |
| --- | --- |
| **第一阶段** | 网页版。支持 PC 浏览器与手机浏览器，响应式设计 |
| **第二阶段** | PWA（可安装、离线可用）。**前提：移动端使用占比 ≥ 40%** |
| **第三阶段** | 根据用户需求考虑 App。架构上已通过"算法与界面解耦"预留复用路径 |

## 8. SEO 要求

Next.js 的 SEO 优势**不会自动生效**，必须靠以下内容兑现。SEO 是本项目最主要的**低成本获客渠道**——中文长尾词（"在线进制转换""字数统计 作文"）搜索量大、竞争弱、意图精准。

## 9. 后续扩展方向

### 9.1 扩展原则

扩展只允许沿三个轴向进行，且**不得改变 §1.6 的定位红线**：

| 轴 | 含义 | 越界示例（禁止） |
| --- | --- | --- |
| **更全** | 覆盖更多学生真实需要的工具，质量不下降 | 不做题库、课程、笔记、待办等"学习管理"功能 |
| **更快** | 更短路径、更少点击、更好的键盘与批量体验 | 不引入需要登录才能使用的能力 |
| **更暖** | 角色与体验更自然、更有归属感 | 不让角色变成会说话的助手，不做养成交互 |

**扩展的前提永远是**：现有功能零缺陷已达成。**不因为"想加"而加，只因为"数据证明需要"而加。**

### 9.2 扩展阶梯

**阶梯 1 · v1.1 —— 补齐高中生刚需工具（最高优先）**

| 候选工具 | 学生痛点 | 数据依据 |
| --- | --- | --- |
| 化学式 / 摩尔质量计算 | 高中化学作业高频 | 待验证 |
| 一元 / 二元方程求解 | 数学作业验算 | 待验证 |
| 函数图像绘制 | 数学理解函数性质 | 待验证 |
| 日期计算（天数差、倒计时） | 考试倒计时、作业截止 | 待验证 |
| 二维码生成 | 社团、班级通知 | 待验证 |

**同步进行**：**数据驱动淘汰**。上线 3 个月后，把使用次数为 0 的工具下线，把使用次数最高的 3 个工具做深度优化。

**阶梯 2 · v1.2 —— 效率深化（最能强化定位）**

- 命令面板（Cmd / Ctrl + K）：键盘直达任意工具，是"快"这个定位最有力的表达
- 工具间互跳（如进制转换 → Base64）
- 批量处理（多行输入 / 多文件）
- 结果导出与分享链接（带预填参数）
- 标签筛选界面（工具数 ≥ 10 后）
- 输入历史（默认关闭、独立开关、单独设计）
- 辅助角色

**阶梯 3 · v2.0 —— PWA 与工程化**

- PWA：可安装、离线可用（工具全是纯前端逻辑，天然适合离线）
- 工具全面配置化收口
- 自建轻量埋点（**不引入第三方追踪 SDK**），驱动排序与淘汰

**前提**：移动端使用占比 ≥ 40%。

**阶梯 4 · v2.x —— 可选账号与个性化（商业化落脚点）**

- 账号**仅用于同步收藏**，且**完全可选**：不登录也能使用全部功能
- 个性化作为付费点：角色外观、主题皮肤
- 符合 §9.3 红线

**阶梯 5 · 长期 —— 学科工具包（谨慎）**

- 按标签聚合出"高中物理工具包""离散数学工具包"，**无需重构分类**
- **前提**：内容质量需真实教学视角审核。内容出错会直接摧毁工具站的信任基础

### 9.3 商业化红线（建议现在就固定下来）

在压力下做出的商业化决策最容易伤害核心体验。因此提前明确边界：

| ✅ 允许 | ❌ 不允许 |
| --- | --- |
| 卖外观（角色皮肤、主题、装扮） | 把工具功能锁在付费墙后 |
| 卖容量 / 性能（更大文件上限、批量处理） | 强制登录才能使用基础工具 |
| 接受自愿赞助 / 开源打赏 | 插入广告或第三方追踪 |
| 卖"周边"性质的内容 | 出售或共享用户数据 |

### 9.4 各扩展方向的前提与风险

| 方向 | 前提条件 | 主要风险 |
| --- | --- | --- |
| 增加工具 | 现有工具零缺陷已达成 | 数量增长导致质量下滑 |
| 命令面板 | 工具数 ≥ 12 | 用户教育成本，需要提示 |
| 标签筛选 | 工具数 ≥ 10 | 过早引入，交互成本大于收益 |
| PWA | 移动端使用占比 ≥ 40% | 过早投入，收益不明显 |
| 账号系统 | 出现明确的"跨设备同步"诉求 | 破坏"打开即用"的核心体验 |
| 学科工具包 | 相关内容可被专业审核 | 内容出错摧毁信任基础 |
| 角色 IP 化 | 主角色获得正向用户反馈 | 过早投入，方向可能推翻重来 |

## 10. 开发原则

### 10.1 模块化

功能必须独立。新增工具尽量**只增加配置和组件**，不改动既有页面。

**验收方式**：加完一个工具后，首页、分类页、搜索、站点地图应**自动出现**该工具。如果没有自动出现，说明有人绕过了统一工具系统写了硬编码列表——这属于必须立即纠正的错误。

### 10.2 保持代码清晰

避免：重复代码、临时代码、无意义依赖。

具体约束：

- 不建"所有工具挤在一起"的大文件，一个工具一个定义文件
- 工具定义文件之间**不得互相引用**，公共逻辑抽到共享工具库
- 文案与逻辑分离，便于反复打磨与校对
- 组件不直接读写本地存储，必须通过统一接口层

### 10.3 修改前理解现有结构

任何 Agent 修改本项目之前，**必须先阅读**：

1. `Documents/WebsiteDesignDocument_v0.2.md`（本文件）
2. `AGENT_RULES.md`
3. `Design/DeepSeek_Technical_Research.md`（涉及目录结构、工具系统、存储设计时）

并遵循既有设计。**不得在未阅读的情况下重新设计页面结构或分类体系。**

### 10.4 新增工具的标准流程

```
1. 新增工具定义文件，填完整字段契约（§3.5）
2. 在工具聚合入口加一行导入
3. 判断能否复用现有界面模板；不能复用需说明原因（模板总数 ≤ 5）
4. 编写边界用例测试：空输入 / 非法字符 / 超长输入 / 极值（0、负数、超大数）
   / Unicode / 换行符 —— 至少 10 组
5. 测试通过后，逐项检查：SEO 文案是否齐全、错误提示是否清晰、
   移动端是否可用、键盘是否可操作
6. 确认首页、分类页、搜索、站点地图已自动出现该工具
```

**第 6 步是这套体系的"自检点"。**

### 10.5 三条不可违反的红线

1. **角色不挡路** —— 工具操作区周围 0 个装饰元素；角色在工具页面积 ≤ 15%
2. **不做会说话的助手** —— 无对话气泡、无主动指导、无聊天功能；文案一律旁白式
3. **6 个工具零缺陷** —— 工具出错一次，用户就再也不会回来

## 11. 项目愿景

打造一个：

**简单、有趣、有温度的学习工具空间。**

让学生不仅能快速完成任务，也能喜欢打开这个网站。

**但这句话有前提**：先做到"快、准、干净"，再谈"有趣、有温度"。动漫元素是最好的加分项，也是最糟的遮羞布——如果工具本身不好用，角色只会让用户觉得这个网站不专业。

**顺序不能颠倒。**

## 附录 B · 上线后验证指标

用于判断"工具负责效率，动漫负责体验"是否真的成立。**下表的健康参考值为假设，需上线后用真实数据校准，不作为验收标准。**

| 指标 | 衡量什么 | 健康参考 | 不健康时的动作 |
| --- | --- | --- | --- |
| 首页 → 工具页转化率 | 首页是否有效 | ≥ 60% | 检查搜索是否好用、分类是否清晰 |
| 搜索使用率 | 搜索框是否是主路径 | ≥ 30% 的首页用户使用过 | 提高搜索框视觉权重 |
| 平均单次会话工具数 | 是否有"逛"的行为 | ≥ 1.5 | 增加工具间互跳与相关推荐 |
| **7 日回访率** | 留存是否成立 | ≥ 15%（无账号的纯工具站已属良好） | 强化"继续上次"与收藏入口 |
| 收藏转化率 | "我的工具箱"是否被使用 | ≥ 10% 的用户产生过收藏 | 降低收藏操作成本，优化空状态引导 |
| 移动端占比 | 是否需要提前做 PWA | ≥ 40% 可考虑提前 | 未达则维持现状 |
| 工具使用分布 | 哪些工具真被需要 | 头部 3 个工具占 ≥ 60% 使用量属正常 | 依据分布淘汰长尾工具，加深头部工具 |
| 无结果率 | 搜索质量 | ≤ 5% | 补同义词、修正匹配逻辑 |

**最重要的一个判断**：

> 如果"首页 → 工具页转化率"很高，但"7 日回访率"上不去，说明**网站是好用的，但没有让人记住的理由**。
>
> 此时的解法**不是加工具**，而是强化"这是你的工作台"的归属叙事（收藏 + 最近使用 + 继续上次 + 角色）。
